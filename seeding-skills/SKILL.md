# Seeding Skills — 在实践中生长的 skill

> **本 skill 的主型:元型**(副型:判断型——它也在教"哪种写法该选")。

## 核心哲学(双维度)

**skill 是一颗在实践中生长的种子;它的作用,是给 agent 提供"能把推理压对、引对"的上下文与能力。**

**静态维度:场景化的上下文与能力包。** 通过五种机制改变行为:**补先验**(它不知道的事实)、**缩空间**(红线 / 不变量 / 反模式)、**定路径**(步骤 / 入口 / 产物)、**卸推理**(脚本 / API / 可执行检查)、**存协议**(跨会话的记忆与交接)。agent 能读代码、能写脚本——skill 只补它读不出来、想不对、或不该每次重做的东西。

**动态维度:从小开始、在复盘中演化。** 一次性写完美的 skill 不存在;给 agent 一个可用起点,让实际使用反过来塑造它。高频路径固化为库函数,常见错误沉淀为约束规则,文档膨胀后拆分文件。

**先判型,再动笔。** 类型决定写法与验收;细节在 `references/skill-types.md`,本文件只做分诊。

## 判型:先确定"缺了它会怎么失败"

类型不按主题切,按**缺了它时 agent 的失败模式**切。这是**失败模式轴**,与上面的五种作用机制是两个轴。

| 类型 | 缺了它会怎样 | 主写 | 默认验收 | 演化信号 |
|---|---|---|---|---|
| **知识型** | 不知道 / 记错 | 反先验事实 + 来源 + 适用范围 + 失效条件 | 来源核对 + teach-back | 新证据、过期、互相矛盾 |
| **判断型** | 在多个合理选项里自信选错 | 决策卡、红线、反模式、本地标定、被拒方案 | 消融 / 负控 / teach-back | 重复踩坑、因它改变过决策 |
| **流程型** | 漏步、乱序、交接断裂 | 步骤、入口 / 出口条件、产物、失败分支、退化路径 | 成功路径 + 失败路径 + 产物检查 | 步骤被跳过、返工 |
| **能力型** | 每次重写脚本 / 执行不确定 | 真实 API、可跑示例、确定性检查、错误语义 | 可执行测试 + 负控 + 干净基线 + 环境矩阵 | 高频脚本固化、工具版本升级 |
| **元型** | 产出物结构漂移 / 不可复核 | 方法论、模板、判定规则、审计清单 | teach-back / 产出审计 | 规则空转、被绕过 |

- **混合型:** 一个主型(决定验收)+ 最多一个副型(只影响写法);不要按部件拆型。
- **反仪式:** 分型只用于选适用规则,不要求填表;分进去后规则没差别 = 这一刀切错了。
- 每型必写 / 不写、与 §2 / §3 / §6 的映射、误判案例:[references/skill-types.md](references/skill-types.md)。

## 结构与加载(要点)

- 每个 skill = 独立目录 + `SKILL.md`;frontmatter 至少 `name`(与目录同名)与 `description`(做什么 + TRIGGER)。
- `description` 是常驻成本,也是唯一触发依据:精简、具体、覆盖用户话术(中英)。
- 加载层级:`description` 常驻 → `SKILL.md` 触发时全文 → `references/` 按需。
- 辅助文件按需:`references/`(详细文档)、`templates/`、`examples/`、`scripts/`、`core/`;引用保持一层深度(按最终消费者位置算)。
- 字段、目录、token 经济、description / name 写法、自由度、脚本、测试:[references/skill-anatomy.md](references/skill-anatomy.md)。

## 静态原则:skill 当下怎么写

### 1. 顺着 agent 的自然工作流

以能力型为例:读需求 → 找入口 → 看示例 → 读代码 → 写脚本 → 执行 → 反馈 → 修正。其它型替换对应动作:知识型 = 查来源,判断型 = 对照决策卡,流程型 = 按步骤产出,元型 = 套模板 / 审计。

skill 必须在这条路径上**加速**;任何"先做 X 再做 Y"的设计,如果 X 不是 agent 自然会做的,就会被跳过。

### 2. 给真实 API + 示例,不要新抽象

直接给函数签名和真实示例。不要发明中间层(伪命令名、词表、DSL)。

```
✅ safe.replace_text(anchor, new_text)
❌ content-replace-text → (翻译) → safe.replace_text(...)
```

判据:agent 看到中间层后,会不会立刻把它翻译回真实 API?会 → 中间层无用。

### 3. 写代码读不出来的信息

| 写 | 不写 |
|---|---|
| 领域知识(为什么这么设计) | 函数实现细节 |
| 边界条件、陷阱、不变量 | 函数做什么(看代码就知道) |
| 何时用 / 何时不用 | 参数定义(看签名) |
| 反模式(防踩坑) | 基础语法(agent 已经会) |
| 真实可复制的示例 | 罗列所有可能的操作 |

判据:**删掉它,读者还知道该怎么做吗?** 知道 → 删;不知道 → 留(并写短)。

### 4. 确定性 > 优雅

agent 宁可走确定性高的长路(直接调函数,签名错立刻挂),也不走优雅但不确定的短路(组合后翻译,可能错、可能跳过)。其它型同理:可判定的规则 / 模板 / 检查 > 依赖语感的表述。

### 5. 少即是多

context 是公共资源,skill 跟对话历史、其他 skill 共享 window。

- SKILL.md 正文 ≤ 500 行(目标 100–300,越短越好)
- 引用保持一层深度
- 每段都问"这占的 token 值得吗?"

### 6. 示例驱动

真实可复制的示例比抽象规则有用 10 倍;2–3 个覆盖典型场景即可。能力型的示例必须可直接跑;其它型的形态按主型(见 `references/skill-types.md`)。

### 适用域:§2 / §3 / §6 是"能力型"的默认判据

§2 / §3 / §6 以有代码 / 可执行 API 为前提;在知识型、判断型、流程型、元型上会空转——不是作废,是判据没有指称对象。逐型等价判据见 [references/skill-types.md](references/skill-types.md)。

## 动态原则:skill 怎么演化(seeding 的真正核心)

静态原则回答"怎么写第一个版本";动态原则回答"怎么让 skill 在实践中变好"。

### 1. 从小开始

只写最关键的:入口(按主型)+ 2–3 个示例 + 边界。不预测未来需求——你不知道 agent 实际会怎么用它,等用过了才知道。

### 2. 观察实际使用

看 agent 怎么走:它用了示例吗?绕过了哪些部分(冗余)?反复写什么脚本(固化信号)?反复踩什么坑(沉淀信号)?哪里需要看 references 才能继续(SKILL.md 缺什么)?

观察方法:另一个 agent 实例跑典型任务,作者在旁边看;或复盘对话历史。

### 3. 固化高频路径

反复写同样的脚本 → 固化为库函数,SKILL.md 改成"用 X 函数"。固化的库比文字指令可靠(签名错立刻挂)。

### 4. 沉淀常见错误

反复踩同样的坑 → 加一条安全规则 / 反模式。一条"不要 X,因为 Y"胜过十条正面指令。

### 5. 拆分膨胀文件

SKILL.md 超过 500 行 → 领域知识拆到 `references/`,示例拆到 `examples/`,SKILL.md 只留导航和入口。拆分的标准是**领域边界**,不是行数。

### 6. 演化是作者的事

agent 用 skill,作者养 skill。作者在复盘时观察、判断、动手;agent 不会自动更新 skill。

### 7. 保留生长空间

结构模块化,未来拆分时能干净抽出;章节边界清晰,不要交叉引用纠缠。

## 结构模板

```markdown
---
name: <skill-name>
description: "<做什么>. TRIGGER: <精准触发词>"
---

# <Skill 名称>

## 定位
一句话说什么 + **主型(/副型)** + 关键边界(不做什么 / 不替用户做什么)。

## 何时用 / 不该用
精准的触发条件 + 排除场景(防误触发)。

## Workflow / 入口
按主型:能力型 = 入口 API + 示例;判断型 = 决策卡 + 反模式;知识型 = 事实与来源;流程型 = 步骤 + 产物 + 失败分支;元型 = 规则 + 模板 + 审计。

## 示例
2–3 个真实示例(形态按主型)。

## 边界
- 能做 / 不能做
- 安全规则 / 适用范围 / 失败分支(按主型)

## 参考(可选)
links to references/*.md(一层深度)
```

> 这是默认骨架;逐型替换项与清单见 [references/skill-types.md](references/skill-types.md)。实际 skill 需要验收段时,补 `## 验收`(档位 + 入口)。

## 写作要点(按型取用)

- **description:** 第三人称 + 做什么 + 什么时候触发;好坏示例见 `references/skill-anatomy.md`。
- **name:** 小写 / 字母数字与 `-` / ≤64 / 与目录名一致。
- **自由度:** 判断 / 知识 / 元型偏高自由,流程型中,能力型低。
- **反馈循环 / 脚本:** 主要适用于能力型与流程型;测试对所有型适用——写前先跑不带 skill 的基线,写后用另一个 agent 实例测。
- 详细写法:[references/skill-anatomy.md](references/skill-anatomy.md)。

## Workflow A: 创建新 skill

1. **识别领域 + 判型**——解决什么问题?没有它 agent 会怎么失败?按失败模式判主型。
2. **找底层资产**——能力型找库 / 工具 / API;其它型找来源、决策依据、现有流程或规则样本。
3. **写 2–3 个真实示例**——形态按主型。
4. **列出边界和陷阱**——按主型:安全规则 / 适用范围 / 失败分支 / 反模式。
5. **写 SKILL.md**——按结构模板;每段按主型过"该不该写"测试。
6. **测试**——另一个 agent 实例跑典型任务,观察是否按预期走。

**设计原则:** 能力型库优先于文档;保留生长空间;删比加难(其余见「动态原则」)。

---

## Workflow B: 演化现有 skill

**何时回顾:** 完成 N 次任务(按主型定)| 主型演化信号出现 | agent 反复绕过 | agent 反复踩坑 | SKILL.md 接近 500 行 | 项目大改动。

**动作:**

- 固化高频路径 / 沉淀常见错误 / 拆分膨胀文件 → 见「动态原则」§3–§5。
- agent 反复看某个 references → 把入口提到 SKILL.md。
- agent 绕过某段 → 删掉这段冗余。
- agent 反复问同一个问题 → 在 SKILL.md 加一段说明。
- 子领域独立成型 → 分裂为单独 skill。

**演化原则:** 基于观察不基于预测;加比删容易,大胆删冗余;演化痕迹归 git(提交信息 / ADR),不写进正文;作者定期复盘。

## Audit checklist

逐项检查目标 skill 的 SKILL.md;条件项按主型取用,N/A 不计。

### 内容健康

- [ ] 标了主型(/副型),放在「定位」或「验收」段?
- [ ] 有一句话核心定位?
- [ ] 有精准的「何时用 / 不该用」?
- [ ] 该主型的必写项(API / 示例形态按型)齐全?(见 [references/skill-types.md](references/skill-types.md))
- [ ] 边界(安全规则 / 适用范围 / 失败分支 / 反模式)列出?

### 简洁健康

- [ ] SKILL.md ≤ 500 行?
- [ ] 每段过"删掉它,读者还知道该怎么做吗?"测试?
- [ ] 引用保持一层深度?
- [ ] SKILL.md 不复述 references 内容?

### 抽象健康(能力型必查;其它型按 [references/skill-types.md](references/skill-types.md))

- [ ] 没有伪命令名 / 词表 / DSL?
- [ ] 没有"翻译步骤"?
- [ ] 没有"先组合再调用"的两步流程?
- [ ] 示例都是真实可跑的代码?

### 演化健康(skill 在役时适用;未投入记"待观测")

- [ ] 初始版本克制(只写入口 + 示例 + 边界,不预测未来)?
- [ ] 用该主型的演化信号复看过?
- [ ] 最近一次更新基于实际使用?
- [ ] 没有该拆未拆的部分?
- [ ] 没有 agent 绕过但未删除的冗余?(只能靠观测:复盘加载后的对话,看实际引用了哪几节;同一节连续多次未引用 = 绕过信号。)

**评分:** 按适用项计(N/A 不计入);不通过 ≤1/5 → 健康。>1/5 且 ≤1/3 → 需修订。>1/3 → 需重新设计。

## 验收(teach-back)

- **档位:** teach-back(无确定性产物;验收 = 独立复核)。
- **流程:** 派一个看不到本会话的独立 agent,只给目标 skill 的 `SKILL.md` + 它的 references + 本 skill 的「判型」「Audit checklist」与 `references/skill-types.md`;产出:主型判定 / 类型特有缺口 / 判定(通过 / 不通过 / 需人拍板)。
- **判据:** ① 主型与失败模式一致;② 该主型必写项齐全;③ 审计按适用项计且不通过 ≤1/5;④ 引用一层深度,能力型无可执行伪抽象。
- **留档:** 结论写目标 skill 的 `docs/reviews/` 或提交信息;未复核留痕。
- **边界:** "通过"只说明文档内部一致,不证明断言为真;事实类断言另靠外部核实。
