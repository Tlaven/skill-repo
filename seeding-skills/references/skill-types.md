# Skill 类型:按失败模式分型,按型处理

> 本文件是 `SKILL.md`「判型」节的展开。SKILL.md 只留分诊表;这里放每型的必写 / 不写、验收、演化信号,以及 §2 / §3 / §6 在非能力型上的等价判据。
>
> **类型不是主题标签,是设计约束。** 同一套写法在某一型是硬要求,在另一型可能空转。分型的唯一目的,是决定**哪些规则适用、该拿什么验收**。

## 一、三问判型

1. **没有它,agent 会怎么失败?**
   - 不知道 / 记错 → **知识型**
   - 知道但选错 → **判断型**
   - 知道但漏做 / 乱序 → **流程型**
   - 每次重做 / 执行不稳 → **能力型**
   - 产出物结构漂移 / 无法复核 → **元型**
2. **它的主要交付物是什么?**
   - 一条事实 / 来源 → **知识型**
   - 一次选择 / 否决 → **判断型**
   - 一个带产物的步骤链 → **流程型**
   - 一段可执行能力 → **能力型**
   - 一套让别的 skill / 文档成立的规则 → **元型**
3. **失败能否被机器判定?**
   - 能 → 优先**能力型 / 流程型**(把判定写成可执行检查)
   - 不能 → **判断型 / 知识型 / 元型**(靠独立复核与证据)

> 三问不一致时,以第 1 问为准:skill 存在的理由是**消除一种失败**,不是"包含某种内容"。

## 二、五种类型

### 知识型

- **一句话:** 给 agent 补它没有、或记不准的先验。
- **缺了它:** 不知道 / 记错 / 用通用常识替代领域事实。
- **必写:** 反先验事实;来源与强度;适用范围;失效 / 过期条件;与直觉冲突的点。
- **不写:** 代码能读出来的事实;通用常识;无出处的"最佳实践"。
- **默认验收:** 来源核对 + teach-back(抽样核对来源;事实类断言能试跑先试跑,不能试跑就写清来源或谁拍的板)。
- **演化信号:** 新证据;来源过期;两条规则互相矛盾;在真实任务里被证伪。
- **常见误判:** 把"判断规则"写成知识——只陈述事实,不告诉 agent 该怎么选。
- **例子:** 排版规则、市场数据口径、领域术语。

### 判断型

- **一句话:** 在多个看起来都合理的选项里,把 agent 推向正确的那一个。
- **缺了它:** 模型会自信地选错——不是不知道,而是知道好几种写法,随机挑一个。
- **必写:** 决策卡(红线 + 最常用的几条);反模式("看起来对、语义却错");本地标定(本项目实测 / 拍板);被拒方案与理由;判定标准。
- **不写:** 长篇知识汇编;实现细节;无触发事件的"经验"。
- **默认验收:** 消融(A / B / C)/ 负控 / teach-back;判"决策是否被改变",不是"术语是否出现"。
- **演化信号:** 同一坑反复踩;某条被引用后改变了决策;消融无净增益(→ 降级或冻结)。
- **常见误判:** 把"流程"写成判断(只有步骤、没有取舍);把"候选"当结论。
- **例子:** essentials 的判定规则(副型)、视觉质量脚手架、代码审查判据。

### 流程型

- **一句话:** 让一组必须按顺序发生的动作不漏、不乱、可交接。
- **缺了它:** 跳步、顺序错、产物缺失、交接断裂。
- **必写:** 步骤;每步的入口 / 出口条件;产物与落点;失败分支;退化路径;谁拍板。
- **不写:** 具体实现细节(留给代码);能机器判定的检查(挪进脚本)。
- **默认验收:** 成功路径 + 失败路径 + 产物检查;能给 e2e 就不靠目测。
- **演化信号:** 某步被跳过;返工;交接时缺东西;退化路径从未被使用。
- **常见误判:** 把"检查清单"写成流程(没有顺序与产物);流程里塞满知识。
- **例子:** init-project-docs、video-decode、部署 runbook。

### 能力型

- **一句话:** 把确定性工作从推理里卸载给脚本 / API / 库。
- **缺了它:** agent 每次重写脚本;执行结果不确定;环境差异导致静默失败。
- **必写:** 真实入口与签名;可跑示例;确定性检查;错误语义;依赖与环境;版本约束。
- **不写:** 伪命令名 / 词表 / DSL / 翻译层;实现细节;罗列所有操作。
- **默认验收:** 可执行测试 + 负控 + 干净基线 + 环境矩阵;检查器自身要先能红一次。
- **演化信号:** 同类脚本反复出现;工具版本升级;环境失败;agent 绕过脚本手写。
- **常见误判:** 把库文档抄进 SKILL.md(该给签名和示例);用文字指令代替脚本。
- **例子:** drawio-export、pptx-delivery 的 `qa_check`、thesis-docx 的 `core/`。

### 元型

- **一句话:** 规定"别的 skill / 文档 / 产出物"应该怎么被设计、验证、演化。
- **缺了它:** 产出物结构漂移、判定标准不一致、规则无人执行。
- **必写:** 方法论;模板;判定规则;审计清单;执行面标签(脚本可查 / 需独立复核 / 只能靠自觉)。
- **不写:** 具体项目内容;无法执行的空泛原则;没有审计入口的规则。
- **默认验收:** teach-back / 产出审计;判"别人照着做能否得到一致结果"。
- **演化信号:** 规则空转;被绕过;产出物仍然漂移;不同会话给出不同判定。
- **常见误判:** 把元型写成知识型(只讲道理,没有模板与审计);规则没有执行面。
- **例子:** seeding-skills、init-project-docs 的方法论部分、essentials 的文档规范。

## 三、类型 × 静态原则

§2 / §3 / §6 是**能力型**的默认判据。其它型的等价判据:

| 规则 | 能力型 | 知识型 | 判断型 | 流程型 | 元型 |
|---|---|---|---|---|---|
| §2 不要新抽象 | 不发明伪 API / DSL;中间层必须减少总工作量 | 一个词一个唯一指称物;同物异名 / 一词多义必须合并或定义 | 决策卡只放能改变选择的条目;不复述知识 | 步骤名必须对应真实动作;不发明"先做 X 再做 Y"的仪式 | 规则必须能落到某条审计项;不发明无法执行的术语 |
| §3 代码读得出来的别写 | 只写代码读不出的边界 / 坑 / 契约 | 查得到出处的才能写;查不到进"开放问题" | 只写"会改变决策"的规则;写不出触发事件的不收 | 只写 agent 不会自然做的顺序 / 门禁 / 产物 | 只写"别人照着做会不同"的规则;其余删 |
| §6 示例驱动 | 可跑代码示例 | 带来源的填好样例 | 正例 + 反例(看起来对、语义却错) | 一条完整成功路径 + 一条失败路径 | 一份填好的审计样例 |

> 这张表回答"判据没有指称对象时换成什么",不是新增要求。不要为了填表而写内容。

## 四、类型 × 验收档

仓库已有的档位(smoke / golden / acceptance / teach-back)与类型对齐:

| 类型 | 默认档位 | 说明 |
|---|---|---|
| 能力型 | acceptance(最低 smoke) | 可执行断言 + 负控 + 干净基线;检查器自身先红 |
| 流程型 | golden 档(复杂流程用 acceptance) | 成功路径 + 失败路径 + 产物检查 |
| 判断型 | teach-back(能消融就消融) | 判"决策是否被改变";没有 lift 就冻结 / 归档 |
| 知识型 | teach-back(附来源核对) | 抽样核对来源;断言要能试跑 |
| 元型 | teach-back | 独立 agent 按文档复述 / 执行,看结果是否一致 |

> 档位不是荣誉等级,是**证据强度**:acceptance = 可复跑;teach-back = 独立复核;smoke = 能跑通;未验收 = 没有证据。

## 五、混合型与类型漂移

- **一个主型 + 最多一个副型。** 主型决定验收;副型只影响写法。例:pptx-delivery = 能力型主 + 流程型副;init-project-docs = 元型主 + 流程型副。
- **不要按部件拆型。** 一个 skill 里出现脚本,不自动变成能力型;先问"缺了它,主要失败是什么"。
- **类型可以漂移。** 早期判断型随着脚本固化变成能力型,是正常的;变更史归 git,不写进 SKILL.md。
- **分型失败的信号:** 分不进去;分进去后没有规则差异;同一 skill 有两个主型都说得通(→ 可能该拆成两个 skill)。

## 六、反仪式

- 分型只用于**选适用规则**,不是新的填表义务。
- 如果一个类型不能改变任何一条写法或验收规则,删掉它。
- 如果一个 skill 的主型标了、但审计项没有任何变化,说明分型没落地。
- 被设计 skill 的主型标签不写进它的 description(会占常驻成本);写在 SKILL.md 的「定位」或「验收」段即可。
