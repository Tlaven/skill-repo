# lessons — seeding-skills 的实测对账记录

> 本 skill 自己要求"**基于观察,不基于预测**"(SKILL.md「演化原则」)。这份文件放**观察结果**:
> 从真实 skill 上对账出来的、可能值得改本体的条目。
>
> **证据纪律:** 单一样本(n=1)= **只记账,不改本体**。同一问题被 ≥2 个**独立**样本撞上,才升格为改本体的候选。
> 每条必须写清样本来源,否则无从判断是否独立。
>
> 处置分两栏:**已改**(逻辑缺口,与样本数无关) / **待第二样本**(经验主张,n=1)。

### B 类:样本教给 seeding 的(经验性,n=1 —— **待第二样本**)

**B1 · 「保留演化痕迹:在 SKILL.md 或 references/ 留简短注释(为什么这么设计)」—— 候选:改**

反证来自 `init-project-docs`:它的反模式清单明写「❌ 代码注释写版本变更史」,主张**历史归 git log / ADR**,并把借鉴溯源收进指定的 `## 参考来源` 节。

理由比 seeding 现文更硬:**散在正文里的"为什么"会和正文漂移**——正是它自己 E1「指针优先」要防的东西。

- 若成立,改法:该条改为"**重大决策留痕**——溯源收进指定节;变更史归 git log / ADR,不写进正文"。
- 待验证:第二个样本是否也这样做;有无"必须内联留注释"的反例场景。

**B2 · description 的 `不适用:` 负触发 —— 候选:补进「description 写法」**

`init-project-docs` 的 description 除 TRIGGER 正触发外,还带一段 `不适用:` 负触发(列出明确**不该**加载的场景)。seeding 的「description 写法」只讲了正触发。

- 待验证:第二个样本上有无同类手法;负触发是否真的降低了误触发。

## 未决

- **skill 特有的静默错误缺系统手段。** A3 只补了"绕过"一条的观察方式。skill 的错误分两类:①**用了但用错**(当场可见);②**根本没被读**(永久静默)。第二类目前全无手段——注意现有的"判定一致性"类评估(如 `init-project-docs` 的 `.calibration/`)也只覆盖"用错了没",覆盖不了"读没读"。
- **第二样本要换类型。** 建议取库封装型(`thesis-docx` / `drawio-export`)或另一流程型(`video-decode`);继续审同类不算独立撞上同一问题。
