# Init Project Docs — 项目记忆做法

## 去哪找规则

- 词义:`references/skill-glossary.md`(本 skill 自己的用词;和通用义冲突时以它为准)。
- 三种时间用途 / 四类路由 / 现状写到什么程度算完:`references/temporal-model.md`(先读)。
- 三段式 / L1–L4 / N0–N2 / 硬规则:`templates/methodology.md`(项目里是 `docs-templates/methodology.md`,**不随 L1 自动加载**)。
- 演化规则 E-1–E-7:`references/evolution-rules.md`。
- 多视角复核:`references/review-panel.md`;复核员与预先埋的错:`references/calibration-guide.md`;脚本:`references/tooling.md`;文件落在哪:`references/layout.md`;对话地图:`references/conversation-map.md`;为什么决策记录会被搜到、`.ignore` 怎么放:`references/search-surface.md`。

## 定位

> **前提:人至少给出功能和可验收的行为**(连需求和验收都交给 AI 起草的项目不在范围内——见 Step 1)。

**关键边界:** 不替用户写内容——但允许"从代码 / 作者已有的文档 / git 推断草稿 + 标『推断,待确认』 + 标来源";禁止凭空编造。

**没证据就给方案,不给结论**——只适用于"为什么 / 不变量(阈值、替代指标)/ 方向与计划",不适用于"是什么"这种事实:新领域没有证据时,给 ≥2 个方案、各自标"待你选"并写清代价,由用户选或否;否掉的理由记进决策记录。**方案没被接受前一律留在开放问题里**:接受后写进现状(不变量 / 用词)或决策记录。不能悄悄转正。

## 先定:L1 文件叫什么?

你用的工具(Claude Code / Command Code / OpenCode / Cursor / Windsurf / Copilot…)决定 L1 文件名——对照表在 `templates/l1-memory.md` 顶部。不确定就问用户;判不出别硬默认 `AGENTS.md`。同时用几个工具:选一个主文件,其余只写一行指向主文件。

## 核心理念

**记录不是默认产物**:只在做决定那一刻和过渡期有用;还成立的理由要写回现状正文,其余要有正面证据才移走——不要用摘要或归档给它续命。

## 对话时的三个动作

1. **先把词定清楚**:听到专有名词 / 易混词,追问并定义:跨模块的写进 `docs/glossary.md`,只在一个模块里用的写在该模块;一个词只定义一次。模糊词("优化 / 合理处理 / 相关逻辑")= 没有可判定的指称 → 追问"具体指什么?给我两个互斥解释让我选"。非功能 / 主观词也要落地(可测的替代指标 / 钉住可观测的不变);审美说不出阈值时允许"替代指标 + 备选",但不许原样留形容词。详见 `templates/glossary.md` 与 `references/verifying-nonfunctional.md`。
2. **把逻辑分档**:N0 通用 / N1 项目特有 / **N2 AI 没见过**。N2 要写到"步骤级说明 + 危险实现清单 + 精确例子 + 能跑的验收 + 失败时是什么样";N0 / N1 不必。详见 `references/verifying-n2.md`。
3. **按需复核**:命中 Step 3.5 的信号时,派独立 agent 或跑多视角复核;"不通过"→ 改文档;"要人定"→ 把没定的事交用户。

## 何时使用 / 不适合

**适合:** 新项目 / 立项;要写 `CLAUDE.md` / `AGENTS.md`;已有项目补 L1;已有 L1 但想引入这套做法;项目结构变了要重建;含 N2 核心逻辑要写到能实现。

**不适合:** 已有完整 L1 且用户没说要改(不推销);单次任务 / 一次性脚本;用户只想快速生成代码速查。

## 规则靠什么生效

| 类 | 谁执行 | 本 skill 的做法 |
|---|---|---|
| **脚本能查** | 检查脚本 / pre-commit / CI | 核对脚本 + 新检查器;见 `references/tooling.md` 与 `references/wiring.md` |
| **得另一个人看** | 一个看不到本会话的独立 agent | teach-back + `review-panel.md`(按需、可以攒一批) |
| **只能靠自觉** | 无 | 明确承认保证不了 |

## Workflow

### Step 1: 看环境 + 定模式 + 定文件名

- 有没有 L1? 没有 L1 + **基本空目录**(除 `.git` / skill 模板外,没有作者手写的文件)→ **2A**;没有 L1 + 有任何作者手写的文件(README / 设计文档 / docs,哪怕只有一份)→ **2C 嫁接**;有 L1 + 文档写太多 / 用户说"看不懂 / 干扰 / 想变少" → **2R 精简**;有 L1 + 已经写着这套做法 → **2D 补差**;有 L1 + 想引入这套做法 → **2B 合并**;有 L1 + 用户没说要改 → 不推销。
- 是不是 git?(不是:补差和 SHA 都用不了,退化成人工清单)
- 用哪个工具?→ 由此定 L1 文件名。
- **前提:人至少给出功能和可验收的行为**;人定下的标 `[已定]`,AI 不得"顺手优化"。连功能和验收都由 AI 起草,本 skill 不适用。

### Step 2A: 全新项目——用到哪份建哪份

**默认只建 L1 + `task_plan.md`**;`docs/.live` 等第一份当前维护的文档出现时再建;`docs/` 里当前维护的文档不预建,哪个话题出现了再建。L1 只放项目记忆;这套做法复制到 `docs-templates/methodology.md`(留在那儿直接引用),**不要写进 L1**。

**按话题建文档:** 主流程 / 架构边界要单独讲清 → L2;某个模块的机制要单独讲清 → L3;跨模块的词 → glossary;决策要留档 → ADR;跨模块 N2 的五个东西 → L2 的「N2 单元规格」节;模块内 N2 → 模块 L3。没有这个话题就不建,不铺模板。

1. 复制 `templates/l1-memory.md` → 项目根,名字按 Step 1 定的。
2. 复制 `templates/methodology.md` → `docs-templates/methodology.md`;再按 `references/layout.md` 的落点表复制这次用得到的模板和参考件。
3. 建 `task_plan.md`(放方向和计划);第一份当前维护的文档出现时写 `docs/.live`(一行一个路径,相对 `docs/`)。
4. 然后进 Step 3 对话;`docs/` 里当前维护的文档按需创建(跨模块的词 → `docs/glossary.md`;L2 → `docs/architecture.md`;模块 → `docs/modules/<name>.md`;ADR → `docs/decisions/`(在议的决策;定下来后把理由写回现状再移走),并把 `decisions/` / `reviews/` / `archive/` / `experiment/` 写进 `docs/.ignore`;核对记录 → `docs/reviews/`(按核对周期成批移走);想看核心怎么串起来 → `docs/core-analysis.md`(L4,可选、没人引用))。
5. 把本 skill 的 `scripts/` **整个目录**拷进项目 `<repo>/scripts/`(含共用的 `_doc_common.py`);用户不接脚本,就在 L1 标「scripts: 没拷进来」,后面相关命令按"这次没跑"处理。

### Step 2B: 合并模式——已有 L1

不破坏现有内容,只补目录 + 缺的层:读现有 L1 → **不要把方法论插进 L1**;按项目现有布局把方法论那份参考件放到位(已有 `docs/templates/` 就沿用,否则用 `docs-templates/`),L1 只加一行目录条目 → **不动用户原有内容(唯一例外:把旧 L1 里的方法论正文移到方法论文件)** → 看到散落的不变量,提示归并,但**让用户决定** → `docs/` 按需创建(先问)→ Step 3 从"补缺"开始。

> **合并后核对:** 方法论参考件在位 + L1 只有目录条目;硬规则 / 加载表 / 完成判据 / E-1–E-7 不再常驻 L1。

> **布局跟着项目走:** 已有 `docs/templates/` 就跟随,不强行改成 `docs-templates/`。要统一 → 写决策记录 + 用户定。项目自定义的模板目录必须同步进检查脚本的 `DOC_EXCLUDE` / `DEFAULT_EXCLUDE`。

### Step 2C: 嫁接模式——已有文档、缺 L1

只要存在作者手写的 README / 设计文档 / docs,就不算空目录,走 2C。

1. 通读既有文档,对应到 L1–L4:现状事实 → L2 事实源(新 `architecture.md` 只写决策 + 不变量,不搬既有正文);设计动机 / 不变量 / 验收 → **L1/L2/L3**(按性质选层;L4 只放阅读视图,不收约束);**去哪份由 L1 的目录交代,正文里不嵌"见 …"**;存档 / 旧方案 → 归档区(legacy/archive;不是第 5 层;不迁、不删,标清边界,核对时排除)。
2. 填 L1 时标清"内容从哪来":证据标来源;猜不到 → 开放问题,别硬填。
3. 冲突时只在新文件顶部加一行"以哪份为准",**不动作者原有文件**;定性冲突记开放问题,交作者定。
4. Step 3 从"补既有文档缺的那部分"开始;`architecture.md` 可先当证据草稿(标 `推断,待确认`)。

> 同名冲突:既有事实源已占 `docs/architecture.md` → 新文件另起名(如 `architecture-l2.md`),顶部写明以哪份为准,并同步脚本两张表。

### Step 2D: 补差模式——项目已经按这套做法跑着

不要重造、不要重写 / 升级版本。动作 = 补缺 + 核对(≈ E-5):

1. 先核对:通读 L1 + `docs/.live` + `docs/`,列"这套做法要求 vs 项目现状"的缺口,标哪些要用户定。
2. 只补没有争议的缺口(死链、缺的参考件);不改 L1 已成文的措辞。
3. 布局跟着项目走;不擅自升级版本(那是用户的决定)。
4. 默认不新增当前维护的文档;要新增先列提问清单。
5. 收尾只汇报"补了哪些缺口 / 还差什么没定"。

### Step 2R: 精简模式——文档写太多 / 全是 AI 生成的 / 想变少

**触发:** 当前维护的文档 >10 份 / 文档总量 > 代码量 / 同一件事有几处写法 / 用户说"看不懂 / 一直干扰 / 想变少"。
**门槛:** 作者点头;**作者手写的文档不删,只归档;AI 生成的历史记录可以移出工作区**(git 里还有)。
**先提交现状**(或建分支 / `git stash`),保证能退回去。

1. **清点:** 列 `docs/` + 根文件;每份标 `作者写 / AI 写 / 记录`。作者写的改动要确认;AI 写的历史记录可以直接移出,AI 写的其他文档可以归档。
2. **挑要留的:** 按加载频率挑 3–6 份(每次都要:L1 / `task_plan` / 当前在做的模块手册 / 设计约束;按任务才用:architecture 一页 / 2–3 个模块 / 词表)。写进 `docs/.live`。
3. **归档:** 其余移到 `docs/archive/`(文件名保留日期)或 `docs/experiment/`(脚手架 / 实验日志);不删。AI 生成的历史记录改为移出工作区:定下来的决策记录可单条移走;上一轮的 reviews 等整轮核对做完再成批移走。
4. **改目录:** L1 只列当前维护的文档;历史记录不进当前文档正文,只在 L1 目录里以目录级出现一次;当前维护的文档不拿决策记录 / reviews 当依据;`docs/experiment/scaffolds/` 从 README / 词表 / L1 入口删掉。
5. **去时间 / 版本:** 当前维护的文档里的日期 / 文档版本号删掉或移进归档;只留顶部 `Last verified: <SHA>`;领域版本保留。
6. **数 before / after:** 文件数 / 行数 / 字节 / 日期数 / `check-consistency` 警告;跑项目验收,证明只动了文档。
7. **留个记录:** 一条 review 或 notes 记结论;两周后再数一次,涨 >20% 说明生成器没改完。

### Step 3: 边对话边写入(核心步骤)

**硬性要求:每段对话产出立刻写进对应段落,让用户看到进度。** 不要攒——用户说完一段就写,再问下一段。写进哪一栏看这句话是决策、现状还是方向,别把计划写成事实。

- **第一阶段(填 L1 主轴):** [是什么] → [为什么] → [不变量],每段问 1–2 个核心问题,答完立刻写。
- **第二阶段(填 L2 主流程):** 主流程 / 架构边界要单独成文时,建 `docs/architecture.md`,重点写主流程(10–20 行,从入口到出口)。
- **第三阶段(按需):** 模块出现 N2 或细节往 L2 堆 → 建 L3;要做决定 → **先看这条决定该记在哪**(可逆 / 局部 / 一次性 → commit body;要评审 / 跨模块 → PR-RFC;不可逆 / 长期约束 → 决策记录),确实需要才建(`docs/decisions/` 一个决定一个文件,目录本身就是在议区;**不另写目录**——`ls` 就是列表;定下来后把还成立的理由写进现状,再把记录移走);跨模块 N2 的五个东西必须有家(`docs/architecture.md` 的「N2 单元规格」节,或模块 L3);**五个东西不放 L4**——L4 是可选的阅读视图,不给验收、没人引用,放进去等于没人读得到;N2 单元同时登记 `docs/n2-acceptance.json`(命令 + cwd),供 `run-n2-acceptance --run` 用。
- **[是什么] 还没定**(重新立项 / 方向未定):L1 概述**只写现状**——"方向未定"本身就是一条现状,**别假装定了**;方向进「开放问题」,一条一行,带 状态 / 谁定 / 什么条件下算结案;`[是什么]` 不放任何方向陈述;复核会正确卡在"要人定"。

### Step 3.5: 改代码前的复核(teach-back + 多视角复核)

**该在改代码之前做**:**攒一批做,不要每次跑**。

**什么时候值得做:** ① 单元标了 N2;② 改到了不变量;③ 用词还没有可判定的定义;④ **跨层大改**——内容在层间搬家(某条规格从 L3 挪到 L2,或反过来),或新增 / 删掉一层。四条都不占就跳过;纯 N1 且验收写得出来也跳过。

**四个信号决定"跑不跑";`review-panel.md` 只决定"跑哪几个视角"。**

**攒批:** 拷进 `scripts/` 的,先跑 `review-backlog`(不花 token)列出自上次复核以来改了什么;没拷就人工列,并标"没拷进来 / 这次没跑"。只把改动喂给独立 agent;每个被喂的单元要给整节(定义段 + 验收段必须都在);结论记 `docs/reviews/`,覆盖的提交写进 `docs/reviews/.last-review`(只记看到哪了,不移走)。

**怎么派:**
- 派一个**看不到本会话**的全新 subagent。
- 基础 prompt:`references/teach-back-verifier-prompt.md`;判定范围:L1 / L2 判决策,L3 / N2 判实现(N2 一律判实现);**L4 不判**——它不给验收、没人引用,判它等于用错标准。
- **待验证的文档太大 / 太多时**,按模板的**只读文件清单**派发(只读列出的文件、禁读代码;要跟代码对标的可以加只读代码)。
- 一个待验证单元 = 一份派发参数;可以并行,但每份独立判;第一次跑,"上轮阻断清单"填"无"。
- **派之前自检:** 范围词(子集 / 方言 / 支持哪些 X)要么列清内容要么记开放问题;文档里有要人定的事,先请人定。

**不通过 → 改文档**,不是改 prompt;重跑时附上轮阻断清单。**要人定 → 别绕着改文档**:把要决定的事交用户,定了写回文档再验。N2 必须先补"步骤级 + 危险清单 + 例子 + 验收 + 失败时什么样"再放行实现。

**派不出独立 agent 时:** 不自己评充数,也不卡死:① 把待验证正文 + prompt + 派发参数封存到 `docs/reviews/<日期>-<主题>-package/`,配 `MANIFEST`(文件清单 + 校验值 + git SHA);② 另写一份声明,明写"复核没做";③ 把"跑一次独立复核"列为移交项。等不等复核由你定。

### Step 3.6: 文档写到什么程度算完

**判据 = methodology 里那四条**(复核 / 现状写到什么程度 / N2 验收 / 够不够紧凑)。**"要人定"不是失败,是正常的终点**:可交付 = 骨架完成 + 待定清单 + **做过复核的话**复核结论已留档。**第一轮按 L1 + 已经出现的话题文档交付,就进 Step 4**;那四条是全部做完的标准,不是收尾的前提。

### Step 4: 收尾

**清理一遍(只 2A;2B/2C 不动作者内容):** 找矛盾 → 只留必需的 → 其余分组到按需加载的文件 → **写进目录**(上层列下层,只写"哪份管什么";不写句子级的"见 X") → **标出能删的**(冗余 / 太泛 / 显而易见的全删)。生成 ≠ 完成。

## 反模式(checklist)

- ❌ 新增当前维护的文档却不做净减(新增一份,就要合并 / 替换 / 归档掉一份)
- ❌ 没经作者确认就生成 L4;L4 是可选的阅读视图,建它先问作者(记 commit body 就够——它随时能删,不必占一条决策记录)
- ❌ `[是什么]` 新旧说法并存;`[为什么]` 留着已被推翻的论述(该直接改写或删掉,别标"已推翻")
- ❌ 改代码绕过不变量;代码注释里写版本变更史
- ❌ 做完 / 放弃的计划留在活跃清单(做完的移出;放弃的写成决策记录)
- ❌ 模板加了要求,却没写明谁来检查(脚本 / 独立复核 / 自觉)
- ❌ 给同一目录的决策记录再写一份列表(`ls` 就是名单,多一份就多一处会漂);把已被取代 / 前提消失的记录留在工作区(读文件的人也会读到它)——**不是 git 的项目例外:没有恢复手段,只能标 `expired` 留在原处**

## 验收(teach-back)

- **验收方式:** teach-back(没有确定性产物;验收 = 独立复核)。
- **流程:** 按 `references/teach-back-verifier-prompt.md` 派一个**看不到本会话**的独立 agent,只喂待验证文档 + 派发参数;产出三段:复述 / 缺口清单 / 判定(通过 / 不通过 / 要人定)。
- **多视角复核:** 命中 Step 3.5 的信号时,按 `references/review-panel.md` 的**三种组合**取视角(单视角 = 1 个通用视角;标准 = 按文件对应 2–3 个;全档 = 四个视角,可加通用视角);怎么分档与对应关系以该文件为准。每个视角配一个预先埋好的错;协调的人合并去重;第 2 轮附上轮阻断清单。派发包格式见该文件。
- **留档:** 结论与覆盖的提交写进目标项目 `docs/reviews/YYYY-MM-DD-<主题>.md` + `.last-review`(只记看到哪了,不移走);reviews 按核对周期成批移走。
- **判据:** "通过"或"要人定"就达到可交付;"不通过(文档有问题)"→ 先改文档,重跑时附上轮阻断清单。**"通过"只说明文档内部一致,不证明断言为真。**
- **脚本自检:** `python -m unittest discover -s tests`(skill 这边);新脚本上线前必须有反向测试。仓库级 `scripts/skills-eval.ps1` 走 `eval/run.ps1`(内容就是这套测试)。
- **用词自检:** 改 `SKILL.md` 的常用词 / 新增词后,按 `references/skill-glossary.md` 跑一次「只给 SKILL.md」的无上下文理解测试;出现"猜的"或偏离,说明那句话没用明白话,重写那一句,不要补定义。
- **没跑 ≠ 通过:** 标了"没拷进来 / 这次没跑"的,都不算验过。
