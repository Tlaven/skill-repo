# Init Project Docs — AI 协作时代项目文档初始化

## 阅读坐标(先知道去哪找定义,正文不复述)

本 skill 反复用三套坐标——**文档四层(L1–L4)**、**novelty 分档(N0/N1/N2)**、**演化规则(E1–E7)**——定义分别在 `templates/l1-memory.md` 与 `references/evolution-rules.md`,正文只引用、不复述。另有两组判定用词:**决策级 / 实现级**(teach-back 判"文档够不够用来做决策 / 够不够照着实现")与 **[阻断] / [非阻断]**(验证者输出的缺口级别),定义都在 `references/teach-back-verifier-prompt.md`。

**teach-back** 指:派一个看不到本会话的独立 agent,只给它文档与派发说明,让它复述并找缺口——按需做、可攒批、不阻塞(见 Step 3.5)。

> **L 的所指:** 本 skill 的 **L** 一律指**文档层**(L1 记忆文件 / L2 架构 / L3 模块 / L4 core-code)。

> **两套标签别混:** 执行面（`[脚本可查]` / `[需独立复核]` / `[只能靠自觉]`，规则靠什么生效）与验证方式（`强制` / `约定`，不变量怎么验）是两套轴；两者的完整区分见 `templates/l1-memory.md` 铁律段。

## 定位

项目文档**骨架**的引导者。不是文档内容的作者——内容靠和用户对话涌现。

> **目标工况:人至少给出功能与可验收行为**（连需求与验收都交给 AI 起草的项目不在范围内——边界见 Step 1）。

skill 提供四样东西:

1. **方法论框架**——让 agent 知道有这套思维方式(三段式 × 4 层)
2. **文件结构骨架**——项目应该有哪些文档文件、放哪里
3. **对话地图**——告诉 agent 该问什么,而不是替用户答
4. **可判定的约束**——术语先定义、N2 写到可实现;独立复核是**按需工具**、可攒批(见 Step 3.5)

**关键边界:** 不替用户写内容——但**允许"从代码 / 证据推断草稿 + 标注『推断,待确认』"**,禁止凭空编造。

**证据 vs 编造判据:能在既有作者文档 / git / 代码里查到出处的 = 证据(允许,标来源即可);查不到、只能靠猜的 = 编造(禁止,进"开放问题"清单)。**

**第三类(只适用于 [为什么] / [怎么做],不适用于 [是什么] 事实):候选(待否决)。** 新领域按定义没有证据,一律禁猜等于禁掉了最有用的一步——允许 agent 给**显式标注"候选,待否决"**的规格草案:能列出替代方案时给 ≥2 个并标各自代价,由用户选 / 否;**否决理由直接成为 ADR 素材**。单方案会诱导默认接受,所以候选必须可被拒绝,不能被当成结论追加进文档。**信息不足时可判定化优先于"不替写"**(空洞文档比待确认草稿更糟)。候选**可以**写进 ADR(状态标 `proposed`)——否决理由正是 ADR 的素材;`accepted` 之前,别处只能引用为题,**不能当结论**引用。

**规则正文分两处归属:** 核心方法论(三段式 / 4 层 / novelty / 铁律)在**项目根的记忆文件**(由 `templates/l1-memory.md` 落入项目);**演化期规则 E1–E7** 在 `docs-templates/evolution-rules.md`。本 skill 只讲流程、不重述规则。

## 宿主适配(先定:L1 文件叫什么?)

**宿主**指承载 agent 的应用(Claude Code / OpenCode / Cursor / Windsurf / GitHub Copilot…),它决定 L1 文件叫什么名。**宿主 ↔ L1 文件名的映射,唯一归属在 `templates/l1-memory.md` 顶部那张表**(本 skill 不重述,避免两处漂移)——决定文件名前读那里。

- **不确定就问用户"你用哪个 agent 宿主?"**;检测到 `.claude/` 用 `CLAUDE.md`,其它宿主按 `l1-memory.md` 顶部表落文件名;判不出就问用户(别硬默认 `AGENTS.md`——名字错了宿主不会加载)。
- **多宿主并存:** 选一个当主文件,其余放一行指针(`见 AGENTS.md`)——不要各写一份,**两份规则必然漂移**(细则同见 `l1-memory.md` 顶部)。

## 核心理念

文档是人和 AI 的"共享内存"。写**决策需要的信息**,不写**实现需要的信息**。

- 人类有工程基础、但不一定通晓项目所用语言 → 不靠逐行读代码理解项目,文档是人类对项目的心智模型
- AI 不会自动读全部代码 → 文档是 AI 加载上下文的入口
- 双方必须在同一份信息上对齐 → 文档是唯一共享协议

内容靠对话产生,因为对话本身就是确立文档内容的核心方法。**skill 不能跳过对话**。

## 去模糊与可实现(对话时的三个动作)

文档不只是"索引",更是让 AI 在**没见过的领域**里能正确动手的唯一依据。**规则正文在 L1 记忆文件**;这里只讲**对话时该怎么做**:

1. **术语先定义**:听到领域专有名词 / 易混词,追问并登记 `docs/glossary.md`(一个词只定义一次)。
   - AI 用模糊词(「优化」「合理处理」「相关逻辑」)= 你没给它可判定的指称物。追问:`"具体指什么?给出两个互斥解释让我选。"`
   - **非功能 / 主观词也必须落地**:"要稳定""要快""要好看"→ 先转成可判定写法(钉住哪些输入 → 什么可观测不变;或至少一个可测代理指标),换写法见 `templates/glossary.md` 的"去模糊词表"。**审美类要求拿不到精确阈值时,允许给"可测代理指标 + 候选(待否决)",但不允许原样留着形容词。**
   - 换写法见 `templates/glossary.md` 的"去模糊词表";转换四步与分类对照见 `references/verifying-nonfunctional.md`。
2. **给逻辑分档**:填 novelty(N0 通用 / N1 项目特有 / **N2 AI 未见**)。N2 = 领域特有 / 创新逻辑,**必须**写到"步骤级说明 + 危险实现清单 + 精确例子 + 可跑验收"(怎么造验收见 `references/verifying-n2.md`);N0 / N1 不必。
3. **按需复核(命中 Step 3.5 的信号时值得做)**:派一个**独立 subagent**(看不到本会话)复述并列出缺口;「不通过」→ **改文档**,「需人拍板」→ 把判定为「需人拍板」的那几条未决问题交用户(见 Step 3.5)。

## 何时使用

**适合:**
- 用户开始新项目(空目录或刚 git init)
- 用户说"写 CLAUDE.md / AGENTS.md / 项目初始化 / 立项 / init docs"
- 已有项目但没有 L1 记忆文件,用户想补
- **已有 L1 记忆文件但用户想引入这套方法论**(走合并模式,见 Workflow Step 2B)
- 项目结构变了,需要重建文档骨架
- 项目含 **AI 未见的领域 / 创新核心(N2)**,需把核心逻辑写到"可实现"

**不适合:**
- 已有完整 L1 记忆文件且用户没说要改(应看现有结构,不主动推销)
- 单次任务、一次性脚本(不需要长期文档)
- 用户没明确要求(避免主动推销方法论)
- **用户只想快速给老项目生成一份速查**(命令、目录结构、依赖、代码风格)→ 改用内置 `init` skill。它扫 codebase 自动填**实现信息**;本 skill 专注**决策信息**(为什么、被拒方案、不变量)。两者互补——`init` 写 [是什么] 事实段,本 skill 写 [为什么] + [不变量] 段。

## 执行面:规则靠什么生效

规则只是文字时,LLM 遵守是概率性的。所以每条规则按"靠什么生效"分三类——**能机器判定就机器判定,能交给验证者就交给验证者,剩下的老实认了**:

| 类 | 谁能执行 | 适用 | 本 skill 的做法 |
|---|---|---|---|
| **脚本可查** | 检查器 / pre-commit / CI | 可机器判定的 | `scripts/` 两个检查器(接线见 `references/wiring.md`) |
| **需独立复核** | 一个独立、看不到本会话的 agent | 需要判断的 | Step 3.5 的 teach-back 验证者(**派发靠自觉**——没人替你触发) |
| **只能靠自觉** | 无 | 不可判定的 | 明确承认无法保证 |

L1 铁律每条末尾都带这个标签(`[脚本可查]` / `[需独立复核]` / `[只能靠自觉]`)。

**自带两个检查器 + 一个辅助脚本**(均 `.sh` + `.ps1`)。前两个是**对账**工具——**对账**指把文档与代码 / 现状逐条核对、找出不一致(完整定义见 E5):

1. `scripts/check-docs-sync.sh` —— 只查一件事:`git diff` 里代码变了、但本项目当前维护的文档(`docs/` 除 `docs/reviews/` 对账留档——历史快照不算同步)与 L1 记忆文件都没变 → 提醒。**只查"有没有动过",不判对错**。
2. `scripts/check-doc-refs.sh` —— 结构性对账:`docs/` 里的死链(含大小写错链)、未填占位符、标了 N2 却缺 `**验收**` / 没有「危险实现清单」、模块文档缺「失败语义」、危险实现清单行未填(空/占位符)、现状文档引记录。
3. `scripts/review-backlog.sh` —— **不判定、不拦截**:列出"自上次复核以来**哪些契约文件变了**、哪些不变量 / 开放问题编号增删改（启发式；不见编号时会提示人工扫 diff）"。给**攒批复核**用,零 token。

接线方式(pre-commit / CI / 宿主钩子)与示例见 `references/wiring.md`;skill 不硬绑宿主。

> 别给"约定型"规则硬配检查器——那只会制造噪音,让人开始无视所有提示。

## Workflow

### Step 1: 检查环境 + 决定模式 + 定宿主

- 当前目录是否已有 L1 记忆文件(按 `templates/l1-memory.md` 顶部的宿主表,共 6 种文件名——`AGENTS.md` / `CLAUDE.md` / Cursor / Windsurf / Copilot 对应文件)?
  - **没有 L1**,且**基本空 / 新项目** → 走 **Step 2A 全新模式**
  - **没有 L1,但已有值得保留的文档**(成体系的 README + `docs/` / 设计规格,**或只有一份 README / 设计文档也算**)→ 走 **Step 2C 嫁接模式**
  - **有 L1,且 L1 里已经写着本方法论**(三段式 / 铁律 / E 规则已成文)→ 走 **Step 2D delta 对账**(项目已在用,只补缺口、别重造)
  - **有 L1,但没引入过本方法论 + 用户想引入** → 走 **Step 2B 合并模式**
  - **有 + 用户没说要改** → 不要主动推销,只回应具体问题
- 是否 git 仓库?(非 git:第 3.5 步的 delta / SHA 起点不可用,退化为人工清单)是否基本空目录?
- 用哪个宿主?→ 决定 L1 文件名(见「宿主适配」)
- **目标工况:人至少给出功能与可验收行为** —— 通常再给核心规则 / 不变量,也可能指定接口 / 数据结构 / 失败码。**文档写到多细由 novelty 分档决定**(N2 → 可实现);人指定项标 `[已定]`。
  **若连功能和验收都由 AI 起草,本 skill 不适用**:"AI 自拟的需求"和"AI 自拟的验收"会互相印证,风险性质不同,别硬套。
  > 任何情况下:**人明确指定的接口 / 数据结构 / 失败码 / 命名标 `[已定]`**,AI 不得"顺手优化"——改动要先走 ADR。指定得越多,这条越关键:典型失败不是写错,是 AI 把你定的设计改得"更好"了。

### Step 2A: 全新模式——落 L1 + 整套 `docs-templates/`

**关键:`docs/` 下本项目当前维护的文档不要预先建空骨架**(会被遗忘、最终空着);但 `docs-templates/` 里放的是两类"不是本项目当前维护的文档",属"对账忽略",**应一次性放齐**——否则 L1 正文里指向它们的指针会悬空:**待填件**(复制出去、填完删注释才成为契约)与**就地读件**(留在原地被引用,不复制、不改)。

1. 复制 `templates/l1-memory.md` → 项目根的 L1 文件名。
2. 把**整套** `docs-templates/` 落地(拷进 `docs-templates/`):`templates/module-doc.md`、`templates/adr-template.md`、`templates/glossary.md`、`templates/decisions-readme.md`、`templates/core-code.md`、`references/evolution-rules.md`、`references/verifying-n2.md`、`references/verifying-nonfunctional.md`、`references/teach-back-verifier-prompt.md`。

然后立即进入 Step 3 对话。**`docs/` 下本项目当前维护的文档按需在对应阶段创建:**

- 出现领域名词 / 易混词 → 把待填件 `docs-templates/glossary.md` 复制到 `docs/glossary.md` 再填
- 进入 L2 讨论 → 从 skill 侧取待填件 `templates/architecture.md` → `docs/architecture.md`
- 首次要写模块文档 → 把待填件 `docs-templates/module-doc.md` 复制到 `docs/modules/<name>.md` 再填
- 首次记 ADR → 把待填件 `docs-templates/decisions-readme.md` 复制到 `docs/decisions/README.md` 再填(单条模板也在 `docs-templates/adr-template.md`)
- 首次对账(teach-back / 文档考古)→ 产出写 `docs/reviews/YYYY-MM-DD-<主题>.md`(无需模板)
- 用户明确要 L4 → 把待填件 `docs-templates/core-code.md` 复制到 `docs/core-code.md` 再填

### Step 2B: 合并模式——已有 L1 记忆文件

**核心原则:不破坏现有内容,只补方法论 + 缺失层。**

1. **读现有 L1 文件**,识别已有段落(项目概述、命令、架构、约束等)
2. 把 `templates/l1-memory.md` 的"文档方法论"整段插入合适位置(通常在项目概述之后、架构之前)
3. **不动用户原有内容**——不替换、不重排
4. 检查现有内容里的 [不变量] 信息:很多项目把约束散落在各段,可提示用户归并到 L1 [不变量] 段,但**让用户决定**
5. `docs/` 目录按需创建(先问用户)
6. 进入 Step 3,但**起点是补缺**,不是从零问(用户已有的内容跳过)

> **布局跟随项目:** 项目若已有自己的文档布局(如 `docs/templates/` 而非 `docs-templates/`、自定义 ADR 命名),**跟随它**,不要强改成 skill 的命名——那会造出两套并存目录,正是 E4 警告的。要统一 → 走 ADR + 用户决定。
> **可无确认即建 / 必须问:** 不改变项目现有结构的(整套模板目录——默认 `docs-templates/`,项目已有别的布局就放那儿,见上条;补 L1 声明过却不存在的文件)可直接落地;会改变项目长期结构或承诺的([不变量] 归并、新建 `docs/` 结构、写 ADR)先问用户。

### Step 2C: 嫁接模式——已有文档、缺 L1

**场景:** 项目**已有成体系文档**(README 很全 / `docs/` 下有架构、设计、规格),但**没有 L1 记忆文件**。**不要当成空项目重造一套**——那会和既有文档撞车(见 E4:"两套并存物必须有 ADR 解释区别")。

**核心原则:先映射,再落骨架;既有的"现状事实"文档 = 指针目标,不新造重复层。**

1. **通读既有文档,映射到 4 层:**
   - 既有的**现状事实**文档(架构描述 / 模块清单)→ 它就是 L2 的事实源。**新 `docs/architecture.md` 只放指针 + 决策 + 不变量,不重抄事实**(E1 指针优先)。**2C 下主流程叙述由既有事实源承担,新骨架不重写**(重写 = 两套并存)。
   - 既有的**设计动机 / 不变量 / 验收**文档 → 对应 L1/L2 的 `[为什么]`/`[不变量]` 与 L4;用**指针**指过去,别搬。
   - 既有的**存档 / 旧方案**(如 `docs/legacy/`)→ **考古层**,不是本项目当前维护的文档;不迁、不删,标注边界即可(对账要排除它——见 `scripts/check-doc-refs` 的 `DOC_EXCLUDE`)。
2. **落 L1 + 整套 `docs-templates/`**(同 Step 2A)。
3. **填 L1 时标清"内容从哪来":** 从既有作者文档 / git 提取的 = **证据**(允许,标来源);查不到、只能猜的 → 进"开放问题"清单,别硬填(见「关键边界」)。
4. **消歧:** 冲突时在**新骨架文件**顶部加一行 banner 声明"谁是事实源、谁是必须维护的正式文档",**不要默默并存**;**但只改新文件、不动作者原有文件**——既有文件的定性冲突(如 README 说"当前实现"、重置章程说"考古层")记为开放问题,交作者拍板(同 2B"不动用户原有内容")。
5. 进入 Step 3 对话,但**起点是"补既有文档缺的那部分"**。嫁接模式下 `docs/architecture.md` 可作**证据草稿**先行创建(映射素材已由既有文档提供),不必等 L1 对话共识——但仍是草案,标 `推断,待确认`。

> **同名冲突:** 既有事实源恰好占用新骨架文件名(如已有 `docs/architecture.md`)→ 新骨架**另起名**(如 `docs/architecture-l2.md`),顶部 banner 指明事实源;既有文件不动,冲突记入「开放问题」,新名字同步进脚本的两张表(见 wiring)。
> **若项目方向尚未收敛**(重立项 / "是什么"未定稿):L1 概述可写成**双段**(现状事实 / 方向草案)+ 显式"开放问题"清单,**不要假装收敛**。teach-back 会正确地卡在这里——那不是文档没写好,是信息还没收敛,补它需要人。

### Step 2D: delta 对账模式——项目已在本方法论上运行

**场景:** 已有 L1,且 L1 里**已经写着本方法论**(三段式 / 铁律 / E 规则)。项目**已在用**——常见于"由本 skill 的早期版本初始化过"或"团队手工采用了"。**不要重造,也不要重写/升级版本。**

**动作 = 补 delta + 对账(≈跑一次 E5):**

1. **先对账,别先动手**:通读 L1 + `docs/`,列"方法论要求 vs 项目现状"的缺口(死链、缺的就地读件、规则与执行说明脱节…),每项标**是否需要用户拍板**。
2. **只补无争议缺口**:如 L1 声明了 `docs/templates/<x>.md` 却**该文件不存在**(死链)→ 补上;就地读件(`verifying-n2` / `teach-back-verifier-prompt`)缺失 → 补;**不改 L1 已成文的措辞**。
3. **布局跟随项目**:项目用 `docs/templates/`、就用 `docs/templates/`——**不要**强行改成 skill 的 `docs-templates/`(两套并存 = E4 违例)。要统一旧布局 → ADR + 用户决定。
4. **版本差异不擅自升级**:项目 L1 可能是本方法论的**早期版本**(铁律条数不同、E2 三类 vs 四类、无 scripts)。**保留项目版**;是否升到当前版本 = **用户的决定**(牵动既有文档),不默默替换。
5. **本项目当前维护的文档默认不建**:`docs/core-code.md`、`docs/modules/*`、新 ADR……凡是要新增**本项目当前维护的文档**的,先列进提问清单,别自作主张。
6. 收尾:只汇报"补了哪些缺口 / 还差什么待定"(见 Step 4 的 delta 版收尾)。

### Step 3: 边对话边写入(核心步骤)

**硬性要求:每段对话产出立即写入对应文档段落,让用户看到进度。** 不要囤积——用户说完一段,马上 Edit 写入,再问下一段。

- **第一阶段(填 L1 主轴):** 按 [是什么] → [为什么] → [不变量] 顺序,每段问 1-2 个核心问题,答完立即写入 L1 文件
- **第二阶段(填 L2 主流程):** L1 有共识后**才创建** `docs/architecture.md`,重点产出**主流程叙述**(10-20 行,从入口到出口)
- **第三阶段(按需,不在初建时一次做完):** 某模块出现 N2 逻辑、或其细节开始往 L2 / 大文档里堆时建 L3;决策发生时建 ADR。跨模块的 N2 **必须有家**——建 L4(**先问"建层还是写进 L2";建层记 ADR**),或写进 L2 的 `[不变量]` 架构级约束 + L3 留一行指针(L4 默认不建)。
- **若 [是什么] 尚未收敛**(重立项 / 方向未定):L1 概述写成**双段**(现状 / 方向草案)+ 显式"开放问题",**别假装收敛**;teach-back 会正确卡在这里(需人拍板,不是 agent 能补的)

### Step 3.5: teach-back 复核（按需，可攒批）

**这是工具，不是关卡。** 由**你主动发起**；默认**攒够一批改动再一起做**——逐次跑的 token 与时间成本不划算。没有任何东西会强制它发生。**攒的是派发，不是顺序：推荐在这批改动对应的实现之前完成复核**——落到实现之后，它就从"提前拦截"退化成"事后对账"。

**什么时候值得用（信号，不是义务）：**

1. 单元标记 **N2**（AI 未见）；
2. 改了**不变量**；
3. 某术语**还没有可判定定义**（词条空白 / 有 ≥2 种互相竞争的含义 / 含义刚被修改）；
4. 一次**跨层大改**（横跨 L1–L4 不止一层）。

都不占就跳过；**纯 N1 且验收写得出来**也跳过——它的返工当场可见，不值得花一次复核。

**攒批怎么做才不贵：**

1. 先跑 `scripts/review-backlog`（零 token）：列出"自上次复核以来**哪些契约文件变了**、哪些不变量 / 开放问题编号增删改（启发式；不见编号时会提示人工扫 diff）"；**未拷入 `scripts/` → 从 skill 目录跑 `bash <skill目录>/scripts/review-backlog.sh`；skill 也不在场 → 用 `git diff --stat <起点>..HEAD -- <L1 文件名> docs/` 替代（L1 文件名按宿主，见宿主表）；非 git → 人工列清单**；
2. 只把**变化的那部分**喂给独立 agent，不必重读全量；但**每个被喂的单元要整节**——定义段 + 验收段必须同在（只喂 delta 会把"我自己没给"误判成缺口）；
3. 结论记一条 `docs/reviews/`，并把**复核覆盖到的提交**（通常是开始复核时的 HEAD；脚本跑完会打印现成命令）写进 `docs/reviews/.last-review`（下次 delta 的起点）。

> 不攒批、当场复核也可以——只要那处改动你觉得"猜错会静默扩散"。

**必须派一个全新 subagent 来做——不继承本会话历史,只喂文档 + 派发参数。** 当前会话自己复述 = 自证(误读会一起误读),不算数。用 `references/teach-back-verifier-prompt.md` 的模板。

- **何时跑:** 命中上方四个信号之一时**值得**做。**N0、以及"验收写得出来的纯 N1"跳过**(模型自己能补)。
- **派发参数必填**(防误伤,写法见 verifier prompt):① 待验证单元;② **判定范围**——**N2 单元一律实现级**(无论家在 L3 / core-code / L2 公共节);其余:L1 / L2 用**决策级**(判"能否据此做决策不跑偏"),L3 模块文档与 **L4 单元**用实现级(判"能否只凭文档正确实现");③ 上轮阻断清单(首跑填"无")。
- **派发粒度:一个待验证单元 = 一份派发参数。** 可以一次并行派多个验证者,但**每份判定互相独立**;冷启动整体可打成一包交付,**不因此把多个单元合并成一次判定**(合并会让缺口归属不明、返工时不知道改哪份)。
- **决策级派发前先自检"范围词":** 文档凡用「子集 / 方言 / 自定范围 / 支持哪些 X」这类词框定范围,却**没列内容、没给路径、也没登记「开放问题」** → 验证者必判 [阻断]。派发前先把范围写死,或登记进「开放问题」——否则必卡。(判据见 verifier prompt「判定范围」决策级第 4 条)
- **决策级派发前再自检"开放问题":** 文档若还有**决策级**开放问题(目标 / 范围 / 不变量未定),验证者一律判**需人拍板**(不是通过)。派发前先把这类问题拿去问用户拍板,或明确它只是"非决策级"(不改变做什么 / 怎么做)。(定义见 verifier prompt 判定段)
- 产出:① 独立复述三段式;② "我需要但你没写"的缺口清单(词句类发现必须逐字引用原文);③ 判定 **通过 / 不通过(文档缺陷)/ 需人拍板**。
- **不通过(文档缺陷)→ 改文档**,不是改提示词;重跑时**附上轮阻断清单**——验证者会先**逐条复核**旧项(附证据)、再**全面扫描**(写法见 verifier prompt 的「复核上轮」)。每轮都是新验证者,不带上轮清单 = 每轮全量重掷,达不到收敛。
- **需人拍板 → 别循环改文档**:待拍板项全是"开放问题"里显式声明的未决信息时,答案在用户手里。先把那几条未决问题拿去问用户,拍板结果落回文档再验——**方向不收敛不是措辞问题,反复重写只会原地打转**。
- 冒出的假设 / 歧义 → 当场澄清:登记 `docs/glossary.md` / 补不变量 / 记 open questions。
- 遇 **N2**(新领域核心逻辑)→ **必须**先把"步骤级说明 + 危险实现清单 + 例子 + 验收"补进它的**家**(core-code / L2 公共节 / L3;**若该模块还没有 L3,先照 `docs-templates/module-doc.md` 生成**),再放行实现。

**退化路径(宿主 / 会话派不出"看不到本会话"的独立 agent 时):** 不要自评充数(自评 = 自证,不算数),也不要卡死。① 把待验证正文 + 验证者 prompt + 派发参数**封存**到 `docs/reviews/<日期>-<主题>-package/`,配一份 `MANIFEST`(最小字段:文件清单 + 每个文件的**同步校验值**(行数或摘要) + 生成时的 git SHA;对当前文档算出同值 = 未过期);**不要抄进同一份文件**——同一文本两处必然漂移,违反 E1;② 另写一份指针记录(如 `docs/reviews/<日期>-<主题>-未复核.md`),声明范围与"**复核未执行**"(明示它,这次跳过就是可见的);③ 把"跑一次独立验证"作为移交项交给宿主 / 人。**是否等复核由你定**(同 Step 3.5)——要等,就把它当冻结标记;不等,照常实现。

结论是「不通过」→ 先改文档;「需人拍板」→ 把判定为「需人拍板」的那几条未决问题交人。**它不阻塞实现**——是否等它由你定;但推荐在对应实现前做完(那才是它值钱的位置)。

### Step 3.6: 文档完成判据(什么时候停)

三条**同时**满足即停,不再往文档里加内容:

1. **如果你做过复核** → 它判「通过」(「通过」只说明文档内部前后一致、别人能照着做——事实断言另靠外部核实（试跑 / 来源）;判「需人拍板」也停笔——把判定为「需人拍板」的那几条未决问题交用户);**没做就跳过这条**(复核不强制,别为了凑这一条去跑);
2. **危险实现清单**里每一项,都被某条不变量或某条 `**验收**` 挡住;
3. 每条 N2 都有可跑验收(命令 或 property 断言)。

> 缺任一条 = 还没写完;**三条齐了还想再加,多半是在把实现细节抄进决策层**。"还能再写点"不是继续写的理由。

**「需人拍板」不是失败,是正常终点。** 全新领域在收敛前必然带决策级开放问题——那说明**需要人拍板**,不是文档没写好。此时的可交付态是:**骨架完成 + 拍板清单 + 复核判定(需人拍板)已留档**(而不是"永不收敛、什么都交不出")。先把清单拿去问人,拍板结果落回文档再验。

**退化路径的停笔判据(派不出独立验证者 / 没有用户可问时):** 上面第 1 条**不适用**,改判为三条同时满足:① 投递包就绪(待验证正文 + prompt + 派发参数已封存 + `MANIFEST` 已标同步状态);② "复核未执行"已显式标注;③ 拍板清单已列出。这三条 = **骨架交付态**;实现要不要等复核,由你定(同 Step 3.5——它不阻塞)。

> **快照失效:** 若 `MANIFEST` 记的摘要与当前文档不符 → **快照已过期**,必须重新封存;过期的快照**不得再被当作当前文档引用**(否则它就是 E1 警告的又一份"该删没删的旧陈述")。

**初始化期(技术栈还没定)的验收怎么写:** 允许命令形态待定——写成"与语言无关的 property 断言 / approved fixture + `形如 <runner> tests/...`",但必须满足:① 断言内容写实(不能只有一个名字或一句"要有测试");② 把它登记进「开放问题」。**命令待定 ≠ 验收可以欠着**;技术栈一拍板,立刻把命令补成可跑的。

### Step 4: 收尾说明

初轮对话(L1 + L2 主流程)完成后,告诉用户后续机制:

```
文档方法论已落地。接下来:
- 开发新模块前,从 docs-templates/ 复制 module-doc.md 到 docs/modules/<name>.md,先填(标 novelty 档)后写代码
- 决策发生时(按 E4 的"惊讶度"判据,不是规模),在 docs/decisions/ 记一条 ADR
- 大改动前,先更新对应层文档,再写代码
- L4 默认不要(`docs/core-code.md`)——只有核心单元**被 ≥2 个工作场景共同加载**时才补,建层先问用户并记 ADR(没补时,跨模块契约写进 L2 的架构级约束 + L3 留一行指针)
- 填好任一文档后,删掉其中的引导注释(`<!-- … -->`)——模板注释里的 `与用户对话后填` / `novelty=N?` 这类字样会被 `check-doc-refs` 报为"未填"(它只扫 `docs/`;L1 在项目根,不在扫描面)
- 出现新领域名词 → 登记 docs/glossary.md;N2 逻辑 → 补"步骤级 + 危险实现清单 + 例子 + 验收"
- 复核按需做、可攒批(先跑 scripts/review-backlog,`.sh` / `.ps1` 均有,只把 delta 喂给独立 agent):命中 N2 / 不变量 / 术语歧义或未定义 / 跨层大改 任一条时值得做,**推荐在对应实现前完成**(**纯 N1 与 N0 跳过**;独立 subagent,见 docs-templates/teach-back-verifier-prompt.md)。**"通过"只说明文档内部一致,不代表断言为真**
- 契约里的断言:能试跑先试跑(跑得出反例别写进去);不能试跑的写出来源 / 裁量依据——**声称不是证据**(见 docs-templates/verifying-n2.md 的"契约断言通则")
- L1 超 ~250 行 → 做一次拆分对账(常驻必要性:方法论 / 铁律 / **加载表** / 不变量留;被拒方案 / 领域详情按 E1 外置 **到 `docs/` 内**);复盘(E5)时顺手:调研 / 踩坑 / 复核发现了名单之外的错法 → **易错领域名单**(见 L1 novelty 分档段)追加一行 + 来源
- (可选)把 scripts/ 拷进项目,按 references/wiring.md(skill 侧文档)接到 pre-commit / CI——挡"改代码忘文档"、查死链 / 占位符 / N2 缺 `**验收**` / N2 缺危险实现清单 / 模块缺失败语义 / 危险实现清单行未填 / 现状文档引记录;**"已验证 / 全绿"这类声称建议接自动执行,不接就标"未接 / 未复跑"**(Windows:先按 wiring.md 加一行 `.gitattributes`——CRLF 在 Linux / CI 上会让 `.sh` 直接语法错)

本文件已含方法论精要,后续 agent 启动会自动加载,不需要再调用这个 skill。
```

> **2B / 2C / 2D 不适用上面这套"全新项目"话术**——按各自起点只汇报"补了哪些缺口 / 还差什么待定"。

## 对话地图(L1 三段式的问题清单)

给 agent 的对话地图,**不是问卷**——根据用户回答自然展开,不要机械地一条条问。

### [是什么] 段——问项目定位

- 这个项目要解决什么问题?(一句话能说清吗)
- 谁会用?用在什么场景?
- **不做什么**(明确边界同样重要,边界外写出来)
- 主要功能 / 模块的大致预想?

### [是什么] 段——问术语(填 `docs/glossary.md`)

- 有没有**外人听不懂**的词?(行业黑话、自定义概念)
- 哪些词**最容易混**?(记下来当反例)
- 有没有**旧叫法**已废弃?(记下来当"禁用别名")
- 生成代码时必须知道**类型 / 结构**的词有哪些?

### [为什么] 段——问设计哲学

- 为什么用这个技术栈 / 架构风格?(强约束还是偏好)
- 核心价值观 / 设计哲学,2-3 条?(例:统一模型优先于扩展、性能优先于优雅)
- 考虑过哪些替代方案?为什么拒绝?(被拒方案要记下"为什么不")

### [不变量] 段——问硬约束

- 性能预算?(响应时间、吞吐、内存上限)
- 技术栈锁定?(必须用 / 必须不用什么)
- 可维护性底线?(测试覆盖、文档要求)
- 安全 / 合规约束?
- **最怕写成什么样?** 让对方列 3 种"看起来对、语义却错"的实现(例:重试没做幂等 / 时间按本地时区算 / 权限只查角色不查资源归属)——这就是**危险实现清单**,每条后面必须跟一句"由哪条不变量 / 验收挡住"
- **失败路径分别怎么表现?**(超时 / 部分成功 / 冲突并发 / 越权)——落到 `docs/modules/<name>.md` 的失败语义表,**别接受"合理处理错误"**

## 反模式(checklist)

> 涉及 E1–E7 的详细判据见 `references/evolution-rules.md`(项目内:`docs-templates/evolution-rules.md`);此处只列**症状**。

skill 自身要避免的:

- ❌ **凭空编造 L1 内容**(目标、设计哲学优先对话产生;但"从代码 / 既有作者文档 / git 等**证据推断草稿 + 标注『推断,待确认』 + 标来源**"是允许的,不算编造——**判据:有出处=证据,只能靠猜=编造**)
- ❌ **跳过对话直接生成"看起来完整"的文档**(空洞内容比空骨架更糟)
- ❌ **一次性把 `docs/` 下本项目当前维护的文档都建成空骨架**(会被遗忘);但 `docs-templates/` 属"对账忽略"、**应一次放齐**(否则 L1 指针悬空)
- ❌ **在已有 L1 文件的项目静默覆盖**(走 Step 2B,只补方法论段)
- ❌ **一次问完所有问题**(应分阶段,边讨论边记录)
- ❌ **囤积对话产出**(说一段就立即写入)
- ❌ **主动生成 L4**(默认不要;即便命中收录标准,也先问"建层,还是写进 L2 的架构级约束")
- ❌ **把 skill 硬套到已有完善文档的项目**(应区分:无 L1 → 走 Step 2C 嫁接;已有 L1 且没诉求 → 不推销)
- ❌ **[是什么] 新旧陈述并存**([为什么] 被推翻要标 `⚠️ 已被推翻,见 ADR-YYY`)
- ❌ **改代码绕过不变量**(违反却不修订文档 = 不变量失效的开端)
- ❌ **代码注释写版本变更史**(历史归 ADR / git log)
- ❌ **方向性陈述混进事实段裸留**(意向不会变假,只会悬置)
- ❌ **完成 / 放弃的计划留在活跃清单**(done 移出;**带理由的** dropped 升格为"不做 X"的 ADR)
- ❌ **领域名词不定义就直接用**(AI 会拿训练数据里的通用含义去猜,新领域必错)——先登记术语表
- ❌ **N2 核心逻辑只写职责、不给步骤 / 危险实现清单 / 例子 / 验收**
- ❌ **把复核当关卡或当仪式**(它按需、可攒批;硬性拦截、或每次改动都跑,都会让人绕过——见 Step 3.5 的信号)
- ❌ **接受模糊词**("优化 / 合理处理"当需求)——换可判定写法
- ❌ **多宿主各写一份规则**(两份必然漂移——主文件 + 指针)
- ❌ **AI "顺手优化"掉人指定的接口 / 数据结构 / 失败码**(`[已定]` 就是挡这个的)
- ❌ **N2 没有危险实现清单**(只写"要做什么",不写"最容易被写成什么"——后者才是模型的真实失败模式)
- ❌ **失败语义只写"错误处理约定"**(不逐条给:可重试?幂等?对外表现?怎么观测?)
- ❌ **把"候选,待否决"当结论写进文档**(候选必须由用户选 / 否;否决理由进 ADR,不能静默转正)
- ❌ **模板加了要求、却没写明由谁来检查它**——每条模板要求都要说清:检查器能查 / 需独立复核 / 只能靠自觉(其中"检查器能查"的部分由两个对账脚本承担——它们只认字面、不判语义);没写清的要求,漂了也没人发现

## 验收（teach-back）

- **档位:** teach-back（无确定性产物；验收 = 独立复核）
- **流程:** 按 `references/teach-back-verifier-prompt.md` 派一个**看不到本会话**的独立 agent，只喂待验证文档 + 派发参数；产出三段：复述 / 缺口清单 / 判定（通过 / 不通过 / 需人拍板）。
- **留档:** 结论与覆盖的提交写入目标项目的 `docs/reviews/YYYY-MM-DD-<主题>.md`。
- **判据:** 判定为「通过」或「需人拍板」即达可交付态；「不通过（文档缺陷）」→ 先改文档，重跑时附上轮阻断清单。
