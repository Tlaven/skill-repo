# Init Project Docs — AI 协作时代项目文档初始化

## 元术语速查(先解码,再读正文)

| 术语 | 一句话定义 | 正文归属 |
|---|---|---|
| 三段式 | 每层文档内部结构:[是什么](事实) / [为什么](决策+被拒方案) / [不变量](约束) | `templates/l1-memory.md` |
| L1–L4 | **L**=层(Layer);粒度四层(**按"加载图"切:** 某单元被 ≥2 个工作场景当前置读,才值得单独一层):L1 项目根记忆文件 → L2 架构 → L3 模块 → L4 核心代码(默认不写) | 同上 |
| N0 / N1 / N2 | **N**=novelty;分档:通用模式 / 项目特有 / **AI 未见**——N2 必须写到"可实现" | 同上 |
| teach-back | 派看不到本会话的独立 subagent,只喂文档,复述+找缺口;过关才实现 | `references/teach-back-verifier-prompt.md` |
| 决策级 / 实现级 | teach-back 判定范围两档:L1/L2 判"能否据此做决策";L3/N2 判"能否只凭文档实现" | 同上 |
| [阻断] / [非阻断] | 验证者缺口分级:阻断 = 会分叉 / 写不出验收;非阻断 = 惯例可定 | 同上 |
| [机器] / [验证者] / [约定] | 铁律执行面标签:检查器可判 / 需独立 agent / 只能靠自觉 | `templates/l1-memory.md` 铁律段 |
| A1–A5 | **A**=authority;授权档:人定到哪一层(问题 / 可验收行为 / 不变量 / 接口与失败处理 / 语句写法)。与文档层 L1–L4 **无关**,别混 | `templates/l1-memory.md`「协作档位」 |
| E1–E7 | **E**=演化(Evolution);演化期规则 E1 陈述退役 / E2 方向与状态 / E3 约束三选一 / E4 ADR 触发粒度 / E5 对账 / E6 注释分工 / E7 术语登记(开头另有「陈述四性质」总表) | `references/evolution-rules.md` |

> 速查行若与"正文归属"列的文件冲突,以正文为准——速查是导航,不是第二定义(E7);发现冲突就改这行。

> **术语冲突(别混):** 本 skill 的 **L** 一律指**文档层**(L1 记忆文件 / L2 架构 / L3 模块 / L4 core-code)。与用户讨论"给 AI 多少自主权"时(说明问题 / 指定可验收行为 / 指定不变量 / 指定接口与失败处理 / 指定语句)用 **A1–A5**,不要也叫 L——两套都叫 L4 必然对话歧义。

> **三套标签别互相污染:** `[机器]` / `[验证者]` / `[约定]` = **执行面**(这条规则靠什么生效);`强制` / `约定` = **验证方式**(这条不变量怎么验);`决策级` / `实现级` = **验证范围**(teach-back 判到哪一层)。注意"约定"一词在两套里含义不同(执行面=只能靠自觉;验证方式=仅文档标注、无检查手段),不要互推。

## 定位

项目文档**骨架**的引导者。不是文档内容的作者——内容靠和用户对话涌现。

skill 提供四样东西:

1. **方法论框架**——让 agent 知道有这套思维方式(三段式 × 4 层)
2. **文件结构骨架**——项目应该有哪些文档文件、放哪里
3. **对话地图**——告诉 agent 该问什么,而不是替用户答
4. **可判定化护栏**——术语先定义、N2 写到可实现、进实现前 teach-back

**关键边界:** 不替用户写内容——但**允许"从代码 / 证据推断草稿 + 标注『推断,待确认』"**,禁止凭空编造。

**证据 vs 编造判据:能在既有作者文档 / git / 代码里查到出处的 = 证据(允许,标来源即可);查不到、只能靠猜的 = 编造(禁止,进"开放问题"清单)。**

**第三类(只适用于 [为什么] / [怎么做],不适用于 [是什么] 事实):候选(待否决)。** 新领域按定义没有证据,一律禁猜等于禁掉了最有用的一步——允许 agent 给**显式标注"候选,待否决"**的规格草案:能列出替代方案时给 ≥2 个并标各自代价,由用户选 / 否;**否决理由直接成为 ADR 素材**。单方案会诱导默认接受,所以候选必须可被拒绝,不能被当成结论追加进文档。**信息不足时可判定化优先于"不替写"**(空洞文档比待确认草稿更糟)。候选**可以**写进 ADR(状态标 `proposed`)——否决理由正是 ADR 的素材;`accepted` 之前,别处只能引用为题,**不能当结论**引用。

**规则正文分两处归属:** 核心方法论(三段式 / 4 层 / novelty / 铁律)在**项目根的记忆文件**(由 `templates/l1-memory.md` 落入项目);**演化期规则 E1–E7** 在 `docs-templates/evolution-rules.md`。本 skill 只讲流程、不重述规则。

## 宿主适配(先定:L1 文件叫什么?)

**宿主**指承载 agent 的应用(Claude Code / OpenCode / Cursor / Windsurf / GitHub Copilot…),它决定 L1 文件叫什么名。**宿主 ↔ L1 文件名的映射,唯一归属在 `templates/l1-memory.md` 顶部那张表**(本 skill 不重述,避免两处漂移)——决定文件名前读那里。

- **不确定就问用户"你用哪个 agent 宿主?"**;检测到 `.claude/` 用 `CLAUDE.md`,否则默认 `AGENTS.md`。
- **多宿主并存:** 选一个当主文件,其余放一行指针(`见 AGENTS.md`)——不要各写一份,**两份规则必然漂移**(细则同见 `l1-memory.md` 顶部)。

## 核心理念

文档是人和 AI 的"共享内存"。写**决策需要的信息**,不写**实现需要的信息**。

- 人类有工程基础、但不一定通晓项目所用语言 → 不靠逐行读代码理解项目,文档是人类对项目的心智模型
- AI 不会自动读全部代码 → 文档是 AI 加载上下文的入口
- 双方必须在同一份信息上对齐 → 文档是唯一共享协议

内容靠对话产生,因为对话本身就是确立文档内容的核心方法。**skill 不能跳过对话**。

## 去模糊与可实现(对话时的三个动作)

文档不只是"索引",更是让 AI 在**没见过的领域**里能正确动手的唯一依据。**规则正文在 L1 记忆文件**;这里只讲**对话时该怎么做**:

1. **术语先定义**:听到领域专有名词 / 易混词,追问并登记 `docs/glossary.md`(一个词只定义一次)。
   - AI 用模糊词(「优化」「合理处理」「相关逻辑」)= 你没给它可判定的指称物。追问:`"具体指什么?给出两个互斥解释让我选。"`
   - **非功能 / 主观词也必须落地**:"要稳定""要快""要好看"→ 先转成可判定写法(钉住哪些输入 → 什么可观测不变;或至少一个可测代理指标),换写法见 `templates/glossary.md` 的"去模糊词表"。**审美类要求拿不到精确阈值时,允许给"可测代理指标 + 候选(待否决)",但不允许原样留着形容词。**
   - 换写法见 `templates/glossary.md` 的"去模糊词表";转换四步与分类对照见 `references/verifying-nonfunctional.md`。
2. **给逻辑分档**:填 novelty(N0 通用 / N1 项目特有 / **N2 AI 未见**)。N2 = 领域特有 / 创新逻辑,**必须**写到"步骤级说明 + 精确例子 + 可跑验收"(怎么造验收见 `references/verifying-n2.md`);N0 / N1 不必。
3. **进实现前 teach-back(命中 Step 3.5 触发条件时)**:派一个**独立 subagent**(看不到本会话)复述并列出缺口,不过关就**改文档或把未决项交用户拍板**(见 Step 3.5)。

## 何时使用

**适合:**
- 用户开始新项目(空目录或刚 git init)
- 用户说"写 CLAUDE.md / AGENTS.md / 项目初始化 / 立项 / init docs"
- 已有项目但没有 L1 记忆文件,用户想补
- **已有 L1 记忆文件但用户想引入这套方法论**(走合并模式,见 Workflow Step 2B)
- 项目结构变了,需要重建文档骨架
- 项目含 **AI 未见的领域 / 创新核心(N2)**,需把核心逻辑写到"可实现"

**不适合:**
- 已有完整 L1 记忆文件且用户没说要改(应看现有结构,不主动推销)
- 单次任务、一次性脚本(不需要长期文档)
- 用户没明确要求(避免主动推销方法论)
- **用户只想快速给老项目生成一份速查**(命令、目录结构、依赖、代码风格)→ 改用内置 `init` skill。它扫 codebase 自动填**实现信息**;本 skill 专注**决策信息**(为什么、被拒方案、不变量)。两者互补——`init` 写 [是什么] 事实段,本 skill 写 [为什么] + [不变量] 段。

## 执行面:规则靠什么生效

规则只是文字时,LLM 遵守是概率性的。所以每条规则按"靠什么生效"分三层——**能机器判定就机器判定,能交给验证者就交给验证者,剩下的老实认了**:

| 层 | 谁能执行 | 适用 | 本 skill 的做法 |
|---|---|---|---|
| **机器** | 检查器 / pre-commit / CI | 可机器判定的 | `scripts/` 两个检查器(接线见 `references/wiring.md`) |
| **验证者** | 一个独立、看不到本会话的 agent | 需要判断的 | Step 3.5 的 teach-back 验证者 |
| **约定** | 无——只能靠自觉 | 不可判定的 | 明确承认无法保证 |

L1 铁律每条末尾都带这个标签(`[机器]` / `[验证者]` / `[约定]`)。

**自带两个检查器**(均 `.sh` + `.ps1`);两者都是**对账**工具——**对账**指把文档与代码 / 现状逐条核对、找出不一致(完整定义见 E5):

1. `scripts/check-docs-sync.sh` —— 只查一件事:`git diff` 里代码变了、但本项目当前维护的文档(`docs/` 除 `docs/reviews/` 对账留档——历史快照不算同步)与 L1 记忆文件都没变 → 提醒。**只查"有没有动过",不判对错**。
2. `scripts/check-doc-refs.sh` —— 结构性对账:`docs/` 里的死链(含大小写错链)、未填占位符、标了 N2 却缺 `**验收**`、活文档引记录。

接线方式(pre-commit / CI / 宿主钩子)与示例见 `references/wiring.md`;skill 不硬绑宿主。

> 别给"约定型"规则硬配检查器——那只会制造噪音,让人开始无视所有提示。

## Workflow

### Step 1: 检查环境 + 决定模式 + 定宿主

- 当前目录是否已有 L1 记忆文件(`CLAUDE.md` / `AGENTS.md`)?
  - **没有 L1**,且**基本空 / 新项目** → 走 **Step 2A 全新模式**
  - **没有 L1,但已有值得保留的文档**(成体系的 README + `docs/` / 设计规格,**或只有一份 README / 设计文档也算**)→ 走 **Step 2C 嫁接模式**
  - **有 L1,且 L1 里已经写着本方法论**(三段式 / 铁律 / E 规则已成文)→ 走 **Step 2D delta 对账**(项目已在用,只补缺口、别重造)
  - **有 L1,但没引入过本方法论 + 用户想引入** → 走 **Step 2B 合并模式**
  - **有 + 用户没说要改** → 不要主动推销,只回应具体问题
- 是否 git 仓库?是否基本空目录?
- 用哪个宿主?→ 决定 L1 文件名(见「宿主适配」)
- **这个项目按哪一档授权开工?(A1–A5)** —— 它决定**文档要写到多细**,不决定闸门频率。问法:"这个项目里,你希望自己定到哪一层?只给问题和场景(A1)/ 给功能与验收(A2)/ 给功能与不变量(A3)/ 连接口、数据结构和失败处理也要由你定(A4)。"

  | 档 | 人定到哪 | 文档的落点 |
  |---|---|---|
  | A1 | 问题 / 场景 | **功能与验收也由 AI 提议**:一律标 `候选(待否决)`,由人挑选 / 否决;不变量由 AI 起草,**必须过 teach-back + 人拍板**;L2 可薄 |
  | A2 | 功能 + 可验收行为 | 重点在「是什么 + 不变量」;**验收必须写死**(人给的行为就是验收);L2 可薄;L3 只在出 N2 时建 |
  | A3(默认) | 功能 + 不变量 | 标准骨架:L1 + L2,L3 按需;N2 写到可实现 |
  | A4–A5 | 接口 / 数据结构 / 模块划分 / 失败处理 / 语句写法 | 以上全要,且**人指定的接口 / 数据结构 / 失败码必须标 `[已定]`**,AI 不得"顺手优化";L3 必填,危险实现清单必填 |

  > A1 下最大的风险不是"AI 做不出来",而是**它把候选当结论用**——所以 A1 的产物必须件件带 `候选(待否决)` 且由人过一遍。
  > A4–A5 的典型失败不是写错,是**AI 把你定的设计改得"更好"了**。`[已定]` 就是挡这个的。
  > 档位可按 diff 调整;这里定的是**默认档**,写进 L1「协作档位」。

### Step 2A: 全新模式——落 L1 + 整套 `docs-templates/`

**关键:`docs/` 下本项目当前维护的文档不要预先建空骨架**(会被遗忘、最终空着);但 `docs-templates/` 是"运行期手册 + 待复制 stub",属"对账忽略",**应一次性放齐**——否则 L1 正文里指向它们的指针会悬空。

1. 复制 `templates/l1-memory.md` → 项目根的 L1 文件名。
2. 把**整套** `docs-templates/` 落地(拷进 `docs-templates/`):`templates/module-doc.md`、`templates/adr-template.md`、`references/evolution-rules.md`、`references/verifying-n2.md`、`references/verifying-nonfunctional.md`、`references/teach-back-verifier-prompt.md`。

然后立即进入 Step 3 对话。**`docs/` 下本项目当前维护的文档按需在对应阶段创建:**

- 出现领域名词 / 易混词 → 复制 `templates/glossary.md` → `docs/glossary.md`
- 进入 L2 讨论 → 复制 `templates/architecture.md` → `docs/architecture.md`
- 首次要写模块文档 → 从已在 `docs-templates/module-doc.md` 的 stub 生成 `docs/modules/<name>.md`
- 首次记 ADR → 复制 `templates/decisions-readme.md` → `docs/decisions/README.md`(单条模板已在 `docs-templates/adr-template.md`)
- 首次对账(teach-back / 文档考古)→ 产出写 `docs/reviews/YYYY-MM-DD-<主题>.md`(无需模板)
- 用户明确要 L4 → 复制 `templates/core-code.md` → `docs/core-code.md`

### Step 2B: 合并模式——已有 L1 记忆文件

**核心原则:不破坏现有内容,只补方法论 + 缺失层。**

1. **读现有 L1 文件**,识别已有段落(项目概述、命令、架构、约束等)
2. 把 `templates/l1-memory.md` 的"文档方法论"整段插入合适位置(通常在项目概述之后、架构之前)
3. **不动用户原有内容**——不替换、不重排
4. 检查现有内容里的 [不变量] 信息:很多项目把约束散落在各段,可提示用户归并到 L1 [不变量] 段,但**让用户决定**
5. `docs/` 目录按需创建(先问用户)
6. 进入 Step 3,但**起点是补缺**,不是从零问(用户已有的内容跳过)

> **布局跟随项目:** 项目若已有自己的文档布局(如 `docs/templates/` 而非 `docs-templates/`、自定义 ADR 命名),**跟随它**,不要强改成 skill 的命名——那会造出两套并存目录,正是 E4 警告的。要统一 → 走 ADR + 用户决定。
> **可无确认即建 / 必须问:** 不改变项目现有结构的(整套模板目录——默认 `docs-templates/`,项目已有别的布局就放那儿,见上条;补 L1 声明过却不存在的文件)可直接落地;会改变项目长期结构或承诺的([不变量] 归并、新建 `docs/` 结构、写 ADR)先问用户。

### Step 2C: 嫁接模式——已有文档、缺 L1

**场景:** 项目**已有成体系文档**(README 很全 / `docs/` 下有架构、设计、规格),但**没有 L1 记忆文件**。**不要当成空项目重造一套**——那会和既有文档撞车(见 E4:"两套并存物必须有 ADR 解释区别")。

**核心原则:先映射,再落骨架;既有的"现状事实"文档 = 指针目标,不新造重复层。**

1. **通读既有文档,映射到 4 层:**
   - 既有的**现状事实**文档(架构描述 / 模块清单)→ 它就是 L2 的事实源。**新 `docs/architecture.md` 只放指针 + 决策 + 不变量,不重抄事实**(E1 指针优先)。
   - 既有的**设计动机 / 不变量 / 验收**文档 → 对应 L1/L2 的 `[为什么]`/`[不变量]` 与 L4;用**指针**指过去,别搬。
   - 既有的**存档 / 旧方案**(如 `docs/legacy/`)→ **考古层**,不是本项目当前维护的文档;不迁、不删,标注边界即可(对账要排除它——见 `scripts/check-doc-refs` 的 `DOC_EXCLUDE`)。
2. **落 L1 + 整套 `docs-templates/`**(同 Step 2A)。
3. **填 L1 时标清"内容从哪来":** 从既有作者文档 / git 提取的 = **证据**(允许,标来源);查不到、只能猜的 → 进"开放问题"清单,别硬填(见「关键边界」)。
4. **消歧:** 冲突时在**新骨架文件**顶部加一行 banner 声明"谁是事实源、谁是必须维护的正式文档",**不要默默并存**;**但只改新文件、不动作者原有文件**——既有文件的定性冲突(如 README 说"当前实现"、重置章程说"考古层")记为开放问题,交作者拍板(同 2B"不动用户原有内容")。
5. 进入 Step 3 对话,但**起点是"补既有文档缺的那部分"**。嫁接模式下 `docs/architecture.md` 可作**证据草稿**先行创建(映射素材已由既有文档提供),不必等 L1 对话共识——但仍是草案,标 `推断,待确认`。

> **若项目方向尚未收敛**(重立项 / "是什么"未定稿):L1 概述可写成**双段**(现状事实 / 方向草案)+ 显式"开放问题"清单,**不要假装收敛**。teach-back 会正确地卡在这里——那不是文档没写好,是信息还没收敛,补它需要人。

### Step 2D: delta 对账模式——项目已在本方法论上运行

**场景:** 已有 L1,且 L1 里**已经写着本方法论**(三段式 / 铁律 / E 规则)。项目**已在用**——常见于"由本 skill 的早期版本初始化过"或"团队手工采用了"。**不要重造,也不要重写/升级版本。**

**动作 = 补 delta + 对账(≈跑一次 E5):**

1. **先对账,别先动手**:通读 L1 + `docs/`,列"方法论要求 vs 项目现状"的缺口(死链、缺的运行手册、规则与执行说明脱节…),每项标**是否需要用户拍板**。
2. **只补无争议缺口**:如 L1 声明了 `docs/templates/<x>.md` 却**该文件不存在**(死链)→ 补上;运行期手册(`verifying-n2` / `teach-back-verifier-prompt`)缺失 → 补;**不改 L1 已成文的措辞**。
3. **布局跟随项目**:项目用 `docs/templates/`、就用 `docs/templates/`——**不要**强行改成 skill 的 `docs-templates/`(两套并存 = E4 违例)。要统一旧布局 → ADR + 用户决定。
4. **版本差异不擅自升级**:项目 L1 可能是本方法论的**早期版本**(铁律条数不同、E2 三类 vs 四类、无 scripts)。**保留项目版**;是否升到当前版本 = **用户的决定**(牵动既有文档),不默默替换。
5. **本项目当前维护的文档默认不建**:`docs/core-code.md`、`docs/modules/*`、新 ADR……凡是要新增**本项目当前维护的文档**的,先列进提问清单,别自作主张。
6. 收尾:只汇报"补了哪些缺口 / 还差什么待定"(见 Step 4 的 delta 版收尾)。

### Step 3: 边对话边写入(核心步骤)

**硬性要求:每段对话产出立即写入对应文档段落,让用户看到进度。** 不要囤积——用户说完一段,马上 Edit 写入,再问下一段。

- **第一阶段(填 L1 主轴):** 按 [是什么] → [为什么] → [不变量] 顺序,每段问 1-2 个核心问题,答完立即写入 L1 文件
- **第二阶段(填 L2 主流程):** L1 有共识后**才创建** `docs/architecture.md`,重点产出**主流程叙述**(10-20 行,从入口到出口)
- **第三阶段(按需,不在初建时一次做完):** 某模块出现 N2 逻辑、或其细节开始往 L2 / 大文档里堆时建 L3;决策发生时建 ADR。跨模块的 N2 **必须有家**——建 L4,或写进 L2 的 `[不变量]` 架构级约束 + L3 留一行指针(L4 默认不建)。
- **若 [是什么] 尚未收敛**(重立项 / 方向未定):L1 概述写成**双段**(现状 / 方向草案)+ 显式"开放问题",**别假装收敛**;teach-back 会正确卡在这里(需人拍板,不是 agent 能补的)

### Step 3.5: teach-back 闸门(每层写完 + 进实现前)

**硬性要求:进实现前,命中下列任一条件才做 teach-back;都不命中则跳过。** 这是"文档够不够实现"的判据,不是可选项——但**触发面必须窄**。否则它在最需要它的项目里(新领域:几乎一切都算 N1)变成每次改动都跑的仪式,人跑三次之后就开始偷偷标 N0 或直接绕过。

触发条件(任一):

1. 单元标记 **N2**(AI 未见);
2. 改动**触及不变量**(新增 / 修改 / 首次为某条约束造验收);
3. **某术语还没有可判定的定义**(`docs/glossary.md` 里该词空白 / 有 ≥2 种互相竞争的含义 / 含义刚被修改)。**"新增了一个已定义清楚的词"不算触发**——否则冷启动时每层都在引入新词,闸门会退化成"每次改动都跑"的仪式;
4. **跨层大改动**(横跨 L1–L4 中不止一层)。

**N0 一律跳过;纯 N1 且验收写得出来 → 跳过**(积木是可迁移的,硬上标准只会误伤)。**写不出验收的 N1,先按 N2 处理。**

> 这不降低标准:四条命中任一,都是"猜错会静默扩散、事后很难发现"的位置;纯 N1 的返工是可见的、当场就能修。

**必须派一个全新 subagent 来做——不继承本会话历史,只喂文档 + 派发参数。** 当前会话自己复述 = 自证(误读会一起误读),不算数。用 `references/teach-back-verifier-prompt.md` 的模板。

- **何时跑:** 命中上方四条触发条件之一。**N0、以及"验收写得出来的纯 N1"跳过**(模型自己能补)。
- **派发参数必填**(防误伤,写法见 verifier prompt):① 待验证单元;② **判定范围**——L1 / L2 一律**决策级**(判"能否据此做决策不跑偏"),**L3 模块文档 / N2 单元才用实现级**(判"能否只凭文档正确实现");③ 上轮阻断清单(首跑填"无")。
- **派发粒度:一个待验证单元 = 一份派发参数。** 可以一次并行派多个验证者,但**每份判定互相独立**;冷启动整体可打成一包交付,**不因此把多个单元合并成一次判定**(合并会让缺口归属不明、返工时不知道改哪份)。
- **决策级派发前先自检"范围词":** 文档凡用「子集 / 方言 / 自定范围 / 支持哪些 X」这类词框定范围,却**没列内容、没给路径、也没登记「开放问题」** → 验证者必判 [阻断]。派发前先把范围写死,或登记进「开放问题」——否则必卡。(判据见 verifier prompt「判定范围」决策级第 4 条)
- **决策级派发前再自检"开放问题":** 文档若还有**决策级**开放问题(目标 / 范围 / 不变量未定),验证者一律判**需人拍板**(不是通过)。派发前先把这类问题拿去问用户拍板,或明确它只是"非决策级"(不改变做什么 / 怎么做)。(定义见 verifier prompt 判定段)
- 产出:① 独立复述三段式;② "我需要但你没写"的缺口清单(词句类发现必须逐字引用原文);③ 判定 **通过 / 不通过(文档缺陷)/ 需人拍板**。
- **不通过(文档缺陷)→ 改文档**,不是改提示词;重跑时**附上轮阻断清单**——验证者会先**逐条复核**旧项(附证据)、再**全面扫描**(写法见 verifier prompt 的「复核上轮」)。每轮都是新验证者,不带上轮清单 = 每轮全量重掷,达不到收敛。
- **需人拍板 → 别循环改文档**:阻断项全是"开放问题"里显式声明的未决信息时,答案在用户手里。把待拍板清单当场问用户,拍板结果落回文档再验——**方向不收敛不是措辞问题,反复重写只会原地打转**。
- 冒出的假设 / 歧义 → 当场澄清:登记 `docs/glossary.md` / 补不变量 / 记 open questions。
- 遇 **N2**(新领域核心逻辑)→ **必须**先把"步骤级说明 + 危险实现清单 + 例子 + 验收"补进它的**家**(core-code / L2 公共节 / L3;**若该模块还没有 L3,先照 `docs-templates/module-doc.md` 生成**),再放行实现。

**退化路径(宿主 / 会话派不出"看不到本会话"的独立 agent 时):** 不要自评充数(自评 = 自证,不算数),也不要卡死。① 把待验证正文 + 验证者 prompt + 派发参数**封存**到 `docs/reviews/<日期>-<主题>-package/`,配一份 `MANIFEST`(文件清单 + 摘要 + 是否与当前文档同步);**不要抄进同一份文件**——同一文本两处必然漂移,违反 E1;② 另写一份指针记录,声明范围与"**闸门未通过(未执行)**",**冻结实现**;③ 把"跑一次独立验证"作为移交项交给宿主 / 人。

只有验证者判"通过"后,才进入下一阶段。

### Step 3.6: 文档完成判据(什么时候停)

三条**同时**满足即停,不再往文档里加内容:

1. teach-back 判「通过」(不是「需人拍板」);
2. **危险实现清单**里每一项,都被某条不变量或某条 `**验收**` 挡住;
3. 每条 N2 都有可跑验收(命令 或 property 断言)。

> 缺任一条 = 还没写完;**三条齐了还想再加,多半是在把实现细节抄进决策层**。"还能再写点"不是继续写的理由。

**「需人拍板」不是失败,是正常终点。** 全新领域在收敛前必然带决策级开放问题——那说明**需要人拍板**,不是文档没写好。此时的可交付态是:**骨架完成 + 拍板清单 + 闸门未通过已明示**(而不是"永不收敛、什么都交不出")。先把清单拿去问人,拍板结果落回文档再验。

**退化路径的停笔判据(派不出独立验证者 / 没有用户可问时):** 上面第 1 条**不适用**,改判为三条同时满足:① 投递包就绪(待验证正文 + prompt + 派发参数已封存 + `MANIFEST` 已标同步状态);② "闸门未执行"已显式标注;③ 拍板清单已列出。这三条 = **骨架交付态**,实现仍然冻结。

> **快照失效:** 若 `MANIFEST` 记的摘要与当前文档不符 → **快照已过期**,必须重新封存;过期的快照**不得再被当作当前文档引用**(否则它就是 E1 警告的第二份"尸体")。

**初始化期(技术栈还没定)的验收怎么写:** 允许命令形态待定——写成"与语言无关的 property 断言 / approved fixture + `形如 <runner> tests/...`",但必须满足:① 断言内容写实(不能只有一个名字或一句"要有测试");② 把它登记进「开放问题」。**命令待定 ≠ 验收可以欠着**;技术栈一拍板,立刻把命令补成可跑的。

### Step 4: 收尾说明

初轮对话(L1 + L2 主流程)完成后,告诉用户后续机制:

```
文档方法论已落地。接下来:
- 开发新模块前,从 docs-templates/ 复制 module-doc.md 到 docs/modules/<name>.md,先填后写代码
- 重大决策发生时,在 docs/decisions/ 记一条 ADR
- 大改动前,先更新对应层文档,再写代码
- L4 默认不要——只有核心单元**被 ≥2 个工作场景共同加载**时才补(没补时,跨模块契约写进 L2 的架构级约束 + L3 留一行指针)
- 填好任一文档后,删掉其中的引导注释(`<!-- … -->`)——它们含占位符,留着会被 `check-doc-refs` 报为"未填"
- 出现新领域名词 → 登记 docs/glossary.md;N2 逻辑 → 补"步骤级 + 例子 + 验收"
- 进实现前先跑 teach-back——命中 N2 / 触及不变量 / 术语未定义或歧义 / 跨层大改动 任一条(**纯 N1 与 N0 跳过**;独立 subagent,见 references/teach-back-verifier-prompt.md)
- (可选)把 scripts/ 拷进项目,按 references/wiring.md 接到 pre-commit / CI——挡"改代码忘文档"、查死链 / N2 缺 `**验收**` / 活文档引记录(Windows:先按 wiring.md 加一行 `.gitattributes`,否则 `.sh` 会被检出成 CRLF、根本跑不起来)

本文件已含方法论精要,后续 agent 启动会自动加载,不需要再调用这个 skill。
```

> **delta 模式(Step 2D)不适用上面这套"全新项目"话术**——只汇报"补了哪些缺口 / 还差什么待定"。

## 对话地图(L1 三段式的问题清单)

给 agent 的对话地图,**不是问卷**——根据用户回答自然展开,不要机械地一条条问。

### [是什么] 段——问项目定位

- 这个项目要解决什么问题?(一句话能说清吗)
- 谁会用?用在什么场景?
- **不做什么**(明确边界同样重要,边界外写出来)
- 主要功能 / 模块的大致预想?

### [是什么] 段——问术语(填 `docs/glossary.md`)

- 有没有**外人听不懂**的词?(行业黑话、自定义概念)
- 哪些词**最容易混**?(记下来当反例)
- 有没有**旧叫法**已废弃?(记下来当"禁用别名")
- 生成代码时必须知道**类型 / 结构**的词有哪些?

### [为什么] 段——问设计哲学

- 为什么用这个技术栈 / 架构风格?(强约束还是偏好)
- 核心价值观 / 设计哲学,2-3 条?(例:统一模型优先于扩展、性能优先于优雅)
- 考虑过哪些替代方案?为什么拒绝?(被拒方案是金矿)

### [不变量] 段——问硬约束

- 性能预算?(响应时间、吞吐、内存上限)
- 技术栈锁定?(必须用 / 必须不用什么)
- 可维护性底线?(测试覆盖、文档要求)
- 安全 / 合规约束?
- **最怕写成什么样?** 让对方列 3 种"看起来对、语义却错"的实现(例:重试没做幂等 / 时间按本地时区算 / 权限只查角色不查资源归属)——这就是**危险实现清单**,每条后面必须跟一句"由哪条不变量 / 验收挡住"
- **失败路径分别怎么表现?**(超时 / 部分成功 / 冲突并发 / 越权)——落到 `docs/modules/<name>.md` 的失败语义表,**别接受"合理处理错误"**

## 反模式(checklist)

> 涉及 E1–E7 的详细判据见 `references/evolution-rules.md`(项目内:`docs-templates/evolution-rules.md`);此处只列**症状**。

skill 自身要避免的:

- ❌ **凭空编造 L1 内容**(目标、设计哲学优先对话产生;但"从代码 / 既有作者文档 / git 等**证据推断草稿 + 标注『推断,待确认』 + 标来源**"是允许的,不算编造——**判据:有出处=证据,只能靠猜=编造**)
- ❌ **跳过对话直接生成"看起来完整"的文档**(空洞内容比空骨架更糟)
- ❌ **一次性把 `docs/` 下本项目当前维护的文档都建成空骨架**(会被遗忘);但 `docs-templates/` 属"对账忽略"、**应一次放齐**(否则 L1 指针悬空)
- ❌ **在已有 L1 文件的项目静默覆盖**(走 Step 2B,只补方法论段)
- ❌ **一次问完所有问题**(应分阶段,边讨论边记录)
- ❌ **囤积对话产出**(说一段就立即写入)
- ❌ **主动生成 L4**(默认不要;即便命中收录标准,也先问"建层,还是写进 L2 的架构级约束")
- ❌ **把 skill 硬套到已有完善文档的项目**(应区分:无 L1 → 走 Step 2C 嫁接;已有 L1 且没诉求 → 不推销)
- ❌ **[是什么] 新旧陈述并存**([为什么] 被推翻要标 `⚠️ 已被推翻,见 ADR-YYY`)
- ❌ **改代码绕过不变量**(违反却不修订文档 = 不变量失效的开端)
- ❌ **代码注释写版本变更史**(历史归 ADR / git log)
- ❌ **方向性陈述混进事实段裸留**(意向不会变假,只会悬置)
- ❌ **完成 / 放弃的计划留在活跃清单**(done 移出,dropped 带理由升格为"不做 X"的 ADR)
- ❌ **领域名词不定义就直接用**(AI 会拿训练数据里的通用含义去猜,新领域必错)——先登记术语表
- ❌ **N2 核心逻辑只写职责、不给步骤 / 危险实现清单 / 例子 / 验收**
- ❌ **实现前不做 teach-back**
- ❌ **接受模糊词**("优化 / 合理处理"当需求)——换可判定写法
- ❌ **多宿主各写一份规则**(两份必然漂移——主文件 + 指针)
- ❌ **自主档和文档层都叫 L**(授权档用 A1–A5,L1–L4 只指文档层)
- ❌ **N2 没有危险实现清单**(只写"要做什么",不写"最容易被写成什么"——后者才是模型的真实失败模式)
- ❌ **失败语义只写"错误处理约定"**(不逐条给:可重试?幂等?对外表现?怎么观测?)
- ❌ **teach-back 常态化**(纯 N1 每次改动都跑 → 三次后必然被绕过,见 Step 3.5 触发条件)
- ❌ **把"候选,待否决"当结论写进文档**(候选必须由用户选 / 否;否决理由进 ADR,不能静默转正)
- ❌ **AI "顺手优化"掉人指定的接口 / 数据结构 / 失败码**(A4–A5 的典型失败;`[已定]` 就是挡这个的)

## 产出文件结构

```
./AGENTS.md  (或 ./CLAUDE.md,按宿主)  # L1 主战场 —— Step 2A 立即创建
./docs/                     # 本项目当前维护的文档 —— 对账只扫这里
  ├── architecture.md       # L2 —— 进入 L2 讨论时创建
  ├── glossary.md           # 术语表 —— 出现领域名词时创建
  ├── modules/<name>.md     # L3 —— 每模块开发前
  ├── core-code.md          # L4 —— 可选:被 ≥2 个工作场景共同加载的核心单元才建;不建时跨模块契约写进 architecture.md 的「架构级约束」
  ├── reviews/              # E5 对账产出(teach-back / 文档考古) —— 首次对账时创建
  └── decisions/
      ├── README.md         # ADR 索引 —— 首次记 ADR 时创建
      └── adr-XXX-*.md      # 真实 ADR
./docs-templates/           # skill 提供的模板与运行手册(不是本项目当前维护的文档:对账忽略) —— Step 2A 整套落地
  ├── module-doc.md
  ├── adr-template.md
  ├── evolution-rules.md              # 运行核心:演化期规则 E1–E7(L1 只留指针)
  ├── verifying-n2.md                 # 运行核心:怎么给 N2 造验收
  ├── verifying-nonfunctional.md      # 运行核心:非功能 / 主观需求怎么造验收(确定性 / 性能 / 审美 / 合规)
  └── teach-back-verifier-prompt.md   # 运行核心:teach-back 验证者 prompt
```

除 L1 与**整套 `docs-templates/`** 外,`docs/` 下本项目当前维护的文档**全部按需创建**(理由见 Step 2A)。
