# Init Project Docs — 项目记忆协议

> **关系定位:** 本 skill 是 `seeding-skills` 的子 skill——沿用其类型判型 / 验收 / 演化纪律;实践中的可泛化经验回灌 seeding(写回上游 skill;见 `RESEARCH-BACKLOG.md`)。
> **主型:元型**(决定验收:定义项目记忆方法论);**副型:流程型**(只影响写法:bootstrap 工作流,不改验收)。类型定义见 `seeding-skills` 的 `references/skill-types.md`。
> **本 skill 只做沉淀侧(把对话固化为项目记忆):** 对话内容如何进入历史 / 当下 / 未来;不规定"怎么提问、怎么质疑、怎么去模糊"这些对话技巧。

## 术语速查(先读;完整表见 `references/skill-glossary.md`)

本 skill 的常用词有专指,按通用义读会偏:

- **历史 / 当下 / 未来** = 三个**时间桶**(决策记录 / 现状与约束 / 方向与开放问题),不是 git 历史 / 当前时刻 / 路线图。**文档层 L1–L4 是另一根轴**,别和时间桶混。
- **升格 / 退役 / 游标** = 把仍成立的理由搬进当下正文后记录离场 / 记录移出工作区(git 保留,不是删除、不是换目录) / `.last-review` 这类只记录"看到哪了"的状态(不是历史)。**年龄不是判据**,只在对账时触发审计。
- **superseded / expired** = 被新决定取代 / 前提**有证据地**消失且没有继任决定;两者都退役,`expired` 不是退役候选。
- **沉淀侧 / 回灌** = 把对话固化为项目记忆 / 把可泛化经验写回上游 skill;不是对话技巧,也不是数据回填。
- **契约 / 契约级变更** = 项目文档里的约束性陈述(不变量 / `[已定]` / 接口 / 术语定义)及其增删改;不是法律或 API 合同。
- **对账 / 复核 / 验证 / 检查** = 文档-代码/记录的结构一致性核对(改代码前也做)/ 独立 agent 的语义复核 / 可执行验收 / 脚本结构检查;四者不互换。**「复核通过」只说明文档内部一致**,不证明断言为真。
- **镜头 / 多镜 panel** = 一个独立复核视角 / 多个互不可见的视角各判一遍再合并去重;不是相机镜头或 UI 面板。
- **未接入 / 未复跑** = `scripts/` 未拷入 / 脚本在但这次只列未执行;都不是"已通过"。
- **待填件 / 就地读件** = 复制后填写的模板 / 留在 `docs-templates/` 直接引用的参考件;不是本项目当前维护的文档。
- **基线 / 快照 / 冻结** = 先钉一个参照再比对 / 某一时刻的完整状态副本 / 把预期钉死;三者都必须带限定语:校准基线(已知答案对照)/ 文档基线(`last verified` SHA)/ 性能基线 / 分档基线;现状快照 / 历史快照 / 数据快照;冻结计数(文档固定数字)/ 冻结期望(已批准 golden fixture)/ 冻结画面(固定渲染状态)。
- **指针 / 唯一正文归属(旧称"正典") / 拍板人(作者 / 用户)** = **只指向文档并说明它管什么**的目录条目(只出现在入口文档的活文档索引里;句子级的"见 ADR-0NN""出处"行不算指针、不许写)/ 定义落在哪一段 / 谁做决定;不要用裸"归属"兼指后两者。
- **主型 / 副型** = 主型决定验收;副型只影响写法,不改验收。
- **档 / 层 / 桶** = 验收档或 novelty 档 / 文档层 L1–L4 / 时间桶;三根轴,不要互相借用。
- **文件白名单 / 最小独立模拟器 / 校准探针** = 允许验证者读的文件清单 / 按文档规则从零写临时实现复现数字(不是替身环境)/ 每镜预埋的已知缺陷。

## 定位

项目记忆**协议**(人-AI 的文档协作约定,不是网络 / API 协议),不是文档模板生成器。不是文档内容的作者——内容靠和用户对话涌现。

> **目标工况:人至少给出功能与可验收行为**(连需求与验收都交给 AI 起草的项目不在范围内——见 Step 1)。

skill 提供四样东西:① 方法论框架(三时间轴 × 三段式 × 4 层);② 文件结构骨架;③ 对话地图(问什么,不替用户答);④ 可判定约束(术语先定义、N2 可实现、复核按需)。

**关键边界:** 不替用户写内容——但允许"从代码 / 既有作者文档 / git 推断草稿 + 标注『推断,待确认』 + 标来源";禁止凭空编造。**有出处 = 证据;只能靠猜 = 编造**。

**候选(待否决)** 只适用于 `[为什么]` / `[不变量]`(阈值 / 代理指标)/ 未来桶(计划),不适用于 `[是什么]` 事实:新领域没有证据时,给 ≥2 个显式标注"候选,待否决"的方案与代价,由用户选 / 否;否决理由进 ADR。**候选是状态,不是落点**:未接受的候选一律登记进未来桶(L1 开放问题 / 项目计划);接受后 → 历史(ADR)或当下(不变量 / 术语)。候选不能静默转正。

## 宿主适配(先定:L1 文件叫什么?)

宿主(Claude Code / Command Code / OpenCode / Cursor / Windsurf / Copilot…)决定 L1 文件名——宿主映射在 `templates/l1-memory.md` 顶部表,本 skill 不重述。不确定就问用户;判不出别硬默认 `AGENTS.md`。多宿主并存:选一个主文件,其余只放一行指针——两份规则必然漂移。

## 核心理念

文档是人和 AI 的"共享内存":写**决策需要的信息**,不写**实现需要的信息**。人类靠文档建立心智模型,AI 靠文档加载上下文;双方必须在同一份信息上对齐。内容靠对话产生,**skill 不能跳过对话**。

**历史不是默认产物**:记录只在决策当下与过渡期有用;仍成立的理由必须回到当下正文,其余要有正面证据才退役——不要用摘要或归档给它续命。

## 去模糊与可实现(对话时的三个动作)

1. **术语先定义**:听到领域专有名词 / 易混词,追问并定义:跨模块的登记 `docs/glossary.md`,只在一个模块里用的写在该模块的术语小节(一个词只定义一次)。模糊词("优化 / 合理处理 / 相关逻辑")= 没有可判定指称物 → 追问"具体指什么?给出两个互斥解释让我选"。非功能 / 主观词也要落地(可测代理指标 / 钉住可观测不变);审美拿不到阈值时允许"代理指标 + 候选",但不许原样留形容词。详见 `templates/glossary.md` 与 `references/verifying-nonfunctional.md`。
2. **给逻辑分档**:N0 通用 / N1 项目特有 / **N2 AI 未见**。N2 必须写到"步骤级说明 + 危险实现清单 + 精确例子 + 可跑验收 + 失败语义";N0 / N1 不必。详见 `references/verifying-n2.md`。
3. **按需复核**:命中 Step 3.5 的信号时,派独立 agent 或跑多镜 panel;「不通过」→ 改文档;「需人拍板」→ 把未决问题交用户。

## 何时使用 / 不适合

**适合:** 新项目 / 立项;要写 `CLAUDE.md` / `AGENTS.md`;已有项目补 L1;已有 L1 但想引入方法论;项目结构变化需要重建;含 N2 核心逻辑需要写到可实现。

**不适合:** 已有完整 L1 且用户没说要改(不推销);单次任务 / 一次性脚本;用户只想快速生成代码速查(改用内置 `init`——它写实现信息,本 skill 写决策信息)。

## 执行面:规则靠什么生效

| 类 | 谁执行 | 本 skill 的做法 |
|---|---|---|
| **脚本可查** | 检查器 / pre-commit / CI | 对账脚本 + 新增检查器;见 `references/tooling.md` 与 `references/wiring.md` |
| **需独立复核** | 一个看不到本会话的独立 agent | teach-back + `review-panel.md`(按需、可攒批) |
| **只能靠自觉** | 无 | 明确承认无法保证 |

**现有脚本:** `check-docs-sync`(代码动、文档没动)、`check-doc-refs`(死链 / 占位 / N2 缺验收 / 危险清单 / 失败语义 / 现状引记录)、`review-backlog`(复核 delta)。
**新增脚本:** `check-code-refs.py`(内联代码引用)、`run-n2-acceptance.py`(验收 runner)、`check-consistency.py`(重复定义 / 数值冲突 / 超预算 / 参数别名 / 术语下沉候选)、`lint-doc-structure.py`(结构警告)。
**共享:** `scripts/_doc_common.py`(与上面这些 Python 检查器同拷)。

> 别给"约定型"规则硬配检查器——那只会制造噪音,让人开始无视所有提示。

## Workflow

### Step 1: 检查环境 + 决定模式 + 定宿主

- 有无 L1? 无 L1 + **基本空目录**(除 `.git` / skill 模板外,没有作者手写文件)→ **2A**;无 L1 + 有任何作者手写文件(README / 设计文档 / docs,哪怕只有一份)→ **2C 嫁接**;有 L1 + 文档过写 / 用户说“看不懂 / 干扰 / 想变少” → **2R reset**;有 L1 + 已写着方法论 → **2D delta**;有 L1 + 想引入方法论 → **2B 合并**;有 L1 + 用户没说要改 → 不推销。
- 是否 git?(非 git:delta / SHA 不可用,退化为人工清单)
- 用哪个宿主?→ 决定 L1 文件名。
- **目标工况:人至少给出功能与可验收行为**;人指定项标 `[已定]`,AI 不得"顺手优化"。若连功能与验收都由 AI 起草,本 skill 不适用。

### Step 2A: 全新模式——先 lite，再按需 full

**默认 lite：** 只落 L1 + `task_plan.md` + `docs/.live`（可空）；`docs/` 先不建。L1 只放项目记忆；方法论复制到 `docs-templates/methodology.md`（就地读件），**不要写进 L1**。

**full：** 只有出现 N2 / 跨模块 N2 / 多模块并行，才加 `docs/architecture.md` / `docs/modules/` / `docs/glossary.md` / `docs/decisions/`。**不要一次铺 13 份模板。**

**关键：** `docs/` 下本项目当前维护的文档**不要预先建空骨架**（会被遗忘）；`docs-templates/` 只放**当前会用到的**就地读件，不要“先铺齐再说”——铺齐会把模板变成义务。

1. 复制 `templates/l1-memory.md` → 项目根 L1 文件名。
2. 复制 `templates/methodology.md` → `docs-templates/methodology.md`；再按需复制 `module-doc` / `adr-template` / `glossary` / `architecture` / `evolution-rules` / `temporal-model` / `review-panel` / `verifying-n2` / `verifying-nonfunctional` / `teach-back-verifier-prompt`（映射见 `references/layout.md`）。
3. 建 `task_plan.md`（未来桶）；第一个活文档出现时写 `docs/.live`（一行一个路径，相对 `docs/`）。
4. 然后进入 Step 3 对话；`docs/` 下当前维护的文档按需创建（跨模块术语 → `docs/glossary.md`；L2 → `docs/architecture.md`；模块 → `docs/modules/<name>.md`；ADR → `docs/decisions/`（决策工作台；稳定后升格 / 退役），并在 `docs/.ignore` 排掉 `decisions/` 与 `reviews/`；对账 → `docs/reviews/`（按对账周期退役）；跨模块 N2 → `docs/core-code.md` 或 `docs/specs/`）。
5. 把本 skill 的 `scripts/` **整目录**拷进项目 `<repo>/scripts/`（含共享模块 `_doc_common.py`）；若用户不接脚本，在 L1 标「scripts: 未接入」，后续命令按「未复跑」处理。

> **模板铺齐 ≠ 完成：** 2A 在 Step 3 填完内容后、Step 4 做一次 prune pass；不要对空模板删栏位（会删掉检查器要求的节）。**2B/2C 不动作者原有文件；2D 只补 delta；想变少走 2R。**

### Step 2B: 合并模式——已有 L1

不破坏现有内容,只补指针 + 缺失层:读现有 L1 → **不要把方法论插入 L1**;确保 `docs-templates/methodology.md` 在位,L1 只加一行指针 → 不动用户原有内容 → 检查散落的不变量,提示归并但**让用户决定** → `docs/` 按需创建(先问)→ Step 3 从"补缺"开始。

> **合并后核对:** `docs-templates/methodology.md` 在位 + L1 只有指针;铁律 / 加载表 / 完成判据 / E1–E7 不再常驻 L1。若旧 L1 已有方法论正文,移到 methodology 并留指针。

> **布局跟随项目:** 已有 `docs/templates/` 就跟随,不强行改成 `docs-templates/`——两套并存 = E4 违例。要统一 → ADR + 用户决定。项目自定义模板目录必须同步进检查器的 `DOC_EXCLUDE` / `DEFAULT_EXCLUDE`,否则模板会被当成现状文档扫。

### Step 2C: 嫁接模式——已有文档、缺 L1

先映射,再落骨架;既有的"现状事实"文档 = 指针目标,不新造重复层。只要存在作者手写的 README / 设计文档 / docs,就不算空目录,走 2C。

1. 通读既有文档,映射到 4 层:现状事实 → L2 事实源(新 `architecture.md` 只写决策 + 不变量,不搬既有正文);设计动机 / 不变量 / 验收 → L1/L2/L4;**去处由 L1 的活文档索引交代,正文里不嵌"见 …"**;存档 / 旧方案 → 存档层(legacy/archive;不是 L1–L4 的第 5 层;不迁、不删,标注边界,对账排除)。
2. 落 L1 + `docs-templates/methodology.md`;其余按 2A lite/full 按需,不要一次铺齐。
3. 填 L1 标清"内容从哪来":证据标来源;猜不到 → 开放问题,别硬填。
4. 冲突时只在新骨架文件顶部加 banner 声明事实源,**不动作者原有文件**;定性冲突记开放问题,交作者拍板。
5. Step 3 从"补既有文档缺的那部分"开始;`architecture.md` 可先作证据草稿(标 `推断,待确认`)。

> 同名冲突:既有事实源占用 `docs/architecture.md` → 新骨架另起名(如 `architecture-l2.md`),顶部 banner 指明事实源,并同步脚本两张表。

### Step 2D: delta 对账模式——项目已在本方法论上运行

不要重造、不要重写 / 升级版本。动作 = 补 delta + 对账(≈ E5):

1. 先对账:通读 L1 + `docs/.live` + `docs/`,列"方法论要求 vs 项目现状"缺口,标是否需要用户拍板。
2. 只补无争议缺口(死链、缺的就地读件);不改 L1 已成文措辞。
3. 布局跟随项目;不擅自升级版本(用户的决定)。
4. 默认不新增本项目当前维护的文档;要新增先列提问清单。
5. 收尾只汇报"补了哪些缺口 / 还差什么待定"。
6. **存量减重(可选 delta):** 触发 = 任一活文档超预算 / 活文档总量 > 代码总量 / 副本候选 ≥3。动作 = 量行数与体量比 → 找重复字面量 / 单模块术语 / 机器可判计数 → 出「合并 / 下沉术语 / 归档 / 退役」清单(不要用"转成指针"减行数) → 作者拍板后动手;不自动重写。**历史退役 = 已升格的 ADR + 上一对账周期的 reviews**;reviews 文件名带日期 + 主题,`ls` 即列表——不要给它另建索引。

### Step 2R: reset 模式——已有文档过写 / AI 生成 / 想变少

**触发:** 活文档 >10 / 文档总量 > 代码量 / 同一事实多处定义 / 用户说“看不懂 / 一直干扰 / 想变少”。
**门槛:** 作者点头；**作者手写文档不删除，只归档；AI 生成的历史记录可退役**（移出工作区，git 保留）；可回滚。

1. **冻结:** 先提交现状（或建分支 / `git stash`），确保可回滚。
2. **清点:** 列 `docs/` + 根文件；每份标 `作者写 / AI 写 / 历史`。作者写的改动需确认；AI 写的历史记录可直接退役，AI 写的其他文档可归档。
3. **选活集:** 按加载频率选 3–6 份（每会话：L1 / `task_plan` / 当前构建手册 / 设计约束；按任务：architecture 一页 / 2–3 个模块 / 术语表）。写 `docs/.live`。
4. **归档:** 其余移到 `docs/archive/`（保留日期在文件名）或 `docs/experiment/`（脚手架 / 实验日志）；不删除。AI 生成的历史记录（已升格的 ADR / 上周期 reviews）改为退役，移出工作区。
5. **改指针:** L1 只指活文档；历史只在“历史”段出现；活文档不拿 ADR / review 当依据；`docs/scaffolds/` 从游戏 README / glossary / L1 入口删掉。
6. **去时间 / 版本:** 活文档里的日期 / 文档版本号删掉或移进归档；只留顶部 `Last verified: <SHA>`；领域版本保留。
7. **量 before / after:** 文件数 / 行数 / 字节 / 日期数 / `check-consistency` 警告；跑项目验收证明只动文档。
8. **留档:** 一条 review 或 notes 记结论；两周后复量，涨 >20% 说明生成器没改完。

### Step 3: 边对话边写入(核心步骤)

**硬性要求:每段对话产出立即写入对应文档段落,让用户看到进度。** 不要囤积——用户说完一段,马上写入,再问下一段。落哪个桶由三时间轴决定,别把计划写成事实。

- **第一阶段(填 L1 主轴):** [是什么] → [为什么] → [不变量],每段问 1–2 个核心问题,答完立即写入。
- **第二阶段(填 L2 主流程):** L1 有共识后才创建 `docs/architecture.md`,重点产出主流程叙述(10–20 行,入口到出口)。
- **第三阶段(按需):** 模块出现 N2 或细节开始往 L2 堆 → 建 L3;决策发生 → **先判载体**(可逆 / 局部 / 一次性 → commit body;需评审 / 跨模块 → PR-RFC;不可逆 / 长期约束 → ADR),确需 ADR 才建(`docs/decisions/` 下一个决策一个文件,主目录即工作台;**不另写索引**——同目录 `ls` 就是索引;稳定后把仍成立的理由升格进当下,然后退役);跨模块 N2 必须有家(先建 `docs/core-code.md` 或 `docs/specs/`,**不要塞进 L2**;L3 留指针);N2 单元同时登记 `docs/n2-acceptance.json`(命令 + cwd),供 `run-n2-acceptance --run` 使用。
- **[是什么] 未收敛**(重立项 / 方向未定):L1 概述写双段(现状 / 方向草案)+ 开放问题,**别假装收敛**;方向草案是 `[是什么]` 里唯一允许的方向陈述,**只有方向半段的每行**带状态并显式标注方向草案,现状半段保持事实、不带方向状态,收敛后移出;复核会正确卡在「需人拍板」。

### Step 3.5: 改代码前的复核(teach-back + 多镜 panel)

**主战场在改代码前**:文档是实现的契约。**攒批做,不逐次跑**;落到实现之后,就从"提前拦截"退化成"事后对账"。commit 时的脚本只是事后漂移提醒。

**何时值得做(信号):** ① 单元标记 N2;② 改了不变量;③ 术语还没有可判定定义;④ 跨层大改。都不占就跳过;纯 N1 且验收写得出来也跳过。

**契约级变更定义:** 契约文件(L1 / L2 / L3 / L4 / glossary)中的不变量、`[已定]`、接口 / 数据结构 / 失败码、术语定义、契约级断言的增删改;纯措辞 / 链接 / 排版不算。**四信号是“跑不跑”的唯一裁决;`review-panel.md`只决定“跑哪几镜”。**

**攒批:** 若已拷入 `scripts/`,先跑 `review-backlog`(零 token)列出自上次复核以来的契约 delta;未拷则人工列 delta 并标「未接入 / 未复跑」。只把 delta 喂给独立 agent;每个被喂的单元要整节(定义段 + 验收段必须同在);结论记 `docs/reviews/`,覆盖提交写进 `docs/reviews/.last-review`(游标,不退役)。**reviews 按对账周期整批退役**:下一次全量对账完成后,上一批移出工作区(git 保留);**退役前确认未闭合的 finding 已处置**。

**派发:**
- 派一个**看不到本会话**的全新 subagent;当前会话自评 = 自证,不算数。
- 基座 prompt:`references/teach-back-verifier-prompt.md`;判定范围:L1 / L2 决策级,L3 / L4 / N2 实现级(N2 一律实现级)。
- **待验证文档过大 / 多篇时**按模板的**文件白名单模式**派发(只读列出的文件、禁读代码;代码对标镜可加只读代码);整段粘贴在实测里会把派发撑挂。
- 一个待验证单元 = 一份派发参数;可并行,但每份判定独立;首跑「上轮阻断清单」填「无」。
- **派发前自检:** 范围词(子集 / 方言 / 支持哪些 X)必须列内容或登记开放问题;文档若有决策级开放问题,先请人拍板——否则验证者会判「需人拍板」或 [阻断]。
- **多镜 panel**(当下层):自洽 / 去模糊 / 术语 / 代码对标(N2 变更时加 N2 镜;可读性可选),见 `references/review-panel.md`。四镜独立、互不可见;协调者合并去重;第 2 轮新验证者先复核上轮阻断,再扫受影响范围。

**不通过 → 改文档**,不是改提示词;重跑附上轮阻断清单。**需人拍板 → 别循环改文档**:把决策级开放问题交用户,拍板后落回文档再验。N2 必须先补"步骤级 + 危险清单 + 例子 + 验收 + 失败语义"再放行实现。

**退化路径(派不出独立 agent):** 不自评充数,也不卡死:① 把待验证正文 + prompt + 派发参数封存到 `docs/reviews/<日期>-<主题>-package/`,配 `MANIFEST`(文件清单 + 校验值 + git SHA);② 另写指针记录,显式标「复核未执行」;③ 把"跑一次独立验证"列为移交项。是否等复核由你定。

### Step 3.6: 文档完成判据

**完成判据 = methodology「文档完成判据」五条**(复核 / 当下 DoD / 危险实现清单 / N2 验收 / 紧凑性);本 skill 不重述,按 `docs-templates/methodology.md` 执行。**「需人拍板」不是失败,是正常终点**:交付态 = 骨架完成 + 拍板清单 + **若做过复核**的复核判定已留档。**初轮按 L1 + L2 交付即进 Step 4**;五条判据是全量完成线,不是收尾前置。退化路径的停笔条件见 Step 3.5。

### Step 4: 收尾

**prune pass(仅 2A;2B/2C 不动作者内容,2D 走存量减重):** 找矛盾 → 只留必需 → 其余分组到按需加载的文件 → 建指针 → **flag for deletion**(冗余 / 太泛 / 显而易见的全删)。生成 ≠ 完成;不 prune 的初始化就是 Init Fossilization。

初轮(L1 + L2 主流程)完成后告诉用户:建模块前先填 L3;决策发生先判载体(commit body / PR-RFC / ADR),稳定后按 E4 升格或退役;大改动前先更新对应层文档;**改代码前跑复核 / panel**;L4 默认不建,跨模块 N2 才建 `core-code` / `specs`;填完删模板注释;新术语登记 glossary;N2 补步骤 / 危险清单 / 例子 / 验收 / 失败语义;复核按需、可攒批,推荐在实现前完成;检查器能查的先跑,不能跑就标"未接入 / 未复跑";**收尾做一次退役 pass**:已升格的 ADR 与上一对账周期的 reviews 移出工作区(git 保留),`.last-review` 保留;退役候选(三问:还挡着哪个具体错误改动 / 会否复发 / 现状文档能否读出;答不出)只登记、交作者拍板,不改 `status`、不自动移走。完整落点与脚本见 `references/layout.md` / `references/tooling.md`。

## 产出文件结构

落点唯一正文归属在 `references/layout.md`(完整目录 + 模板清单 + 脚本清单)。要点:L1 在项目根,只放项目记忆;`docs/.live` 是活文档清单;`docs/` 只放白名单活文档 + 决策工作台 + 冷存;`docs-templates/methodology.md` 是协议正文(不自动加载);`docs-templates/` 是待填件 / 就地读件,对账忽略;`docs/decisions/` 是在议 / 在途,稳定后升格或退役;`docs/reviews/` 存对账 / 复核留档,按周期批量退役;`docs/archive/` 与 `docs/experiment/` 不进日常加载。

## 反模式(checklist)

> 本清单是**失败模式索引**,不是规则正文:每条只指向已有规则,不在这里发明新规则;新增条目必须能回指 E1–E7 / 方法论 / 本文件某个 Step。规则冲突时以正文为准。

- ❌ 凭空编造 L1 内容(允许证据推断草稿 + 标来源;禁止猜)
- ❌ 把方法论塞回 L1，或让 L1 写日期 / 文档版本号
- ❌ 新增活文档不做 net-negative（合并 / 替换 / 归档一个）
- ❌ 跳过对话直接生成"看起来完整"的文档
- ❌ 一次性把 `docs/` 当前维护文档都建成空骨架(但 `docs-templates/` 应一次放齐)
- ❌ 在已有 L1 的项目静默覆盖(走 2B)
- ❌ 一次问完所有问题 / 囤积对话产出
- ❌ 主动生成 L4(跨模块 N2 除外;要建先问,并记 ADR)
- ❌ 把 skill 硬套到已有完善文档的项目(2C / 不推销)
- ❌ `[是什么]` 新旧陈述并存;`[为什么]` 留着已被推翻的论述(该直接改写或删除,不标"已推翻")
- ❌ 把**历史**当现状事实;**未来**计划裸留 `[是什么]`
- ❌ 改代码绕过不变量;代码注释写版本变更史
- ❌ 完成 / 放弃的计划留在活跃清单(done 移出;dropped 升格 ADR)
- ❌ 领域名词不定义就用;N2 只写职责,不给步骤 / 危险清单 / 例子 / 验收 / 失败语义
- ❌ 失败语义只写"错误处理约定"
- ❌ 把"候选,待否决"当结论
- ❌ 把复核当关卡或当仪式;**改完代码才做复核**,把事后对账冒充事前拦截
- ❌ 每个 commit 跑全 panel;四镜重复报告同一条不去重;没有校准探针就宣布"没问题"
- ❌ 接受模糊词("优化 / 合理处理"当需求)
- ❌ 多宿主各写一份规则
- ❌ AI "顺手优化"掉人指定的接口 / 数据结构 / 失败码(`[已定]`)
- ❌ 模板加了要求、却没写明由谁检查(脚本 / 独立复核 / 自觉)
- ❌ 让每层都"自足"(＝每层重写);也别用指针兜:摘要、`> 出处：…` 行、"见 ADR-0NN"都会变成第二处出处——别处就该不写(读者要知道去哪份文档,看 L1 的活文档索引)
- ❌ 生成模板后不 prune(初始化 ≠ 完成;Init Fossilization)
- ❌ 给同目录的 ADR 再写一份索引(`ls` 就是名单,多一份清单只多一处会漂);把 `superseded` / `expired` 记录留在工作区(读文件的人也会读到它)
- ❌ 把"答不出三问"当退役证据——只登记退役候选,交作者;退役要有正面证据(升格 / 前提消失 / 作者拍板)
- ❌ 把归档当终点(只把 `superseded` 记录移进 `archive/`)——目录对内容搜索无效;**退役 = 移出工作区**;ADR 是日志,整个 `docs/decisions/` 都该在 `docs/.ignore` 里排掉(且 `git grep` 仍会漏,见 `references/search-surface.md`)
- ❌ 用摘要压缩历史——摘要会成为第二处出处;历史要么升格进当下,要么退役
- ❌ 给 reviews 写索引 / 年度总结——`ls` 即列表;唯一的"压缩产物"是写进 L1 的流程修正

## 验收(teach-back)

- **档位:** teach-back(无确定性产物;验收 = 独立复核)。
- **流程:** 按 `references/teach-back-verifier-prompt.md` 派一个**看不到本会话**的独立 agent,只喂待验证文档 + 派发参数;产出三段:复述 / 缺口清单 / 判定(通过 / 不通过 / 需人拍板)。
- **多镜 panel:** 命中 Step 3.5 信号(四信号)时,按 `references/review-panel.md` 跑四镜(必跑;N2 变更时加 N2 镜;可读性可选);每镜配校准探针;协调者合并去重;第 2 轮附上轮阻断清单。派发包格式见该文件。
- **留档:** 结论与覆盖提交写入目标项目 `docs/reviews/YYYY-MM-DD-<主题>.md` + `.last-review`(游标,不退役);reviews 按对账周期整批退役。
- **判据:** 「通过」或「需人拍板」即达可交付态;「不通过(文档缺陷)」→ 先改文档,重跑附上轮阻断清单。**「通过」只说明文档内部一致,不证明断言为真。**
- **工具自检:** `python -m unittest discover -s tests`(skill 侧);新脚本上线前必须有反向测试。
- **术语自检:** 改 `SKILL.md` 的高频词 / 新增术语后,按 `references/skill-glossary.md` 跑一次「只给 SKILL.md」的无上下文理解测试;出现「猜的」或偏离就补限定。
