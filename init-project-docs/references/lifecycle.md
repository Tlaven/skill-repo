# 维护：时间轴与演化规则

> 本文件管：过去 / 现在 / 未来怎么分、怎么落、怎么维护（E-1–E-7）、记录寿命、术语退役、当下 DoD。
> 读的时机：改文档 / 定期 / 大改动前。
> **E-5 的执行见 `verification.md`；层 / 深度见项目 methodology（`docs-templates/methodology.md`）；脚本见 `scripts/`。**

## 一、三个时间桶

| 桶 | 陈述性质 | 住哪 | 真相源 | 会怎么烂 |
| --- | --- | --- | --- | --- |
| **历史** | 决策型 | 记录：决策记录 / 复核与核对记录 / git | 历史 | 悬置 |
| **当下** | 描述型 + 约束型 | 当前维护的文档 + 术语表 | 代码 / 约束 | 变假 / 被悄悄违反 |
| **未来** | 方向型 | 开放问题 / 项目计划（含实现方向、ROADMAP、`task_plan`） | 承诺 | 悬置 |

阅读视图归当下，但不是约束的家。

## 二、四类路由

每段对话产出立即判类并落盘：

| 产出 | 去哪 |
| --- | --- |
| **决策 / 被拒方案** | 先判载体：可逆 / 局部 / 一次性 → commit body；需评审 / 跨模块 → PR / RFC；不可逆 / 长期约束 → 决策记录 |
| **事实 / 不变量 / 术语** | 当下：当前文档 / 术语表 |
| **计划 / 开放问题 / 候选** | 未来：开放问题 / 项目计划 |
| **未决且决策级** | 开放问题 + 请人拍板；不硬写成结论 |

**候选是状态，不是放哪**：未接受的候选一律标 `候选(待否决)` 并登记在未来；接受后 → 历史（决策记录）或当下（不变量 / 术语）。

判不准时问一句：**它是关于过去的选择、现在的真相，还是未来的意向？** 三者都不是，可能属于对话技巧，不归这套做法。

## 三、历史的使用四问

1. 读它是为了**理由 / 被拒方案 / 方向**，还是为了**现状事实**？
2. 当前文档里有没有**指向记录条目 / 记录目录**的引用？（有 = 违规；稳定条款代号不算）
3. 当前断言是否**自足**，还是挂在记录类文档上当依据？
4. 它现在还挡着哪个**具体**的错误改动？（答不出 = 退役候选，只登记交作者；仍挡着但当前文档没有 → 先升格，再退役）

规则：**历史只作方向，不作事实**。记录目录只在入口文档的活文档索引里出现一次（见项目 methodology 的引用 / 索引节，`docs-templates/methodology.md`）。若有脚本，`check-doc-refs` 的「现状文档引记录」是这条规则的代理检查；没有脚本就靠复核。

**记录 vs 唯一出处：** 复核 / 核对记录是记录，不是决策的唯一出处；决策记录的「需要跟进」段也是历史记录，不是未来的唯一出处；仍成立的决策理由只写在当下的 `[为什么]` / 不变量里；未来桶 = 开放问题 / 项目计划；要让记录的跟进项保持活跃，在项目计划里登记并回指记录。

## 四、未来最小约定

只需要三件事：

1. **状态**：`planned / doing / done / dropped`；
2. **拍板人**：谁做决定；
3. **结案条件**：什么情况下移出。

done 移出活跃清单；带理由的 dropped 升格为「不做 X」的决策记录。
未来**不配检查器**——只在核对 / 复核里看这三条。

## 五、当下 DoD（四条）

四条同时满足才算写完：

1. **自洽**：一个术语一个定义；一条不变量在项目活文档里只在一处成文，别处不写摘要（按代号引用不算第二处）；陈述的时态 / 类别正确；跨处引用不产生第二份定义。
2. **可读**：主流程 10–20 行；同一层内部自足；不做实现抄写；标题层级能当目录。可读性复核是可选加强，不是必需。
3. **对标**：描述型事实要么指向文件 / 目录，要么是可核对断言；内联代码引用（路径 / 符号 / flag / 配置键）只作辅助定位，规则本身必须可核对；代码改动映射到文档更新；文档基线记 `Last verified: <SHA>`（可选）。
4. **核心逻辑**：每条 N2 规格按五件套写全；每个危险项都被某条不变量或验收挡住。

脚本未接入时，相关项标「未接入 / 未复跑」，不得当成已通过。

**E 与时间桶：** E-1 当下 / E-2 未来 / E-3 当下 / E-4 历史 / E-5 跨时间 / E-6 代码与历史的分界 / E-7 当下。与三句话冲突时，以三句话为准，并回改 E 规则。

## 六、E-1 描述型（当下）

**旧陈述直接改写或删除。** 禁止新旧并存，哪怕标注「旧的」。

> 限定：`[为什么]` 里的决策论述被推翻时，同样改写或删除——不标「已被推翻」、不留原文、不附编号。方向型（E-2）例外：保留状态，因为「还没做」是当下事实。

- **能从代码 / git 验证的事实不抄**：文件清单、函数名、参数表这类，文档里不重抄。只留代码里**读不出来**的事实：边界、数据流方向、协作约束。确有必要指出住处时，指到**文件或目录**，不指行号、函数名或小节。
- **提示与证据不占正文**：防坑提示、实测比例、轮次与日期、「旧版曾用…」「已落地」这类过程叙事——都不住正文。理由仍成立 → 当下正文（危险清单 / `[为什么]`）；过程证据 → 记录类文档。
  **判据：** 这句删掉之后，读者还知道该怎么做吗？知道 ⇒ 提示 / 叙事，删；不知道 ⇒ 规则，留（并写短）。
- **现状 / 规则陈述必须自足**：不许把它挂到记录类文档上当依据。「旧称已退役，只写现行称（ADR-002）」是错的：记录不与现状同步，拿它当依据 = 让现状挂在会过期的文档上。
- 引用前先分清对方是**记录**（预期不与现状一致，「不符」不是病）还是**待办**（引用即承诺，过期即失效，见 E-2）。
- 判断「与旧决策是否冲突」看**当下的当前文档**，不看历史。
- `⚠` 只表示「注意」（危险清单里的强调），**不表示「已被推翻」**——看到它不要去找旧论述。
- 改 `[是什么]` 时顺手检查同文件 `[为什么]`；两者矛盾 = 有人只更新了一半，当场修掉。

> 引用 / 索引的写法（代号、方向、不写位置）见项目 methodology 的引用 / 索引节（`docs-templates/methodology.md`）；本文件只管「旧陈述不留」。

## 七、E-2 方向型（未来）

方向型最容易混进 `[是什么]` 伪装成事实。

- **集中安置**：方向型陈述住在未来桶（开放问题 / 项目计划 / 实现方向 / ROADMAP / `task_plan`）；记录的「需要跟进」段是历史，不是未来的唯一出处；要跟进时在项目计划登记并回指记录。状态只在有数的地方维护；散落在事实段里的方向性内容就地清除。
- **状态流转**：`planned → doing → done / dropped`。**done 移出**；**带理由的 dropped** 往往应升格为决策型（「不做 X」是约束，走记录）。
- **未来最小约定**：见 §四。
- **未收敛也不例外**：概述写「方向未定」这个**事实**，方向住「开放问题」。方向性陈述在 `[是什么]` 里裸留（无状态、无集中安置）= 过时旧陈述的另一种形态，核对时同样清。

## 八、E-3 约束型（当下）

- 任何一次改动若与现有不变量冲突，**必须从三条出路里选一条并执行**：修订不变量原文；给不变量加例外说明；放弃该改动。**禁止只改代码不动文档**。
- 推翻重大不变量必须升格为决策记录。
- 新理由落进当下正文后，记录只是过程载体：按 E-4 的记录寿命升格或退役。**不要让记录变成新不变量的第二处出处。**
- 判据：**当你会说「这条不变量过时了」时，就是记录的触发点。**
- **一条不变量跨多处成立时**，只留一处正文定义，放在它**最常被违反的地方**；别处不写摘要、不重述，按代号引用可以。
- 编号约定：不变量与开放问题用稳定编号（`I-` / `Q-`）；前缀含义只在项目的代号表里登记一次；编号供核对 delta 扫描与拍板引用；引用处不复述。
- **不变量引用了未拍板的术语 = 这条不变量本身未定**：当场标 `本条未定：取 <X> 读；若 Q-N 拍板为 <Y>，本条须改写`，并确保 `Q-N` 登记在开放问题里。
- **联动义务**：记录里标 `superseded` 只算 50%——记录状态不改变当前真相。必须：① 把当前文档里与旧决策绑定的段落改写或删除；② 修订相关不变量；③ 在新记录的「后果」段记下这两步是否完成。

## 九、E-4 决策型（历史）

### 什么该记

**必记：**

- 改完之后让后来者「惊讶」的决策（为什么不用 X？为什么这么绕？）；
- 推翻先前决策 / 引入第二套并行机制 / 改变数据模型身份语义；
- 养出「两套并存物」的决策（两个同名函数、两种标识符规则、两条数据通路）。

**不记：** 单纯的新功能、bug 修复、重构（代码即真相）。

### 补充 vs 推翻

判据是**被选方案有没有变**，不是规模：

| 情况 | 做法 |
| --- | --- |
| 改的是参数 / 实现方式 / 边界，被选方案不变 | 在原记录末尾追加**带日期的补充**（append-only，状态 `accepted(修订)`） |
| 改的是被选方案本身，或引入第二套并行机制 | 新建记录；旧记录只改 `status: superseded`；继任写 `supersedes` |

补充只增不改——记录不是现状文档；最新状态看 frontmatter，最新补充按日期排在文末；有歧义时**优先补充**，补充里写一句「为什么不是新记录」。

### 记录寿命

记录是**决策过程**的载体，不是长期档案。稳态目标量 = 0；目录里留的是「还在议 / 还在执行链上 / 理由尚未升格」的记录。**目录本身就是名单**：不另写列表；`ls docs/decisions/` 就是在议清单。

**三问决定去留：**

1. 它现在还挡着哪个**具体**的错误改动？
2. 未来还会有人重新提这个方案吗？
3. 当前文档读得出这个理由吗？（读得出 → 可直接退役）

**退役要有正面证据**，三选一：理由已升格进当下正文；前提可证伪地消失（依赖移除 / 代码路径删除 / 外部约束失效），并写明证据；作者拍板退役。
**「答不出」不是证据**——只登记为**退役候选**（不改 `status`），进当次核对的待拍板清单，交作者；不自动退役。

**升格**（理由仍成立、当前文档读不出）：把理由写进当下的 `[为什么]` / 不变量 / 危险清单；写不进任何一段 = 它其实不约束当下，按退役处理。升格后记录退役。

**退役**：文件移出工作区；字节留在 git。**不是换目录**——`archive/` 只改路径、不改检索结果，`rg` / `git grep` 照样命中。每次退役在核对记录里留一行处置证据。

**`superseded` vs `expired`：** 被新决定替代 → `superseded`（继任记录写 `supersedes`）；前提**有证据地**消失、没有继任决定 → `expired`。两者都退役；`expired` 不是退役候选。

**其他：**

- 关系字段跟着继任记录走；退役记录不再要求可解析的反向链接，继任的 `supersedes` 是唯一保留的链。
- 非 git 项目不退役：确认前提消失后标 `expired` 留在原处（读时按 `status` 跳过），靠 `docs/.ignore` 退出检索面；没有恢复手段。
- 存量归档的迁移：已有归档的项目不强制一次清空；按核对逐条判（升格 / 退役），退役前把关系搬到继任记录的 `supersedes`。
- 一次审计只做一遍：每次集中核对末尾跑一次，不逐 commit 检查。**复核不是退役判据**——它判文档写没写清，不判记录还值不值得留。

### 检索面（`.ignore` 的边界）

- `docs/.ignore` 只影响 `rg`；`git grep` 不认它，IDE 全局搜索要各自配 `search.exclude`。
- `archive/` 只改路径，`rg` / `git grep` 照样命中——**退役（移出工作区）才是唯一能挡住 `git grep` 的做法**。
- 配置细节与残留（`rg --no-ignore`）见项目的 `docs/decisions/README.md`（由 `decisions-readme` 模板生成）。

## 十一、E-6 代码注释与文档的分工

- 代码注释**不写版本变更史**（如「v0.13 从 io.js 迁入」）。文件头注释只写：该文件的角色定位 + 读者必须先知道的约束。
- **可逆 / 局部的决策**写 commit body（为什么 + 被拒方案，两行），不升级成决策记录。
- 判据：注释内容若能在 git log 或决策记录里找到，就不要写在代码里；注释里只留「读这段代码前必须知道的坑」。

## 十二、E-7 术语表 + 术语退役

- 出现**新领域概念** → 当场定义：跨模块的登记进 `docs/glossary.md`，只在一个模块里用的写在该模块的术语小节；再在别处使用。
- 文档里出现**未登记的名词** = 漂移信号：要么补登记，要么改用已登记词。
- 术语**含义变化** → 视为可能的不变量变更，走 E-3。
- 一个词只在一处定义（单一事实来源）；别处只引用，不重述。
- **找不到词先报作者**：概念 + 拟词 + 拟定义；未获批前不自造词。
- **术语退役 / 改名**：宣布全库退役前**必须 grep 实测**（范围 = `docs/` 全部 + 相关页面 / 脚本的中文叙述），**命中不为 0 不得宣布完成**。两类豁免**逐条记进记录**：① 历史原话（在记录里作**证据**引用）；② 被要求保持原样的件（逐条记明是哪个文件）。**代码标识符与数据字段名不在退役范围**——它们是实现量，不是领域词。

## 十三、自检

**时间：**

- [ ] 这段陈述是描述型 / 决策型 / 约束型 / 方向型？
- [ ] 它住在对应的桶里吗？方向有没有混进 `[是什么]`？
- [ ] 当前断言是否自足，有没有挂记录当依据？
- [ ] 历史记录是否只在索引里出现一次？
- [ ] 未来项是否有状态 / 拍板人 / 结案条件？

**E：**

- [ ] 有没有把旧描述留在正文里？
- [ ] 有没有抄代码能读出来的事实？
- [ ] 提示 / 过程叙事有没有混进正文？
- [ ] 改动碰到不变量时，走了三条出路的哪一条？
- [ ] 决策有没有先分流（commit / PR / 记录）？
- [ ] 记录退役有没有正面证据？
- [ ] 术语退役前 grep 过吗？豁免逐条记了吗？
