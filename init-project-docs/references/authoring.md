# M2 写入

> 本模块只管：问什么、写进哪一层、写多深、写在哪一段。
> 验收怎么造（M4）、记录怎么退役（M3）、复核怎么派（M5）不在本模块。
> 读的时机：每次写 / 改项目记忆时。
> 层 / 深度的判据在本模块 §四；验收怎么造见 M4。

## 一、词先定清楚

- 听到专有名词 / 易混词，追问并定义：跨模块的写进 `docs/glossary.md`，只在一个模块里用的写在该模块；一个词只定义一次。
- 模糊词（「优化 / 合理处理 / 相关逻辑」）= 没有可判定的指称 → 追问「具体指什么？给我两个互斥解释让我选」。
- 非功能 / 主观词也要落地：可测的替代指标 / 钉住可观测的不变；审美说不出阈值时允许「替代指标 + 备选」，但不许原样留形容词。
- **找不到词先报作者**：概念 + 拟词 + 拟定义；未获批前不自造词。

## 二、写入三阶段

### 第一阶段：填 L1 主轴

`[是什么]` → `[为什么]` → `[不变量]`，每段问 1–2 个核心问题，答完立刻写。问题库见 §五。

### 第二阶段：填 L2 主流程

主流程 / 架构边界要单独成文时，建 `docs/architecture.md`，重点写主流程（10–20 行，从入口到出口）。

### 第三阶段：按需

- 模块出现 N2，或细节一直往 L2 堆 → 建 L3；
- 要做决定 → 先看这条决定该记在哪（M3），确实需要才建；
- N2 单元的住处和登记不能漏：跨模块 → L2「N2 单元规格」；模块内 → L3；能跑成命令的登记进 `docs/n2-acceptance.json`。

### `[是什么]` 还没定

L1 概述**只写现状**——「方向未定」本身就是一条现状，别假装定了；方向进「开放问题」，一条一行，带 状态 / 谁定 / 什么条件下算结案；`[是什么]` 不放方向陈述。

## 三、三段式与必填件

| 段 | 写什么 | 判据 |
| --- | --- | --- |
| **`[是什么]`** | 事实：模块清单 / 函数清单 / 机制 | 不看代码也知道「是什么」 |
| **`[为什么]`** | 决策：考虑过的方案 + 选择 + 理由 + 被拒方案 | 后来者能回答「为什么不用 X」 |
| **`[不变量]`** | 约束：必须满足的条件 | 每条可判真假，尽量可检查 |

- 写决策需要的信息，不写实现需要的信息：删掉这句话会让实现产生歧义吗？会 → 留；只是更快 → 删。
- 三段之间：`[是什么]` 不放方向；`[为什么]` 只留仍成立的理由；`[不变量]` 优先。
- **必填件归位**：事实 / 步骤 / 例子 → `[是什么]`；选择理由 / 被拒方案 → `[为什么]`；约束 / 危险清单 / 可跑验收 / 失败语义 → `[不变量]`。

## 四、放哪层、写多深

### 4.1 四层

| 层 | 文件 | 装什么 | 何时写 |
| --- | --- | --- | --- |
| **L1** | 项目根 L1 | 方向 / 定位 / 索引 | 立项 |
| **L2** | `docs/architecture.md` | 模块清单 / 主流程 / 架构决策 / 跨模块规格 | 主流程或架构边界要单独讲清 |
| **L3** | `docs/modules/<name>.md` | 模块机制 / 内部约束 / 模块规格 | 某模块的机制要单独讲清 |
| **L4** | `docs/core-analysis.md` | 核心运行视图（可选） | 需要把核心从代码里剥出来看 |

- **按抽象度切，不按主题切**：高层指方向，低层做具体；同一事实只在一层成文。
- **读低层默认已读上层**；同层内部自足；上层列下层；L4 没有下层，不写目录。
- **L4 是阅读视图**：不承载规格 / 不变量 / N2；建它先问作者。

### 4.2 三档

| 档 | 定义 | 判据 | 写法 |
| --- | --- | --- | --- |
| **N0 通用** | 模型见过，且有公认写法 | ① 训练见过 / 能检索到 **且** ② 存在明显唯一的公认写法 | 三段式 |
| **N1 项目特有** | 模型见过类似，但本项目有自己的约定 / 取舍 | 看着眼熟，但存在多个语义相近实现，或项目指定了具体做法 | 三段式一页 |
| **N2 AI 未见** | 没有公认写法，也没有 oracle | 判不出「正确答案长什么样」 | 五件套 |

- **档位属于最小逻辑单元**，不属于文档位置；一个单元一个档。
- **默认 N1 一页**；只有 N2 才加五件套。
- N0 不因「简单」省略不变量；N2 不因「重要」自动成立。

### 4.3 判 N0 要两条同时成立

只满足「训练见过 / 能搜到」= 眼熟；没有**明显唯一**的公认写法，就不是 N0。

**这些领域一律不许判 N0**：金额与舍入、时区与 DST、权限边界、ID 生成、重试与幂等、字符编码、并发读写。它们看着眼熟，但存在多个语义相近实现 → 按 N1 起评，核心单元按 N2。

### 4.4 N2 五件套与住处

五件套：步骤级说明 / 危险实现清单 / 精确例子 / 可跑验收 / 失败语义；缺一不可。

- **模块内** → 该模块 L3 的 N2 栏（没有模块文档就先补一份）。
- **跨模块 / 架构骨架 / 高扇入**（被 ≥2 个模块的工作场景默认加载）→ L2 `docs/architecture.md` 的「N2 单元规格」节，一个单元一节。
- **N2 不落 L4**；跨模块逻辑只许一处成文：五件套记 L2，模块 L3 不复述，按代号引用。
- 模块文档的 `novelty=` 照**模块概念**填；五件套上移 L2 后仍是 N2，档位不因摆放位置降级；L3 只留档位说明，不重复五件套。
- **信号 · 该不该开一份 L3**：某模块的细节一直往 L2 / 别的大文档里堆，而不是堆进它自己的 L3 → 该给它开一份 L3（存量模块同样适用）。

### 4.5 验收

N2 必须有可跑验收；怎么造见 M4 `acceptance.md`。

## 五、L1 问题库（对话地图）

> 给 agent 的对话地图，不是问卷——根据回答自然展开，不要机械地一条条问。每答完一段就立即写入。

### `[是什么]` 段——项目定位

- 这个项目要解决什么问题？（一句话能说清吗）
- 谁会用？用在什么场景？
- **不做什么**（明确边界同样重要）
- 主要功能 / 模块的大致预想？

### `[是什么]` 段——术语

- 有没有**外人听不懂**的词？
- 哪些词**最容易混**？
- 有没有**旧叫法**已废弃？
- 生成代码时必须知道**类型 / 结构**的词有哪些？

### `[为什么]` 段——设计哲学

- 为什么用这个技术栈 / 架构风格？（强约束还是偏好）
- 核心价值观 / 设计哲学，2–3 条？
- 考虑过哪些替代方案？为什么拒绝？

### `[不变量]` 段——硬约束

- 性能预算？（响应时间、吞吐、内存上限）
- 技术栈锁定？（必须用 / 必须不用什么）
- 可维护性底线？（测试覆盖、文档要求）
- 安全 / 合规约束？
- **最怕写成什么样？** 列 3 种「看起来对、语义却错」的实现——这就是危险实现清单，每条后面跟「由哪条不变量 / 验收挡住」。
- **失败路径分别怎么表现？**（超时 / 部分成功 / 冲突并发 / 越权）→ 落到模块文档的失败语义表；别接受「合理处理错误」。

### 时间轴追问（贯穿各段）

- 这条是**过去的选择**、**现在的真相**，还是**未来的意向**？
- 未来：状态是什么？谁拍板？什么情况下移出？
- 历史：读它是为了理由 / 被拒方案 / 方向，还是现状事实？
- 当下：它和代码对得上吗？有没有第二处定义？

## 六、内容自检

- [ ] 新词已登记，且判断过是「领域新行为」还是「通用新名」？

- [ ] 跨模块逻辑只有一处成文吗？
- [ ] 方向有没有混进 `[是什么]`？
