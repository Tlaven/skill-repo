# 验收

> 本文件只管：没有 oracle 时怎么造验收（五种手段）、非功能 / 主观需求怎么落地、两道闸门。
> 读的时机：定 N2 单元 / 非功能 / 视觉需求时。
> **N2 五件套的结构（放哪、三段归位）见项目 methodology（`docs-templates/methodology.md`）；复核怎么派见 `verification.md`；命令怎么执行见 `scripts/`。**
> L4 不适用：阅读视图不给验收，也不被引用。

## 一、为什么单列

N0 / N1 有大量同类测试可抄；N2 没有 oracle，风险不是「忘了写测试」，而是「**测试写了假**」——循环自证、同义反复、只测 happy path。假测试没人能靠肉眼看出来，所以必须用能识破它的手段。

非功能需求同理：功能性有「输入 → 输出」，非功能没有；最常见的失败是做了一个「看起来达标」的版本，验收栏里写着「人工确认」。

## 二、五种手段（按对「无 oracle」的替代力排序，选 1–2 种）

1. **不变量 → property test**（首选）
   - 把每条不变量写成「任意合法输入下恒成立」的断言。
   - 这是 N2 **唯一可靠的 oracle 替代品**。
   - 例：`∀ order, slots: 返回非 None ⇒ slot.used + order.weight <= slot.capacity`
   - 工具：hypothesis (py) / fast-check (js) / proptest (rs) / QuickCheck 类。
2. **mutation testing**（验「测试本身是否有效」）
   - 故意改坏实现，看测试会不会红。红不了 = 这测试没用。
   - 专杀循环自证 / 同义测试。
   - 工具：mutmut / Stryker / cargo-mutants。
3. **approved scenario / golden fixture**（冻结期望）
   - 人工确认过的「输入 → 输出」冻结起来；被破坏必须**重新批准**。
   - 可直接复用 `docs/glossary.md` 的「例子」栏正例——同一事实一处定义。
   - 交互 / 视觉类：配一个可复现状态钩子（URL 参数 / fixture 入口 / 固定种子），把系统预滚到目标状态再截图或断言——**同一状态能反复进入，画面才算证据**。
4. **盲测验证者**（独立找反例）
   - 一个看不到实现、只按文档用系统的人 / agent，专门找反例。
   - 复用 `teach-back-verifier-prompt.md`（同一套独立验证思路）。
5. **differential**（对照）
   - 有旧实现 / 参考实现时，做输出对照。

## 三、危险实现清单 = 现成的变异体

`[不变量]` 段那张「危险实现清单」不是文档装饰，它就是 mutation testing 的**现成变异体**：把「最可能被写成的错样子」真的写出来（或临时改坏实现），看测试红不红。

- 红 → 这条错法已被挡住，把证据写回该清单的「由谁挡住」列（推荐直接写挡它的断言 / 用例；别删行——清单是约束）。
- 不红 → **不是实现错了，是验收不够**，回去补断言。

## 四、非功能需求怎么落地

判据：**能不能写出一条会失败的检查。** 写不出来 = 需求还没定义，不是「实现时注意点」。

**四步转换：**

1. **钉住输入**：这条性质在哪些变量固定时才成立？（数据 / 配置或合同版本 / 引擎版本 / 字体与 DPI / 硬件与并发度）
2. **选可观测量**：换成能测的数或能 diff 的产物（字节、耗时分布、字段集合、几何量）。
3. **定比较方式**：相等 / 逐字节 / 分位数阈值 / 单调 / 覆盖性 / 人工批准冻结。
4. **写成验收**：命令 + 预期，或 property 断言。**必须能失败**——先问「它在什么情况下会红」。

**分类对照表：**

| 需求原话 | 必钉住的输入 | 可观测量 | 验收形态 | 常见错法 |
| --- | --- | --- | --- | --- |
| 结果要稳定 / 可复现 | 数据 + 配置或合同快照 + 引擎版本（+ 字体 / DPI / 随机种子 / 时区库） | 产物的字节或规范化序列 | 同输入双跑 → diff 为空；跨版本重算 → 结果不变 | 只测「两次跑差不多」；把随机数、当前时间、字典序当无关变量 |
| 要快 / 不能卡 | 数据规模 + 并发度 + 运行环境 | 耗时**分布**（P50 / P95 / P99），不是单次 | 基准脚本 + 分位数阈值；回归时对比性能基线 | 用一次 `time` 当验收；不固定规模与环境；只测空数据 |
| 要好看 / 体验要顺 | 输入样本集 + 渲染参数 | 代理指标（最小间隙、重叠数、行数、字距差） | 代理指标断言 + approved fixture | 直接写「人工确认」；拿实现自己的输出当期望 |
| 要安全 / 要合规 | 威胁模型或条款清单 | 字段集合、权限矩阵、日志条目 | schema 校验 / 权限矩阵表驱动 / 审计字段存在性 | 只写「做了鉴权」；只测正例 |
| 不能算错 | 边界样本 | 精确例子 + 守恒等式 | 输入→输出表 + 计数 / 能量守恒断言 | 例子只有名字没有数；例子没人复算 |

## 五、交互 / 视觉类：双测

能自动测的先用**数值断言**（headless / property）；测不了的视觉项用**可复现状态钩子**冻结画面（URL 参数 / 固定种子 / fixture 入口），再截图对比或人工批准。**「同一状态可反复进入」是截图能当证据的前提。**

- 真实踩法：smoke 只打印数字、没有失败退出码 → 永远绿；测量点选错（读终态而不是「触地瞬间」）→ 读数恒为 0。
- 判据：每条视觉验收都要能回答——它**怎么进入**这个状态、**怎么复现**、**什么情况下会红**。

## 六、审美类：唯一允许「主观」的地方

审美没有 oracle，但可以冻结：

1. 让用户在**少量候选**（≥2 个，各自标注代价）里挑；选型按 E-4 分级：不可逆 / 跨模块长期约束进 ADR；可逆 / 局部走 commit body。
2. 把选中的结果做成 **approved fixture**（输入 + 期望产物），之后被改动必须**重新批准**。
3. 同时写一条**代理指标**兜底（如「任意两字最小间隙 ≥ 2pt」「无重叠」），否则 fixture 一换就没人知道底线在哪。
4. 代理指标标 `候选(待否决)`，并登记进未来桶（L1 开放问题 / 项目计划）；在 `[不变量]` 里只引用，不另立结论；用户确认后转正（历史 ADR 或当下不变量）。

## 七、写进文档

在对应层（项目级 → L1；架构级 → L2；模块级 → L3）的 `[不变量]` 段写：

- 钉住的输入（一句话列出全部变量）；
- 可观测量的具体数值或比较方式；
- `**验收**: <命令> → <预期>`，或 property 断言；
- 若用了 approved fixture：写明谁批准（批准人 + commit SHA）；日期放记录，不写进活文档。

N2 的 `**验收**` 栏：命令 + 预期（`pytest tests/test_x.py` → 通过），或 property 断言；并注明用了上面哪 1–2 种手段。

- 写成什么样（`novelty=N2` 字面量、独立一行 `**验收**:…`）见 `docs-templates/module-doc.md` / `docs-templates/architecture.md` 的 N2 说明。
- **跨模块 N2 的五件套只写在 L2 的那一节**；模块文档只保留 `novelty` 档位标记，不重复五件套、不留「验收见 docs/…」的引用行。
- **批量执行**：若已拷入 `scripts/`，可用 `scripts/run-n2-acceptance.py --manifest <file> --run`；没有 manifest 只列不跑，并标「未复跑」。
- **检查器只查形式、判不了语义**：凑一个 `**验收**` 字样就能骗过它；验收是否有意义、错法是否真被挡住，仍归复核。

## 八、先跑一次，再写进约束

要写进文档的断言（不变量 / N2 步骤级说明 / 危险清单 / 失败语义 / 性能预算），只要跑一下就能证伪，就先花十行脚本跑一遍——**跑得出反例的，不许写进文档**。「任意情况下都成立」的（property 型）尤其如此。

- 跑得出反例 → 这条断言不成立，别写；改成「近似相等（给出容差）」或改写断言。
- 跑不出、但你也不确定 → 在约束里标 `经验证：<脚本路径>`，后跟「经验性，非定理」；轮次 / SHA / 组数记进 `docs/reviews/`，不进正文。
- **脚本别丢**：试跑脚本推荐直接长成那条 `**验收**` 的一部分；不留的，就放固定位置（如 `tests/probes/`）并在标记里写路径——没有可复跑的脚本，「经验证」只是一句声称。
- 不能试跑的断言：至少要能说明它「靠什么站住」（外部来源 / 人的裁量）；两样都没有 → 降级为假设 / 开放问题，或明确标「未验证」。

**为什么**：试点里一条「分两次结算 = 一次结算」的断言，文档层面读起来毫无破绽，实测 53% 的随机整数对不成立。复核读不出这种错——它只能验「写得清不清」，验不了「做不做得到」。

## 九、反模式

- 测试拿实现自己的输出当期望（循环自证）
- 断言同义反复
- 只测 happy path
- 只打印、不断言——打印的数字是报告，不是验收；断言必须能失败（非零退出 / 红测试）
- 把「有测试」当成「测试有效」
- 文档声称「已验证 / 全绿」却没有可复跑的命令 / 脚本（或没标「未接入 / 未复跑」）——**声称不是证据**

## 十、两道闸门

### 10.1 N2 规格闸门

某条 N2 逻辑**造不出可跑验收** → 不是「测试先欠着」，而是**逻辑还没讲到可实现**：回去补步骤级说明（跨模块补进 L2 的 `N2: <单元>` 节；模块内补进 L3）。**别放行实现。**

这道条件管的是「逻辑能不能被实现」，**与复核跑不跑无关**——复核是按需工具，不阻塞实现。

### 10.2 非功能需求闸门

某项非功能需求**造不出可失败的检查** → **这条需求还没定义**：回到对话里降成「钉住哪些输入 + 哪个可测代理指标」，或登记进「开放问题」交人拍板。**别放行实现。**

这与 N2 规格是两道门：那道管「逻辑讲到可实现」，这道管「需求定义到可判定」。
