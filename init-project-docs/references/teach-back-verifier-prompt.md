# Teach-back 独立验证者 prompt 模板

Use this template when dispatching a teach-back verifier subagent.

**Purpose:** 判断"只凭这份文档，一个工程师能否正确实现它"——用一个**看不到设计对话**的全新 subagent 来做，消除"同一会话自评"的偏差。

**何时用:** N1 / N2，或任何"进实现前"的闸门。**N0 跳过**（模型自己能补，白花一次调用）。

**关键:** 新开一个 subagent，**不继承本会话历史**；把文档正文**整段粘进 prompt**，不要让 subagent 自己去仓库里读——保证它唯一的输入就是文档本身。

```
Task tool (general-purpose):
  description: "teach-back 验证：<层 / 模块名>"
  prompt: |
    你是一个独立验证者。你没有参与这个项目的任何设计讨论，也看不到那些对话。
    你唯一的输入是下面这份文档。你的任务是判断：只凭这份文档，
    一个工程师能否正确地把它实现出来。

    ## 待验证文档

    [整段粘贴：待验证的那一层文档；如相关，附 docs/glossary.md 的术语表与相关不变量段]

    ## 你的立场

    - 不要相信任何“作者已经说清楚了”的转述；你只能看文档本身。
    - 你不能先提问再判断——你发现的每一个疑问，本身就是一条“发现”，不是等待澄清。
    - 不要评判文风、排版、是否啰嗦；只评判“够不够实现”。

    ## 你要产出三件东西

    ### 1. 复述（用你自己的话）

    逐段复述文档的三段：

    - [是什么]（事实）
    - [为什么]（决策与被拒方案）
    - [不变量]（约束）

    复述时保留原文的词，不要替它“翻译”或“顺手补全”——
    你补全的地方，恰恰是作者可能没说清的地方。

    ### 2. 缺口清单：我需要、但你没给

    对文档里每一处需要动手的地方，先问自己：“我会怎么实现它？”
    凡是你无法只凭文档回答的点，逐条列出，并给每条打一个**级别**：

    | # | 级别 | 我卡在哪 | 我当时想问你什么 | 为什么文档没覆盖 |
    |---|---|---|---|---|
    |   |      |          |                  |                  |

    级别只有两种：

    - [阻断] — 不补就**无法正确实现**：两处规则互相矛盾；失败 / 边界分支未定义；
      同一文档可引出**行为不同**的多种实现；或**根本写不出可跑的验收**。
    - [非阻断] — 实现细节，有经验的工程师按惯例 / 框架即可定
      （例如：数据类型的形态、空白字符集、纯措辞），不影响可观察行为。

    每条都要附一个探针问题来暴露它，例如：
    当 <边界条件> 发生时，应该 <做什么>？

    拿不准时问自己：**这个分叉会让两个工程师做出行为不同的东西吗？会 → [阻断]。**

    ### 3. 判定：通过 / 不通过

    判定只卡**阻断项**：

    - 缺口清单里有 **≥1 条 [阻断]** → 判「不通过」。
    - **只有 [非阻断]**（或没有缺口）→ 判「通过」，并把非阻断项列为“建议”。

    出现以下任一条，一律视为 **[阻断]**：

    - 复述里出现未在术语表中定义的名词（或我看不懂的领域词）
    - 复述或缺口里出现模糊表述：合理处理 / 优化 / 适当 / 相关逻辑 / 等等
    - 你说不出至少一条不变量
    - 该单元标记为 N2（AI 未见），而你只凭文档写不出一个可跑的验收
      （测试 / fixture / 断言）

    ## 输出格式

    ## 复述
    ...

    ## 缺口清单
    | # | 级别 | 我卡在哪 | 我当时想问你什么 | 为什么没覆盖 |
    ...

    ## 判定
    通过 / 不通过（+ 依据）

    ## 若不通过：必须先补的 3 处（只列 [阻断] 项）
    1. <指向具体段落>
    2. ...
    3. ...

    ## 边界

    - 不要修改文档——你不是作者。
    - 不要因为“大概猜得到”就放过一个缺口：猜得到 ≠ 写清楚了。
    - 如果文档确实完整，明确说“通过”，并说明你是怎么验证的
      （例如：我从文档独立推出了验收命令 X 并跑通）。
```

---

## 校准对照（首次上线前拿它当基线测）

- 喂一份**故意留洞**的文档 → 判**不通过**（缺口标 `[阻断]`），且点到那处。
- 喂一份**完整**的文档 → 判**通过**，并给出它是怎么验证的。
- 喂一份**行为明确、只是有点糙**的文档 → 也应判**通过**，缺口只作 `[非阻断]` 建议。

三条都对，这个 prompt 才算合格：太松（发现不了洞＝没用）、太紧（误伤＝没人用）都不行。

## 设计依据

- 骨架借自 `subagent-driven-development/spec-reviewer-prompt.md`（"verify independently / do not trust the report"）。
- 判据写法借自 `writing-skills`（把漏洞堵死、列显式不通过条件）。
- N2 验收要求呼应 `test-driven-development` 与 `verification-before-completion`（先证据后断言）。
