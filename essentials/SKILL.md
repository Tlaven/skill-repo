# Essentials — 弱领域的外部脚手架

## 定位

给 agent 的**先验不可靠的领域**造一副外部脚手架:判断建立在外部证据上,而不是模型直觉。

产物是一份 **essentials 文档**(跨项目可迁移,结构见 `templates/essentials-doc.md`)。三个用途,**缺一不算完成**:

1. **审查**(主用途):该域做设计 / 选型 / 推荐**之前**,先拿它逐条砍自己的提案;
2. **对齐**:作者与 agent 在同一份判断标准上工作;
3. **生长**:从实操摩擦中修订;项目内验证有效后升级为个人级(所有项目可用)。

**不做什么:**

- 不替作者做**价值判断**(好不好玩 / 好不好看 / 手感 / 方向)——价值类一律标「候选,待否决」,作者是评审 oracle;
- 不做工程实现(本 skill 的产物是判断文档,不是代码方案);
- 不对「有唯一公认写法」的领域启动——直接做,造架子是浪费;
- 不产一次性调研报告——跳过「审查」用途的,是报告,不是脚手架。

## 何时用 / 不该用

**该用(触发,任一即进分诊):**

- 作者质疑可靠性:"你可靠吗?" "这是你擅长的领域吗?" "你懂这个吗?" ——**最高优先**;
- 作者点名:"做个脚手架 / 要领 / essentials";
- 你要在**先验可疑**的领域给推荐:该域存在**多个语义相近实现**(金额舍入、时区、权限边界、ID 生成、重试幂等、字符编码、渲染确定性、游戏手感与物理参数……),或**没有先验**,且判断错了会静默扩散。

**分诊(三问;完整版需三问全过):**

| 问 | 答 | 处置 |
|---|---|---|
| ① 该域有唯一公认写法吗? | 有 | 直接做,不造 |
| ② 会重复出现吗? | 只此一次 | **轻量版**:当场核证(带来源)+ 记入任务笔记 |
| ③ 赌注大吗? | 小 | 轻量版 |
| —— | ①没有 + ②重复 + ③大 | **完整版**:造脚手架 |

**不该用:** 已有完善 essentials 的领域(直接用,只做生长);纯执行任务(无判断空间);已知无效的方法(走否决记录 / ADR,不建新文档)。

**强制动作(没有触发词也要做):** 弱领域给推荐前,先给**可靠度声明**——该域先验属哪层:①唯一公认写法 ②多个语义相近实现 ③没有先验。分层不依赖"自知弱点",只需如实报告;②③ 进分诊。

## Workflow

1. **分诊**(上表 + 可靠度声明)。

2. **定范围**:列出这份脚手架要支撑的**判断清单**(将来拿它审什么);补**隐含需求**——作者没说、但显然要满足的要求,逐条列出,请作者确认或标「待确认」。

3. **外部搜集**:
   - **先例优先**:作者点名的参考物(某产品 / 某文章 / 某作品),先挖透它的细节,从细节里取答案;不要拿抽象选项菜单向作者提问;
   - 来源优先序:官方文档 / 标准 > 权威社区实践 > 同类作品前例 > 真实用户报告(issue / 论坛 / 复盘);每条**附链接**;
   - **来源分级**:`【核】`有来源 / `【估】`推断(自估打折看,注明) / `【待补证据】`弱来源;查不到出处的 → 进「开放问题」,不许写成事实;
   - 手段:`web_search` / `web_fetch`;中英双语各搜一轮。

4. **蒸馏与收录**——每条候选按**证据定级**处置:

   | 档 | 条件 | 去处 |
   |---|---|---|
   | 可复用指令 | 跨项目成立且有证据 | 「通例 / 判据」 |
   | 限定示例 | 只在特定条件成立 | 例子 + 写明条件 |
   | 剔除 | 无证据 / 只对单一场景成立 | 丢,或进「开放问题」 |

   **反凑数**:每条通例必须回指**一次真实触发事件**(踩的坑、调研发现、事故);写不出 → 不收。
   **作者评审门**:价值类判断一律「候选,待否决」;作者接受才转正,否决理由进 ADR(或项目等价物)。

5. **当尺子用**(最容易漏的一步):
   - 时机:该域出提案 / 选型 / 推荐**之前**;
   - 动作:提案的每个部件逐条对证——指不回任何一条判据的部件,删或改;
   - 证据判据:改进的证据 = **结构 / 行为变化**(新增选择 / 失败状态 / 技巧轴 / 系统交互,或工程上可复现的行为变化);**术语出现不算**;
   - 试跑优先:能跑 / 能试的先试(声称不是证据);不能试的写出来源或谁拍的板。

6. **生长**:修订触发 = 新摩擦 / 更强来源 / 判断被证伪;版本记录写在文档内;变更史归 git / ADR,**不写进正文**。作者经验由作者补,agent 只代记。

7. **升级**(项目 → 个人级):内容上移到本 skill 的 `references/<domain>.md`;项目版 `docs/<domain>-essentials.md` **冻结为一行指针**;两处并存 = 漂移,禁止。

## 入口

- **项目版(默认)**:复制 `templates/essentials-doc.md` → 项目 `docs/<domain>-essentials.md`,填完删引导注释;在项目 L1(如 `AGENTS.md`)的「本项目特殊工件」登记一行(登记习惯随项目,不重造)。
- **个人级(升级后)**:本 skill `references/<domain>.md`——各项目可见、单源、git 管理;不要在项目里另存一份全文。
- **正例**:`references/sample.md`(一份真实脚手架——学它的格式,别抄它的内容)。

## 示例

**正例 · 一条合格的通例**(摘自 `references/sample.md`):

> 易犯:手感不对就调数字 → 更有效:先分诊(结构 / 参照 / 参数);三层修法完全不同,结构错时调参数 = 打地鼠。

合格点:来自真实摩擦;抽象到跨项目;给出可执行动作。

**反例 1 · 词汇层合规**:通篇引用"张力""可输性""决策深度",但没有新增任何失败状态或选择结构。→ 术语出现、结构照旧:**不算改进,不算收录**。

**反例 2 · 无来源条目**:「玩家会喜欢 X」——无出处、无试跑、无标记。→ 这是编造;正确写法:标「候选,待否决」并附依据,或登记进「开放问题」。

## 边界 · 反模式

- ❌ 无来源条目 / 来源不标强度(`【核】/【估】/【待补证据】`必须带)
- ❌ 为一次性小问题造完整脚手架(仪式化 → 文档通胀)
- ❌ 跳过「当尺子用」(退化为调研存档)
- ❌ 术语合规冒充改进(词汇层)
- ❌ 「候选」当结论引用;跳过作者评审
- ❌ 升级后两处并存(项目版该冻结不冻结)
- ❌ 通例凑数(写不出真实触发事件的条目 → 不收)

## 演化

本 skill 自身按 `seeding-skills` 的纪律生长(从小开始 / 基于观察 / 变更史归 git);本文件只管脚手架**文档**的造、用、长。复盘回改信号:分诊被跳过、架子造了不用、示例被绕过、反例又在现场发生。
