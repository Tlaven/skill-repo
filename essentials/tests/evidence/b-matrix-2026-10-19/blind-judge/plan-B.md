# hoverster 脚手架优化方案

**结论:** 四份脚手架的问题不在于内容质量(file/feel 里的条目确实是从实际摩擦中提炼出来的),而在于**结构上无法用于主用途(审查),以及没有使用记录的证据链**。因此优先级最高的三件事是:**决策卡、稳定条目 ID、使用记录**——这三件不做,后面所有修订都无法判断是“改进”还是“词汇层合规”。方案只做结构改动和条目级搬运,不重写全文。

**审查标准:** 本次只读 `MATERIALS.md`(340 行),下文 `L   ` 均为该材料的行号;未联网、未读其他文件。涉及“哪条该留/该删”的价值判断一律标「候选,待作者否决」。

   1. 问题清单(10 条,按优先级)

    P0 — 阻断主用途(审查)

**P1 · 四份文档都没有决策卡,决策时只能读完整份文档,或者不读。**
影响:方法里“审查”是主用途,而审查的成本是决策时能否在 10 行内读完。现在 feel 正文约 70 行(4 条观察 + 23 条通例 + 3 条程序,L209–L246),加载表又只写“进弱领域 → + `docs/scaffolds/`(相关的)”(L7),等于把“读哪份、读到哪一层”留给 agent 临时判断。
证据:L336「四份文档均无「决策卡」、无「使用记录」」;L7 的登记与加载各只有一行指针。

**P2 · 无使用记录 → “用了且改变了决策”与“只是引用了”无法区分,转正 / 到期 / 删除三条规则全部悬空。**
影响:方法要求“候选→已验证”必须有至少一次可查的“因它改变”,否则不许宣称有效。现在唯一的可考使用是一段叙述(L314–L323),而且它没有进任何记录;其余 6 次触碰 scaffolds 的提交都是“文档更新”类(L293–L303),引用的是版本号 + 序号(L308–L311)。
证据:L338「提交信息引用条目编号…只出现在“文档更新”类提交里;没有决策类提交引用 ` T<n>`」;L339「任务笔记有“首次按手感脚手架走流程”的叙述,但没有 `feel T<n>` 形式的引用」;L340「正式评审(v0 候选 → 已验证)从未发生」。

**P3 · 条目没有稳定 ID,引用坐标是「文档 + 版本号 + 序号」,会随版本漂移。**
影响:历史提交里的“通例22”只有在序号永不重排的前提下才能定位;而 feel 已经在做**修订**(L270 修订通例 20)、并且下一条动作是合并(见 P6),一旦重排,git 史里所有“通例N”都变成悬空引用。
证据:L308–L311 四条引用全部写成「手感脚手架 v0.9(通例22)」这种双坐标;L267/L268 用「通例 17/18」交叉引用,L322 用「通例 13/14」交叉引用——都靠序号。

    P0 — 证据完整性

**P4 · 证据等级缺失,且范围声明与正文自相矛盾:来源被“略”掉,本地标定被写成通用。**
影响:方法里唯一有增量的是“反先验事实”,其前提是能核验。来源省略后,feel / dev 的条目与“AI 凭先验写出来的”在文本上不可区分——这正是这些脚手架要防的东西。
证据:
- L139「来源清单:(略——与本地标定无关,保留原文链接 15 条)」;L256「来源精选:(7 条外部链接,略)」。
- L337「文档头都写“只写跨项目通用”,但 feel 的通例 17–23 含大量本项目实测数值 / 公式」。实例:L235 `v ≤ √((g + F贴/m)·R)` + L267「推导出 10.8 m/s」;L240「线性外推会系统性乐观(实测偏 30%+)」;L268「落地 58°/5.6 → 1°/0.35」。
- dev 6 条技术栈判据(L105–L110)零来源;game-design 六条标准(L21–L24)零来源;全文只有 L133 一条 `【弱来源,待补强】`。
- 声明冲突:L68「本作的具体决定(选哪个引擎等)…不进本文件」vs L103 内嵌「本作已产出:adr-001-engine-and-platform.md(proposed)」;L92–L97 分档表带「本作」列。

    P1 — 结构与生长

**P5 · 四份文档四种骨架,域边界重叠,而且没有“哪份是权威”的规则。**
影响:同一类判断在两份文档里各写一遍,加载任一份都可能漏;跨项目复用时(方法里的“整份复制过去”)要按新骨架重排一次。作者已经因为这件事提过两次要求,说明这是真实摩擦而非我的偏好。
证据:game-design 中段是「成败标准 + 评估维度 + 失败模式表」(L19–L51),dev 是「事实 + 分档表 + 判据」(L72–L112),collab 与 feel 是「观察 + 通例表 + 作者经验」(L155–L185 / L207–L250);L197 版本记录「格式对齐 `dev-essentials`;触发:作者:“参考已认可的格式”」;L196「升抽象层级…作者:“写抽象一点”」。重叠实例:同一文档内 L210(观察 2)与 L222(通例 5)是同一判断的两份文本,连“打地鼠”的措辞都重复;跨文档 L22(失败即内容)与 L228(失败要可恢复)覆盖同一件事的不同层。

**P6 · 生长只有“追加”,没有合并 / 修订 / 删除路径,条目按事故流水线性膨胀。**
影响:23 条通例里有 4 条(T20–T23)是**同一场“自动层”事故的四个切面**,分别进 v0.7–v0.10(L269–L272);提交 66b67e8 自己就写着“三个根因”。这样下去,条目数会与事故次数成正比,决策卡永远写不进 10 行。
证据:L269–L272 四条连续新增;L281「66b67e8 修落地:倒扣下落蹭地(三个根因:触地时间估计/差动半砍/翻转刹车目标)」;L332「feel … 23 条 … 2026-10-18 一天 10 版」;方法要求“到期删除 + 修订触发”,但四份文档无一条删除或合并记录。

**P7 · 状态语义三档并存,又没有归档/到期,导致“候选”永久候选、“使命结束”的文档仍挂在加载路径上。**
影响:读者无法判断一条判断现在能不能当依据用;而 game-design / dev 大概率不是“没做好”,是**已经做完了**(设计阶段结束、引擎已决)。
证据:L15 / L67「v0 · 候选(待作者评审)」;L151 / L201「记录和尝试(持续增补,不勉强凑数)」;L329「game-design … 设计阶段结束后未更新」;L330「dev … 引擎决策后未更新」;L340「正式评审…从未发生」。

**P8 · 强制程序停在“问句”,没有落成必答项或可跑的检查;条目也没有“检查形式”与「观察项」上限。**
影响:方法要求每条通例落成 ① 可跑检查 ② 交付物必答项 ③ 强制步骤 之一,落不成的标「观察项」且 ≤5 条。现在 23 条通例与 3 条程序之间没有映射,哪些是“必须做的动作”、哪些只是“看着点”,读不出来。
证据:L246「验收:改完怎么测?数值先跑(headless / 断言),画面后看(可复现截图);手测留给人」——是问句,没有产物名;而 L321 说明实操里**已经**产出了正确形态:「探针全谱(4.2–32 m/s 入弯)零翻车…smoke 新增 [急转] 与 [慢转]」——这个形态没有被写成必答项,所以下次仍靠人记得。

    P2 — 卫生

**P9 · 作者裁决(整套材料里最不可检索的内容)被埋在版本表的“触发”列,而「作者经验」两处是空壳。**
影响:方法明确“价值判断只有作者能做、agent 只代记”。这些原话现在是最容易丢的东西:它们在一个几乎不被人读的列里,且没有抽象成可复用规则。
证据:L196「作者:“写抽象一点”」;L197「作者:“参考已认可的格式”」;L262「作者:“总结之前的改进记录,再做一个脚手架”」;L270「作者:“松手可以自动回平,但不着急时慢一点省气”」;L271「作者:“让翻转转完,别强行快速降转动惯量”」;L272「作者:“又不能平稳落地了,特别是倒着下落”」。对照:L250「(待作者补充)」、L185 仅一条。

**P10 · 审计痕迹(提交摘要 / 统计 / 其他事实)混进脚手架正文,而且诊断已经写出来却没有触发任何改动。**
影响:脚手架正文应只放判断;变更史归 git / 任务笔记。更要紧的是:L336–L340 那五条“其他事实”**就是本清单 P1–P3 的诊断**,它们已经写进文档,却没有任何一条被转成修订动作——这说明缺的不是发现问题的能力,是“诊断→动作”的通道。
证据:L274–L340 共 67 行,内容为提交记录(L278–L291)、触碰 scaffolds 的提交(L293–L303)、引用样例(L305–L312)、task_plan 节选(L314–L323)、文档统计(L325–L332)、其他事实(L334–L340)。

   2. 改动方案(与上表 1:1;标注「结构级 / 条目级」)

**P1(结构级)· 给每份文档加一张决策卡,并改加载语义。**
- 文档头加 `   决策卡(决策时只读这 10 行)`,固定五问:哪一层(结构/参照/参数)→ 参照物有没有名字+来源 → 受力与坐标系 → 是不是在用辅助/砍输入兜物理 → 验收产物在哪。每条问句后挂条目的稳定 ID。
- feel 决策卡骨架(示例,约 8 行,不是重写正文):
  ```
  触发:改键位 / 相机 / 反馈 / 受力点 / 自动层 / 落地姿态。
  ① 这次"不对"属哪层:结构 / 参照 / 参数?→ T5·观察2
  ② 参照物有名字+来源吗?没有先找 → 强制程序 2
  ③ 作用点相对质心?依取向的力写在机体坐标系?→ T4 / T17
  ④ 是否在用砍输入或加辅助兜物理与几何?→ T13 / T15 / T20
  ⑤ 验收产物:数值断言 + smoke 用例名 + 画面钩子,缺一不算"修好" → 强制程序 3
  细则:T1–T23 正文;本项目数值只在附录 A 取。
  ```
- AGENTS.md 加载表一行改为:`进弱领域 → 先只读 docs/scaffolds/<域>-essentials.md 的「决策卡」;复盘/生长才读正文`。

**P2(结构级)· 加「使用记录」表 + 转正/到期规则 + 提交信息约定。**
- 文末表:`| 日期 | 条目 ID | 用在哪 | 改变了什么决策 |`;每次使用一行,空行不算。
- 转正:候选 → 已验证,须至少 1 行使用记录,其“改变了什么决策”非空。
- 到期:2 周或 5 次使用内 0 触发 → 删条目(留 git),首轮只标记不删(见 R6)。
- 约定:决策类提交正文必须带 `feel T20` 形式;文档更新类提交可只带版本号。
- **回填一次历史**:L314–L323 那次只能为「强制程序 1(分诊)」与「T5」记一条——`T13/T14 是它的产物,不能拿来自证`(这一点必须写明,否则记录一开始就是自证的)。

**P3(结构级)· 稳定 ID + 只增不删的别名表。**
- 条目一律改称 `feel T17`、`collab C4`;编号分配后**永不重排**;新增取未用号。
- 新增 `   别名 / 合并` 表(只增不删):`通例22 → feel T20③`、`通例21 → feel T20②`、`通例5 → 观察2`。任何合并/删除**先登此表再动正文**,保证老提交信息仍可解析。

**P4(条目级,不删内容)· 恢复来源指针 + 拆分本地标定 + 加证据档。**
- (a) 把 L139 的 15 条、L256 的 7 条从“略”恢复为文末清单;当前无网,只能恢复**结构位置**,内容先标 `【待补证据】`,不允许以 `【核】` 姿态出现。
- (b) feel 通例表加 `证据` 列:`【核】`(带链接)/`【估】`/`【待补证据】`/`【本地标定·hoverster】`。
- (c) 本项目数值搬到 `   附录 A · 本地标定(hoverster 实测)`,每行带条件 + 提交 hash:10.8 m/s(L267)、30%+ 偏差(L240)、58°/5.6→1°/0.35(L268)、16.1 m/s→179°、4.2/8.9→6.2°/26.9°、latAccelMax 6.5/9.6、侧倾 ≤3.4°(L319–L321)。正文只留**可迁移的形式**(分层、公式、判据)。
- (d) 修声明冲突:L103 与 L92–L97 的「本作」内容移入 `docs/design-contract.md` 指针,或把 L68 的声明改成“可以留一行指针,不留具体参数”。
- (e) game-design 六条标准补 `【待补证据】` 或降级标「候选,待否决」——**不删**,因为它们可能是作者的价值判断。

**P5(结构级)· 只统一“外壳七槽”,不强推中段。**
- 七槽:① 状态行(三值)② 决策卡 ③ 正文 ④ 强制程序 ⑤ 作者经验 ⑥ 使用记录 ⑦ 来源(带档)。
- 中段允许两形态:形态 A =「成败标准 + 评估维度」(game-design),形态 B =「观察 + 通例表」(feel / collab)。**不把标准改成表格**——这一条是刻意选的,理由见 R4。
- 去重:`T5` 删除,替换为 `见观察 2`(逐字重复,L210/L222);`T11` 与 game-design 标准 2 的关系写成一行指针 `见 game-design 标准2`,不复制。
- 路由表放 AGENTS.md(4 行):键位/相机/反馈/力 → feel;引擎/物理/拟真度/范围 → dev;玩法/成败标准/评审 → game-design;方向/沟通/提案 → collab。规则一条:**同一判断只在一份“主存”,其余只放指针。**

**P6(条目级)· 合并同源条目,保留触发与数值。**
- `T20+T21+T22+T23 → T20 自动层三问`:① 权限(常驻控制器是看不见的推力,先补动词再谈自动;分档:不急=宽容差低出力、急=满权限;耗气 ∝ 推力)② 表示(轴+角/atan2 在 ±π 跳变,逐帧 unwrap;死区角速度 > A·dt)③ 时序(有动量顺着走完,只刹不加;预测含加速度)。
- 合并条目下方保留:`【触发】…作者原话 + 提交 66b67e8` 与 `【本地标定】58°/5.6 → 1°/0.35 → 附录 A`。
- 通例表加 `触发` 列(1 行,锚到版本行或 commit),满足“每条通例回指一次真实触发事件”。
- 目标:feel 条目 23 → ≤16;合并动作各自单独成一个提交,便于回退。

**P7(条目级)· 状态只留三个值 + 归档而非删除。**
- 合法值:`候选(待否决)` / `已验证` / `归档`。“记录和尝试”改标 `候选`,“持续增补”改由使用记录 + 到期机制承担,不再当形容词用。
- game-design / dev 走归档:文件头一行 `归档 2026-10-18:因<设计阶段结束 / ADR-001 已决>;重开条件:<新项目 / 引擎变更>。不再修订。`,并从加载表摘掉;文件仍留在 `docs/scaffolds/`(见 R3)。

**P8(条目级)· 把强制程序写成必答三行,并给条目加“形式”列。**
- feel 强制程序 3 改为必答:
  ```
  3. 验收必答(缺一不许说"修好"):
     - 数值断言:文件 + 断言名 / smoke 用例名(例:smoke [急转] [慢转])
     - 画面钩子:命令 + 参数(可复现截图)
     - 手测:作者确认一行
  ```
  依据是 L321 已经这么做了——零新增成本,只是把既有做法写成必答。
- 每条通例加 `形式` 列 ∈ {断言, 必答项, 步骤, 观察};`观察` 全文 ≤5 条,超出必须转成断言或降级进「开放问题」。

**P9(条目级)· 把作者原话抽进「作者经验」,版本表只留指针。**
- 格式:`【作者·2026-10-18】"松手可以自动回平,但不着急时慢一点省气" → T20①(分档)`,共 6 条:L196、L197、L262、L266、L270、L271、L272。

**P10(结构级)· 审计痕迹外迁,并建立“诊断→动作”闭环。**
- L274–L340 整体移到任务笔记 / `docs/experiment-log.md`(L6 已存在该文件)或 `docs/scaffolds/_audit-2026-10-18.md`;feel 正文只留 `使用记录` 表 + 一行指针。
- L336–L340 五条逐条映射到本方案的 P1 / P2 / P3 / P6 / P7,作为该次修订的提交正文——让这条已存在的诊断第一次产出改动。

   4. 验证(怎么确认改动有效)

**原则:** 证据 = 行为/结构变化,不是术语出现。下列 A 类为可跑检查(应写成脚本/断言),B 类为可观察行为,C 类为对照。

**A. 可跑的结构断言(改完当天可跑)**
- **A1 外壳完整性(每个 md):** 必含 `决策卡`(≤10 行)、`强制程序`、`作者经验`、`使用记录`、`来源` 五节;缺一节即 fail。
- **A2 证据档完整性:** 每条条目行必须含 `【核】/【估】/【待补证据】/【本地标定】` 之一;`【核】` 必须带链接;game-design 允许全为 `【待补证据】`,但不允许为空。
- **A3 引用可定位:** `grep -rn "通例\s*[0-9]\+"` 全仓(含 git log)后,每个命中都能在别名表或正文解析到目标 ID;悬空 = fail。
- **A4 状态合法值:** 状态字段只允许三个值;归档文档在加载表里命中数 = 0。
- **A5 体积回归:** feel 通例 ≤16、决策卡 ≤10 行、feel 总行数不高于改动前。超了说明改动在制造通胀。

**B. 行为验证(2 周内)**
- **B1 冷启动:** 新会话只给 AGENTS.md + 决策卡,做 5 次抽测(键位/相机/受力/自动层/落地姿态)。判据:≥4 次命中正确域文档 + 命中正确条目 ID。**这是主判据**,因为它测的正是“主用途能不能执行”。
- **B2 决策类提交引用:** 2 周内 `git log --grep="feel T"` 至少 1 条来自决策/修复类提交(不是文档更新类)。0 条 = 改动失败,回到 P1 重新设计入口。
- **B3 使用记录质量:** 到期检查时,每条被引用的 ID 的“改变了什么决策”列非空;空值行不计入转正依据。
- **B4 信息守恒:** 改动前给每条将被合并/搬移的条目取一个唯一串(如 `58°/5.6`、`别强行快速降转动惯量`),改动后 grep 全仓,必须仍在 (a) 合并条目 (b) 附录 A (c) 别名表 (d) 归档文件 四处之一出现。缺一即回退该条。

**C. 对照(可选,且只作方向不作结论)**
- **C1 同任务三组:** 无脚手架 / 只决策卡 / 全文档,同一任务各跑一次,比 (a) 分诊是否命中层 (b) 是否产出“数值断言 + smoke 用例名” (c) 作者否决次数。样本只有 1,按方法纪律**不得**据此宣布“更好”,只记录方向。

**D. 我建议的落地顺序(依赖关系)**
P3(稳定 ID)→ P2(使用记录,含回填)→ P1(决策卡)→ P4(证据档)→ P6(合并)→ P8(执行化)→ P7(归档)→ P5(骨架/路由)→ P9(作者经验)→ P10(外迁)。
理由:没有 ID 就无法写记录,没有记录就无法判断合并/删除是否伤了东西——P3/P2 是其余八项的证据基础设施。
