# hoverster 脚手架优化方案(组2)

> **口径**:`L<n>` = `MATERIALS.md` 行号;「脚手架」指 `docs/scaffolds/` 下 4 份文档 + `AGENTS.md`(L1)的两行登记(L6-7)。排序依据:先按“规则**是否被使用、是否可信**”排序,再按“是否好用、是否整洁”排序。本方案只做结构与条目级编辑,**不改任何一条规则的判断内容**。

## 0. 结论先行

四份文档的问题不在内容质量,而在于**只有写入、没有读取**:手感脚手架 23 条规则靠即时反馈在一天内长了 10 版(L262-272、L332),却没有任何一次决策类提交引用它(L338-339);唯一有“每条带来源”纪律的 dev,把 15 条来源写成了“略”(L139)。所以最高优先级不是补内容、也不是压缩篇幅,而是**先给规则装上 ID、来源和命中记录**——否则合并、裁撤、评审都无法判断该动哪一条。

---

## 1. 问题清单(11 条,按优先级)

### P1 · 写而不读:脚手架没有消费端
- **证据**:L336「四份文档均无「决策卡」、无「使用记录」」;L338 提交信息引用条目编号「只出现在“文档更新”类提交里」;L339 无 `feel#T<n>` 形式的引用;L340「正式评审(v0 候选 → 已验证)**从未发生**」。
- **后果**:规则有效与否不可测,无效条目与有效条目权重相同;“候选”状态永久悬挂(L15、L67)。
- **要保留的正例**:L103 是全文**唯一**一处“规则 → 决定页”的双向引用(dev 判据 → `adr-001`),应作为模板推广。

### P2 · 只增不减:活文档在单调膨胀
- **证据**:L262-272 共 11 条版本记录 = **10 次新增 + 1 次修订(v0.8)+ 0 次删除合并**;L332「2026-10-18 一天 10 版」;L327-332 条数:feel 23 / collab 11 / dev 4 事实 + 6 判据 / game-design 4+6。
- **后果**:加载与维护成本线性上涨,重复条目无人清理(P5);“条数/版数”事实上变成了进度指标,激励方向反了。

### P3 · 边界失守:项目细节与仓库痕迹进了“通用”脚手架
- **证据**:L337 自述 feel 通例 17-23 含本项目实测数值/公式;实例:L235(`v ≤ √((g+F贴/m)·R)`)、L267(10.8 m/s)、L268(落地 58°/5.6 → 1°/0.35)、L240(实测偏 30%+)。更严重的是整段项目痕迹:L279-291(12 条 commit hash)、L295-303(触碰 scaffolds 的 7 条提交)、L307-312、L316-323(task_plan 节选)、L327-332(文档统计)。
- **与自定规则直接冲突**:L16、L68、L153、L205 四处都写“只收跨作品可迁移 / 只写跨项目通用”;L190、L255 又要求“整份复制过去”——复制后 hash、任务笔记、`ADR-003` 全是悬空引用。

### P4 · 证据链断裂:来源被写成“略”
- **证据**:L139「来源清单:(略——…保留原文链接 15 条)」;L256「来源精选:(7 条外部链接,略)」;L17 game-design 只有“会话讨论与公开资料的初步综合”,零内联来源;全库只有 L69 有分级纪律(【待补证据】/弱来源)。
- **后果**:这套方法唯一站得住的地方是“把对开发域的判断建立在外部证据上,而不是 AI 直觉”(L138),但它恰恰在来源上落空——读者无法核证任何一条。此外 feel 23 条里只有 T13-T23 有逐条触发记录,**T1-T12 共用一行**(L262「从改进记录(相机/键位/受力/验证)抽象」)。

### P5 · 重复与同源条目(至少 5 条)
- **证据**:① L210(观察 §一.2“分诊三层”)≈ L222(通例 5“先分诊”);② L212(观察 §一.4“反馈性价比之王”)≈ L226(通例 9“反馈先行”);③ L233(通例 16“先盘点缺的动词”)≈ L237(通例 20 同一句);④ L230(T13 条件优先于砍输入)、L232(T15 几何优先于辅助)、L237(T20 别用自动保持替代)是同一原则的三次书写;⑤ L228(T11 失败可恢复)≈ L22(game-design 标准 2 失败即内容)。
- **后果**:同一条规则两处维护,改一份忘一份即分叉。

### P6 · 引用靠自然序号,插入一条即全库失效
- **证据**:L44-51 失败模式表的“挡它的”列写“维度 1 / 2 / 3 / 5”“标准 2 / 3”;L128“强制程序 1”;L338 提交里写“通例 22”。全是位置序号或自由文本,没有稳定 ID——game-design §二(L28-33)插一条维度,整列引用全错。

### P7 · 结构、状态词、命名三套并存
- **证据**:版本表位置不一——game-design 在 §五 内(L53-61)、collab(L187-193)、feel(L252-260)也在 §五 内,但 **dev 是正文后的独立 H2**(L141);状态词两套:「v0 · 候选(待作者评审)」(L15、L67) vs 「记录和尝试(持续增补,不勉强凑数)」(L151、L203);标题口径不一:collab/feel 标“通用”(L149、L201),feel 的用法却收窄到“直接操控一个物理主体的游戏”(L204)。

### P8 · 加载口径粗,且无冲突裁决
- **证据**:L7 全部约定只有 L1 一行登记 + 加载表一行“进弱领域 → + `docs/scaffolds/`(相关的)”——4 份文件、23 条规则,没有“任务类型 → 文件/条目”映射,也没有“何时**不**加载”。冲突实例:L230(T13 砍输入是最后手段)vs L233(T16 辅助默认开);L39(game-design 禁止 craft 参与“好不好玩”的论证)vs L212、L226(反馈先行、性价比之王)——两套轴本来分得清,但四份文件没有一处写清优先级。

### P9 · 强制程序四份各写一遍,且没有复核节奏
- **证据**:条目数 4 / 5 / 3 / 3(L37-40、L116-120、L179-181、L244-246),内容互相重叠(都要“先复现/先找参照”)。修订触发只有“发生新摩擦/被证伪”(L55、L137、L189),**feel 连证伪都没有**,只写“抽象成通例追加”(L254);没有“到期复核”“从未被引用则退役”的路径。

### P10 · 空占位与残留
- **证据**:L250「(待作者补充)」单列一整节;L185 collab 的“作者经验”只有 1 行却占一节;L139、L256 两处“略”。

### P11 · 库存失真:统计表与正文对不上,且统计本身不该住在脚手架里
- **证据**:L329 称 game-design「6 条标准 + 6 条失败」,正文实为 4 条成败标准(L21-24)+ 6 条评估维度(L28-33)+ 6 条失败模式(L44-51);L327-332 描述的是四份文档的项目状态,却被写进脚手架内部,必然随文档改动腐坏。

## 2. 改动方案

### 2.0 目标结构(只加 3 个文件,不重写任何正文)

```
docs/scaffolds/
├─ README.md          # 索引:域 / 加载触发 / 状态 / 条数 / 最近验证 / 上游决定   [新]
├─ protocol.md        # 共用强制程序 + 收录闸门 + 复核规则 + 冲突优先级          [新]
├─ usage-log.md       # 日期 / 提交 / 条目 ID / 怎么用的 / 结果                  [新]
├─ game-design-essentials.md
├─ dev-essentials.md
├─ collab-essentials.md
└─ feel-essentials.md
```

L1 的两行登记保留,第二行(L7)改为指向 `docs/scaffolds/README.md`,由索引承担“哪份、何时加载、现在什么状态”。

### 2.2 ID 与规则 schema

**ID**:`GD-S1..S4`(成败标准)/ `GD-D1..D6`(维度)/ `GD-P1..P4`(程序)/ `GD-F1..F6`(失败);`DEV-F1..F4` / `DEV-L0..L3` / `DEV-C1..C6` / `DEV-P1..P5` / `DEV-M1..M6`;`COL-R1..R11`;`FEEL-R1..R23`。
**兼容**:通例 n 恒等于 `FEEL-Rn`,历史提交里的“通例 22”(L338)仍可解析,不必改写历史。

规则表从 3 列变 5 列:

| ID | 易犯的模式 | 更有效的做法 | 何时不适用 / 反例 | 证据 |
|---|---|---|---|---|
| FEEL-R23 | 自动层按“预测时间”触发却用线性外推 | 按真实运动学 `t=(v+√(v²+2gy))/g`;低基准下差动不要对半砍 | 无重力/匀速场景不适用 | B:ADR-003 补充4(L272) |

**成本约束**:作者只写“模式 / 做法”两列,`ID`、`证据`、`何时不适用` 由 agent 从 git 记录回填,每条净增 ≤2 个短字段。这条限制是为了不破坏作者“即时反馈即刻追加”的生长机制(L332 一天 10 版)。

### 2.3 状态机(替代现有两套状态词)

`draft → trial → adopted → validated → retired`,另加 `dormant`(阶段结束、保留)。

- `adopted` = usage-log 里 ≥3 次真实使用;`validated` = 一次正式评审 **且** ≥1 次在别的项目复用。
- 现状映射:game-design / dev → `draft·dormant`(依据 L329-330「设计阶段结束后未更新」「引擎决策后未更新」);collab → `trial`;feel → `adopted`(L262-272 有 10 次实战触发),**不能**直接写 `validated`(L340)。

### 2.4 冲突优先级(写进 README 一处,不在四份里各写一遍)

> 项目决定(`design-contract.md` / `ADR`) > 脚手架规则;脚手架内 主则 > 例外子项;“好不好玩”(GD 维度)与“做得好不好”(craft/手感反馈)**互不作证**(承接 L39 与 L212 的表面张力)。

### 2.5 执行批次(顺序本身就是风控)

| 批次 | 内容 | 判断标准 | 回滚 |
|---|---|---|---|
| **批 0** 纯机械(约半天) | 加 ID、建 README、状态词统一、两处“略”展开抄录、版本表移位、统计失真修正 | 零判断 | 单 commit 可 revert |
| **批 1** 只增不删 | 加 schema 两列、建 usage-log、写 protocol.md 的闸门与优先级 | 不改任何一句规则 | 可 revert |
| **批 2** 有删除 | 去重合并、项目痕迹外迁、game-design/dev 标 dormant、版本表压缩 | **必须在批 0/1 之后** | 打 tag 后执行 |

## 4. 验证

### 4.1 机械可查(脚本化)

| 指标 | 现状基线 | 目标 | 查法 |
|---|---|---|---|
| 悬空引用 | 0 个 ID,无从校验 | 定义集 ⊇ 引用集,0 悬空 | 全库 grep `(GD\|DEV\|COL\|FEEL)-[A-Z]\d+` 对照定义表 |
| 决策提交引用率 | **0**(L338-339 明说无 `#T<n>`) | 新增决策类提交 ≥80% 带 ID | `git log` 按类型分类计数 |
| 证据覆盖 | A 级在线 **0**(两处“略”) | 每条“证据”列非空 100%,A/B 合计 ≥60% | 表格字段校验 |
| 单文件条数 | feel 23 / collab 11 | ≤20 条/份 | 计数 |
| 状态一致性 | 两套状态词 + 1 个永不评审的“候选” | 6 值状态机;`validated` 必有 usage-log 支撑 | 交叉检查 |

### 4.2 可移植性测试(验 L190 / L255 的“整份复制”是否真成立)
把改后的 feel 复制进空目录、断网,让一个不知道 hoverster 的 agent 回答 3 问:落地前怎么估触地时间 / 倒挂时下压力写哪个坐标系 / “太难操作”先做什么。**判定**:只用文件内信息可答,且不出现 commit hash、任务笔记、`ADR-003` 悬空引用。现在这一测会失败(L279-291、L316-323、L237)。

### 4.3 加载映射测试
给 5 个真实任务描述(改相机 / 调落地 / 选引擎 / 方向讨论 / 加一个场景),看 README 的“任务→条目”表能否**唯一**命中一份文件 + 1-3 条规则。命中过多或过少都算失败,用来校准 C8。

### 4.4 成本
单文件 CJK 字数 + 一次任务实际加载的条目数。目标:命中率不降的前提下 feel 从 23 → 21 条,字数降 ≥10%(靠去重与指针,不靠删内容)。

### 4.5 历史回测(最重要:验的是“还有效”,不是“更整齐”)
取 3 个已结案事件,**只给“现象 + 脚手架”**,看命中条目与原始修法是否一致:

- 平地转向翻车(L317-323)→ 应命中 R13(条件优先)/ R14(参数配比对);
- 倒挂坡(L301、L267)→ 应命中 R17(机体坐标系)/ R18(进坡速度上限);
- 倒扣下落落地不稳(L272、L281“三个根因”)→ 应命中 R23,并连带 R19 / R22。

**判定**:合并前后命中同一条的比例不下降;若某条在全部回测中从未命中,它是**退役候选**——用数据裁,不用感觉裁。
**注意**:T1-T12 没有逐条触发记录(L262),回测必须回到它们诞生的“相机 / 键位 / 受力 / 验证”改进记录,否则这 12 条永远无法裁决。

### 4.6 留一法
对每个合并组(R13+R15、R16+R20),代入该组最近一次实战,检查合并后的“主则 + 子项”是否仍能推出当时的修法。推不出 → 不合并。

### 4.7 作者盲评
同一个新问题(如“高速入弯推头”),分别用旧版 23 条与新版 21 条给建议,作者只判“更可执行 / 一样 / 更差”,N=5。这是唯一能验证“少而准是否真的更好”的手段。

### 4.8 复审闹钟(防 P2 复发)
